By the end of this page your package manager installs through apm, and `apm add` checks a package before it installs it.

The registry is `https://registry.apmjs.dev/`. It serves every npm package, and adds a score, yank and revoke on top.

Moving a project that already installs from npm? [Move an existing project to apm](/guides/migrate) covers lockfiles, CI, teammates and how to switch back.

## 1. Point your package manager at apm

Pick your package manager. Each setting goes in the project folder, so it applies to that project only.

<Tabs>
  <Tab title="Bun">
    Add this to `bunfig.toml`. Bun then installs through apm: new installs skip revoked, yanked and confirmed-malicious versions and the versions the OSSF malicious-packages feed lists.

    ```toml title="bunfig.toml"
    [install]
    registry = "https://registry.apmjs.dev/"
    ```

    Optional: the [Bun scanner](/guides/bun-scanner) also makes `bun install` warn about versions scoring under 40. It is not on a registry yet, so you install it from a clone of apm first, as its guide shows. Add its `[install.security]` lines only after that: with the scanner named in `bunfig.toml` but not installed, every `bun install` fails.
  </Tab>
  <Tab title="npm">
    Add this to `.npmrc`. npm then installs through apm: new installs skip revoked, yanked and confirmed-malicious versions and the versions the OSSF malicious-packages feed lists. Even to an existing lockfile, the tarballs of revoked and confirmed-malicious versions answer 410, and the tarballs of other OSSF-listed versions answer 403 with the version's MAL- id.

    ```ini title=".npmrc"
    registry=https://registry.apmjs.dev/
    ```
  </Tab>
  <Tab title="pnpm">
    pnpm reads the same `.npmrc` as npm.

    ```ini title=".npmrc"
    registry=https://registry.apmjs.dev/
    ```
  </Tab>
</Tabs>

Then install as usual (`bun install`, `npm install`, `pnpm install`). Packages come from apm, which fetches them from npm, checks each tarball against npm's checksum and scores it.

apm's package documents leave out fields npm's have and no install reads from them: each version keeps its install fields, scripts, links and checksums, and drops the rest (`licenseText`, `readme`, the `exports` map, npm's signatures), and the abbreviated form installs use has no `devDependencies`. `npm view <package> devDependencies` still works. The full list is in [What apm's packuments leave out](/reference/http-api#what-apms-packuments-leave-out).

:::tip
For a strict mode with stock npm or pnpm, use `registry=https://registry.apmjs.dev/~safe/` instead. The [`~safe` view](/guides/safe-view) hides versions under 24 hours old, versions scoring under 40 and versions apm has not fully analysed, so some very large packages have no version it can install. Today that includes `next`. To install it anyway, use the plain registry and `apm add` without `--strict`, which warns that apm read only part of it; `--strict` and `apm audit` flag it too.
:::

## 2. Get the apm CLI

:::note[Windows]
The apm CLI runs on macOS and Linux. On Windows, run it in WSL (Windows Subsystem for Linux): open a WSL shell and use the install script below there. There is no native Windows CLI yet; in Git Bash or MSYS the script stops with "Windows is not supported yet". [Step 1](#1-point-your-package-manager-at-apm) needs no CLI, so npm, pnpm and bun on Windows still install through apm.
:::

:::note[Which apm is this?]
This apm installs only from `https://apmjs.dev/install` or `brew install opencoredev/tap/apm`. Other tools share the name: the npm packages `apm` and `apmjs` (an AMD package manager) are unrelated, plain `brew install apm` installs Microsoft's Agent Package Manager from homebrew/core, and the Atom editor's package manager was also called `apm`.
:::

Install it with one command. The install script downloads one prebuilt binary for macOS or Linux (x64 or arm64, and musl systems such as Alpine on x64). Running it needs no git, Bun or Node.

<Tabs>
  <Tab title="Install script">
    ```bash
    curl -fsSL https://apmjs.dev/install | sh
    ```
  </Tab>
  <Tab title="Homebrew">
    On macOS or Linux with Homebrew:

    ```bash
    brew install opencoredev/tap/apm
    ```

    Keep the full tap path: plain `brew install apm` installs a different tool, Microsoft's apm from homebrew/core. Update with `brew upgrade opencoredev/tap/apm` and uninstall with `brew uninstall opencoredev/tap/apm`. Don't also run the install script: it puts a second apm in `~/.apm/bin`, which can shadow the Homebrew one on your PATH.
  </Tab>
</Tabs>

The rest of this section describes the install script.

The script installs to `~/.apm/bin/apm`, never uses sudo and does not edit your shell profile. It prints the line to add to your PATH instead:

```bash
export PATH="$HOME/.apm/bin:$PATH"
apm --version
```

`apm --version` prints `0.1.9`. To update, run the install command again. To uninstall, delete `~/.apm`.

### What the install script checks

When a version is released, the SHA-256 of each of its binaries is written into the script. The script downloads the binary for your machine from `https://apmjs.dev/cli/<version>/`, compares its SHA-256 with that list, and installs nothing if they differ. It also runs the binary once and installs it only if it reports that version. In a terminal it shows each step and the SHA-256 it checked. Piped or in CI, it prints the fingerprint it checked as two plain lines:

```
apm 0.1.9 (darwin-arm64) installed to /Users/you/.apm/bin/apm
SHA-256 <64-char hex digest>, checked against this script
```

To read the script before it runs, save it first:

```bash
curl -fsSL https://apmjs.dev/install -o install.sh
less install.sh
sh install.sh
```

### In scripts and agents

`curl | sh` suits a person who reads what it prints. A script or an agent that runs apm next must not carry on after a failed install with an apm left from before. Save the script to a temporary folder, run it only if it arrived whole, pin where it installs, and run apm only if the install succeeded:

```bash
APM_DIR="$(mktemp -d)" &&
  APM_SCRIPT="$APM_DIR/install.sh" &&
  curl -fsSL https://apmjs.dev/install -o "$APM_SCRIPT" &&
  tail -n 1 "$APM_SCRIPT" | grep -Fqx 'main "$@"' &&
  APM_OUT="$(APM_INSTALL="$HOME/.apm" sh "$APM_SCRIPT")" &&
  printf '%s\n' "$APM_OUT" &&
  printf '%s\n' "$APM_OUT" | grep -q '^SHA-256 [0-9a-f]\{64\}, checked against this script$' &&
  "$HOME/.apm/bin/apm" --version
```

The script's last line is the call that runs it, so an empty or cut-off download fails the `tail` check instead of exiting 0 with nothing installed, and apm runs only when the install printed the SHA-256 it checked. This is what the prompt on `https://apmjs.dev/publish` gives agents.

To check a binary by hand, compare its SHA-256 with the line for your platform in the script and in the version's published checksums:

```bash
curl -fsSL https://apmjs.dev/cli/0.1.9/SHA256SUMS
shasum -a 256 ~/.apm/bin/apm     # sha256sum on Linux
```

The script, the checksums and the binaries all come from apmjs.dev. The check proves the binary is the one released with the script you read; it does not prove who released it.

`--version X` or `APM_VERSION=X` installs another released version: `curl -fsSL https://apmjs.dev/install | sh -s -- --version 0.1.9`. `APM_INSTALL=<dir>` installs to `<dir>/bin/apm`. On Alpine, apm needs `libstdc++` and `libgcc` (`apk add libstdc++ libgcc`).

apm uses the package manager your project already uses: it reads the lockfile, then the `packageManager` field in `package.json`, then falls back to bun when bun is installed and npm when it is not. Pass `--pm npm` to choose.

## 3. Add a package

Run it in a folder with a `package.json` (`npm init -y` makes one). Like npm, apm uses the nearest `package.json`, so in a folder without one it changes the nearest parent project and says which. The one exception is a `package.json` in your home folder: from a folder below it, `apm add` and `apm remove` refuse and change nothing.

```bash
apm add zod
```

apm asks the registry for the newest version in the range or tag you ask for (`latest` for a bare name) that is not revoked, yanked, confirmed malicious or on the OSSF malicious-packages list, prints its score card, and checks every package under it. With bun, npm and pnpm, your package manager then computes the add's lockfile in a copy of your project, installing nothing, and apm checks every package in it at its exact version. Only a lockfile that passes is written to your project and installed, with install scripts held back until apm has confirmed the install matches it, so a revoked or yanked version anywhere in that lockfile refuses the add before anything in your project changes. One exception: npm can run a git dependency's `prepare` script while it computes the lockfile. Yarn runs install scripts while it installs. Yarn 2 and later compute the lockfile first, and apm checks it before the install and refuses one that fails. Yarn 1, or yarn 2 and later when yarn cannot produce that lockfile or apm cannot read it, installs first, and apm checks what installed afterwards. See [Lockfile first](/reference/cli#lockfile-first).

```text
✓ zod@4.6.7  score 100/100 (A)
  ✓ no risk signals found
  capabilities (what it can do; not scored)
    filesystem  loads fs to read or write files
        src/v4/core/tests/locales/parity.test.ts:1: import { readFileSync } from "node:fs"; (in a test file)
    eval        eval, Function, vm or a Worker from a string
        v4/core/compile.js:184: const factory = new F(...constantNames, factoryCode);
```

`apm add` asks your package manager for the exact version it checked, so with their default settings bun and pnpm write `"zod": "4.6.7"` to `package.json`, where `bun add zod` and `pnpm add zod` write a range (`"^4.6.7"`). npm writes a range either way.

A score informs; it does not block. If the package or one it brings in scores under 40, was not fully analysed, has no score, or could not be looked up, apm prints a warning with the score, the top reasons (file and line) and a link, then installs. Run `apm add --strict` (or set `APM_STRICT=1`) to refuse those instead.

If a package is refused, apm says why and whether `--force` would help. A package or dependency published in the last 24 hours installs with a warning. `--strict` refuses it instead; for the package you name, it skips fresh versions and may pick an older one that passes. `apm explain` looks for an older version in range past the cooldown and says whether to install it. `--force` lifts the cooldown for the named package only, and in strict mode its score floor. Revoked and yanked versions, and versions apm reviewers confirmed malicious, stay blocked.

`apm install` with no package names runs your package manager's own install and checks nothing. The checks happen in `apm add`, and `apm audit` checks what is already installed.
