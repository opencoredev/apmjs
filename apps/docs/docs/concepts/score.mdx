---
title: How the score works
description: What apm's 0 to 100 score reads, what costs points, how evidence is cited, and what the score cannot catch.
---

Every version on apm gets a number from 0 to 100. It starts at 100, and every point it loses is a named risk signal with the file and line that caused it. Below 40, the floor, `apm add`, the `~safe` view and the Bun scanner refuse the version.

The score counts what looks like malware, not what a package can do. Using the network, reading environment variables, touching files, starting processes, running dynamic code, shipping native code and having install scripts are listed beside the score as [capabilities](/concepts/capabilities), with their evidence, and cost nothing on their own (since `apm-score-v10`).

The score is a static read of the package's text. It catches most of what npm malware does today, because a dropper has to download, run a shell or read credentials somewhere in its files. It is weak against an author who knows the rules and writes code that only shows what it does at runtime. Read a high score as "nothing on this list was found", not as "safe".

## What goes in

The score is computed once per version, from three things:

- the tarball's files;
- its `package.json`, as it is inside the tarball;
- the publish history: who published earlier versions, and which dependencies are new.

Popularity and download counts are never inputs.

## What it reads, in order

1. **Install scripts.** `preinstall`, `install` and `postinstall` run on every install; `prepare`, `prepack` and `postpack` run when someone installs from git. Both run on the installing machine, so the files they run count as install time. apm follows each script the way the package managers do, into `npm run x`, `sh -c '...'`, base64 handed to `node -e`, and the files those commands name.
2. **`binding.gyp`**, and a `Makefile` or `CMakeLists.txt` when an install script builds with it.
3. **Entry points**: `bin`, `main`, `module`, `browser`, `exports` and `imports`, then every file they load by a path apm can work out.
4. **Every other file that could be code**, whatever its extension. A file called `lib/payload.dat` is read too.

Every file is read whole, as text, including comments, regular expressions and TypeScript types, because code can read that text back and run it. JavaScript and TypeScript are also parsed, and the parse can only add findings.

## Where values go

In JavaScript and TypeScript, apm follows values to the calls that use them. It knows where a value came from: the whole environment, a credential file's path or contents, a network response, or the program's own source. It follows that value through variables, aliases, callbacks, events (`emit` to a listener), generators and `for await`, string building, what a program puts into an array, object or `Map` (also through another name for it), and into other files of the package that import it. Each call of a helper function is worked out with that call's own arguments, so `id(process.env)` in one place and `id('public')` in another are told apart, and each property of an object keeps what was put there, so sending `tokens.npm` is not sending every token in `tokens`. The calls it watches are the ones that run code (`eval` under any name, `Function`, `vm`, a `Worker` from a string), start a process, send a request (including through `curl` or `wget` arguments) or read a file, and a file the program writes and then loads or runs.

That is what makes the heaviest signals sure:

- the environment, a credential file's contents or three kinds of tokens reaching a request is `exfiltration`, enough to refuse on its own;
- a download reaching an evaluator, reaching a process as the whole command (`exec(body)`), or written to a file that is then loaded or run, is `remote-shell`, also enough to refuse on its own; a download put into a longer command (`exec('echo ' + body)`) is a possible `remote-shell`, which refuses at install;
- a credential path reaching a file read is `credential-read`.

Code a file keeps as text is read as a program too: a string it runs, a comment or regex it turns back into code with `String(fn)` or `.source` and runs (padding is squeezed out first), or a string that holds a program. What that code does counts where the file holds it, so code an install script runs still counts as install time. A program a module only exports as text (example code a generator ships) adds its risks, but not a confirmed flow.

Small decoder functions a package defines (`h => h.replace(/../g, m => String.fromCharCode(parseInt(m, 16)))`) are run on the strings they are called with, so a name hidden behind one is read. A decoder runs only regexes apm can prove take linear time: no groups, alternation or open-ended repeats, and at most one optional character. A decoder that runs out of steps or output before it returns is code apm did not finish reading.

The analysis is bounded for any input by counted work, not by time. One work meter covers the whole of it, from inflating the tarball to the score: parsing, following values, constant strings, decoders, code held as text, the text rules. Every step whose cost grows with the input is charged before it runs, and every regex apm runs over package text takes linear time. A full meter is under 25 s of CPU, so an analysis always fits the registry's CPU limit. When the meter or a budget inside it runs out, or code that runs is longer than apm reads, the result says so (`incomplete`, naming what apm was doing, or `unanalyzed-files` for files nothing runs). It never reads as clean.

An anonymous request never analyses a package itself: a version nobody has scored yet is queued, and the page says so and checks again until the score is there. A signed-in or token request may have two small versions analysed on the spot. If the platform stops an analysis anyway, a scheduled sweep finds it and runs it again, reading less and marked incomplete.

Some versions can never be scored: a tarball over 32 MiB, or one that unpacks to more than 48 MiB, one the upstream lists with no checksum, one apm cannot read, or one whose analysis keeps running past the registry's CPU limit. The registry records why. The score page, `apm add`, `apm score` and the Bun scanner show that reason instead of "not scored yet". Installs through apm refuse the version, as they refuse any version with no score.

Images, fonts, archives and WebAssembly are recognised by their bytes and skipped. Executables and native `.node` modules are listed as `binary`. A file over 32 MB, or code past the 200 MB total, is not read and marks the analysis `incomplete`, which on its own puts the version below the floor.

## How text tricks are undone

Each file is read three times: as written; with split strings joined (`'chi' + 'ld_' + 'process'` becomes `'child_process'`) and `\x63`-style escapes decoded; and on strings decoded from base64, hex, character codes and URI escapes. A dangerous name that only shows up after joining or decoding also counts as `obfuscated`.

## Signals

| Signal | Points | Fires on |
| --- | ---: | --- |
| `revoked` | -100 | Pulled as malicious. |
| `incomplete` | -61 | Code that runs could not be read. |
| `remote-shell` | -61 | A command the code runs that opens a shell to another machine, or downloads a program and runs it (`/dev/tcp/`, `nc -e`, `curl … \| sh`), or a download apm follows into an evaluator or a process. -50 when an evaluator only sits next to a network call. |
| `capture-endpoint` | -50 | A request bin, out-of-band host, or chat webhook with its secret in the URL (`webhook.site`, Burp Collaborator, `pipedream.net`, a Discord webhook). |
| `install-download` | -40 | An install command that downloads (`curl`, `wget`), pipes into a shell, or runs `npx` for a package that is not a dependency. |
| `exfiltration` | -61 | The whole environment, a credential file's contents or tokens of three services that apm follows into a request. -35 when they only sit beside a network call; at install, also the machine's name or user. |
| `credential-read` | -30 | A credential file read: a path to `.npmrc`, SSH keys, cloud credentials, browser profiles or wallets that reaches a file read. |
| `risky-dependency` | -30 | A dependency whose resolved version scores below the floor. |
| `install-network` | -25 | Code that runs at install, or from `prepare`, `prepack` or `postpack`, uses the network. |
| `runs-decoded-code` | -25 | Code run from a string that was decoded or joined, a network call kept inside a string the code runs, or code the program hid in its own comments or regexes and runs. |
| `obfuscated` | -20 | Obfuscator output, escapes or base64 that decode to text, or a dangerous name hidden by joining or decoding. |
| `typosquat` | -20 | A name one edit from a popular package, or the same name with different separators or a `.js` suffix. |
| `unanalyzed-files` | -20 | Files nothing was seen loading were left out because the byte budget ran out. |
| `install-shell`, `install-eval` | -15 | Code that runs at install starts processes, or runs dynamic code. |
| `suspicious-combination` | -15 to -30 | Pairings malware has: dynamic code, network and an install script; obfuscated code that uses the network; a request bin in a file that starts processes. |
| `undeclared-capability` | -10 to -20 | A capability the code uses that the package's own [declaration](/concepts/capabilities) leaves out. |
| `install-script` | -10 | Has `preinstall`, `install`, `postinstall` or `binding.gyp`. |
| `git-install-script` | -10 | A git-install script (`prepare`, `prepack`, `postpack`) with shell, network, credential or eval content. |
| `new-publisher` | -10 | An account that never published this package before. |
| `yanked` | -10 | Hidden by its maintainer. |
| `new-dependency`, `deprecated` | -5 | Dependencies the previous version did not have; deprecated by its maintainer. |
| `credential-mention` | -3 | Text that names a credential file or token, with no read: a deny list, help text. -10 when the name sits next to a file read that apm did not see it reach. |
| `encoded-data` | -2 | Long base64 or escape runs that decode to data, such as WebAssembly. |
| `dynamic-require`, `recent`, `no-license` | 0 | Shown, not scored. |

Grades: A is 90 and up, B 75, C 60, D 40, F below 40.

## Confirmed and possible

Each code signal is **confirmed** or **possible**.

- **Confirmed**: apm saw the code do it, or a text rule matched it in a file apm read. Full points.
- **Possible**: only the parsed program suggests it, for example a loaded `inspector` module, and no text rule matched. About a third of the points, labelled "Possible ...".

A finding made only of text matches says so: a credential name in text is `credential-mention` (3 points), not `credential-read` (30), and a capability seen only as text says "Text mention only". Each evidence line also says where the match sits: "(text match in a comment)", "(text match in a regex)", "(text match in a TypeScript type)" or "(text match in a JSON file)".

## Evidence

Every signal cites the place it came from: `file:line` and the line itself. A joined string is cited where its first piece is, a decoded payload where the decoder is called. A file in a test folder says `(in a test file)`. On apmjs.dev every citation links to the file, opened at that line.

## What the score does not catch

Every score carries a shorter form of this list as "not checked". These are known, and left on purpose:

- **One named token sent the way a tool sends it.** `fetch(url, { headers: { authorization: process.env.NPM_TOKEN } })` is what every registry client does, and a stealer that sends one token looks the same. So does a CLI that reads `~/.npmrc` and sends the `_authToken` entry for a registry; the read costs points, the send does not. The whole environment, a credential file's whole contents, or three families of tokens in one request are caught.
- **Where data goes.** A request to an API and one to an attacker look the same, so code that only uses the network costs nothing outside install time. It is listed under [capabilities](/concepts/capabilities), and the [AI review](/concepts/ai-review) reads it.
- **Payloads in dependencies.** A package that hands `process.env` to a dependency, or only declares one, has no payload of its own. That dependency has its own score, which `risky-dependency` uses.
- **Typosquats with no visible payload.** A name like a popular package's costs points (`typosquat`), but a squat that ships a copy of the real code and nothing else passes.
- **Destructive code that does not steal or download.** Code that deletes files, wipes a disk or corrupts a build, with nothing sent or fetched, uses only capabilities, so it costs nothing outside install time.
- **WebAssembly and native code.** Their internals are never read; a module is listed, and a value a WebAssembly import receives is followed only on the JavaScript side.
- **Runtime behaviour.** Code that downloads, decrypts or assembles a second stage while running. A loader that runs what it fetched scores low, but the score cannot say what the second stage does.
- **Other encodings.** XOR, compression, a custom alphabet, base64 inside base64, unless a small decoder function in the package does it.
- **Names and values built some other way**: values read from a file at runtime, strings built by an obfuscator's lookup tables, an object filled in by a function it is passed to, and events a class emits on itself (`this.emit`).
- **A downloaded field in a command.** `exec('npm view pkg@' + json.version)` is a value in a command, not a command, so it costs nothing; the whole downloaded body in a command does.
- **Files only a computed path loads.** Docs, JSON and style files are read only when code reaches them by a path apm can work out. `require(name)` pointing elsewhere shows up as `dynamic-require`.
- **A popular name under another scope**, such as `@someone/react`. Scopes exist so names can be reused.
- **The publisher's machine or CI.** A compromised build that ships a quiet backdoor in clean-looking code scores well.

## Why it has false positives, and what fixes them

The score has no exclusions: every attempt to skip "harmless" text, such as comments, was beaten by a review that hid a payload there. So the score reads everything, and that has a price. On a hand-checked set of 70 popular packages, 28 of the 102 confirmed code signals are false, mostly words like `curl` in a comment or `sh` in a regular expression.

Precision comes from people instead of rules: an apm reviewer can [dismiss one evidence item](/guides/appeals-and-reports#appeal-a-score) for one version's exact tarball. The [AI release review](/concepts/ai-review) adds a second reading next to the score, never inside it.

The full rules, the review history and the test corpus are in [`docs/SCORE.md`](https://github.com/opencoredev/apmjs/blob/main/docs/SCORE.md).
