---
title: Capabilities
description: What a version can do (network, environment, files, processes, dynamic code, native code, install scripts), listed beside the score, and how a package declares them in package.json.
---

Since `apm-score-v10`, the [score](/concepts/score) counts what looks like malware, and what a package can do is listed beside it as **capabilities**. A capability costs no points on its own. An email SDK that calls its API, reads its key from the environment and has a sendmail transport is scored on its risks, not on those abilities.

## The capabilities

| Capability | What apm looks for |
| --- | --- |
| `network` | `fetch`, `http`/`https` requests, sockets, DNS, HTTP client libraries, `WebSocket` |
| `env` | `process.env.X`, `process.env['X']`, `const { X } = process.env`, `Bun.env`, `Deno.env.get`, reads by a computed name, reads through an alias (`const e = process.env`) or `globalThis.process.env`, and uses of the whole environment (`{ ...process.env }`, `JSON.stringify(Bun.env)`, `Deno.env.toObject()`) |
| `filesystem` | loading `fs`, `fs/promises`, `fs-extra` or `graceful-fs`, `Bun.file`, `Deno` file calls |
| `shell` | `child_process` and its calls, `Bun.spawn`, `Bun.$`, `Deno.Command`, shell text in commands |
| `eval` | `eval`, `Function`, `vm`, string timers, a `Worker` run from a string |
| `native` | executables, native `.node` modules, `binding.gyp` |
| `install` | `preinstall`, `install` and `postinstall` scripts |

Each one lists the lines that show it, linked to the file. When every line is only text, such as a variable name in help output or `curl` in a comment, the capability says "Text mention only". For `env`, the variable names it reads are listed too.

The version page shows capabilities in their own section, under the score. `apm score`, `apm add` and `apm publish` print them under the score, with what the declaration says for each and the variables read outside it.

## Declaring capabilities

A package can say what it does in its `package.json`:

```json
{
  "name": "@opencoredev/email-sdk",
  "apm": {
    "capabilities": {
      "network": ["api.resend.com", "*.amazonaws.com"],
      "env": ["AWS_*", "RESEND_API_KEY", "*_BASE_URL", "SMTP_*"],
      "filesystem": "reads attachment files",
      "shell": "sendmail transport"
    }
  }
}
```

The keys are `network`, `env`, `filesystem`, `shell`, `eval`, `native` and `install`. Each value is a reason (a string), `true`, or a list. `false`, `""` and `[]` declare nothing.

apm compares the declaration with the code:

| The code | The declaration | Result |
| --- | --- | --- |
| uses it | lists it | shown as **Declared** |
| uses it | leaves it out | **Not in its declaration**: the `undeclared-capability` risk signal, 10 points for the first, 5 for each further one, at most 20 |
| uses it only as text | leaves it out | shown, costs nothing |
| never uses it | lists it | a note: "Declared, not seen used" |

For `env`, the list is variable names, where `*` stands for any run of characters. Variables the code reads outside the list are shown under the capability; they are not scored. Network hosts are shown as declared and not checked against the URLs in the code, because most URLs in code are documentation links.

A declaration never cancels a risk signal. An install-time download, a credential file read, a request bin, or the environment sent in a request costs the same whether or not the package declares the network and `env`.

A package without a declaration, which is most of npm, is scored on risk signals alone. An `apm` field without `capabilities`, or one apm cannot read, counts as no declaration, so a typo cannot cost points; the version page says when apm could not read it.

## Example

`@opencoredev/email-sdk` 3.0.1 scores 97 without a declaration: 3 points for the variable names in its CLI help, a weak `credential-mention`. With the declaration above it still scores 97, with every capability marked declared. With a declaration that lists only `network`, `env` (`AWS_*`, `RESEND_API_KEY`) and `shell`, it scores 87: its CLI imports `node:fs/promises`, so `filesystem` is undeclared.
