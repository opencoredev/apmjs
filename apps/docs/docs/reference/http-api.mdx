The registry at `https://registry.apmjs.dev/` speaks the npm registry protocol, so stock clients work unchanged, and adds its own API under `/-/apm/v1/`. This page lists every public route. Routes used only by the website (sign-in, approvals, second factors) and by the AI reviewer are listed at the end without detail.

## Conventions

- **Auth.** Send `Authorization: Bearer <token>` with the token from `apm login`. Routes marked "token" need one; the rest are public.
- **Second factor.** Routes marked "factor" also need `otp` (a six-digit authenticator code) in the JSON body, or a website approval of that exact command made in the last 10 minutes.
- **Errors.** A `GET` or `HEAD` of a path the registry has no read route for answers `404` before anything else runs. A trailing slash, `%40` for `@` and `%2f` inside a scoped name name the same route. A failure answers JSON with an `error` message and the matching status: `400` bad input, `401` no token, `403` not allowed, `404` not found, `405` wrong method, `409` conflict, `410` revoked or expired, `413` too large, `422` refused by a check, `429` over a quota, `503` an upstream check could not run.
- **Per-user answers** (account, staged uploads, tokens, login, and any `/-/` answer to a request carrying credentials) are sent with `Cache-Control: private, no-store` and `Vary: Authorization, Cookie`.
- **Source-bearing answers** (`/-/apm/v1/file/`, `/-/apm/v1/readme/`, `/-/apm/v1/score/`, `/-/apm/v1/packages/`, `/-/apm/v1/resolve` and `/-/apm/v1/review/`) are sent with `Cache-Control: private, no-store`: whether a version's source may be shown is decided on every request.
- **Timing.** `GET` and `HEAD` answers under `/-/apm/v1/packages/`, `score/`, `review/`, `readme/` and `file/` carry a `Server-Timing` header only for the registry's operator, who sends the deploy's debug token as `x-apm-debug`. It gives the database's time (`db`), npm's packument fetched (`npm`) or read from the data center's cache (`npm-cache`), a version scored on read (`analysis`) and the whole answer's (`total`), each with its count. Anyone else gets no `Server-Timing`, because timing alone shows whether npm's answer was cached.
- **Package names** in paths are URL-encoded the npm way: `@scope%2fname`.
- **Size limits.** Publish bodies 32 MB, JSON API bodies 5 MB, a tarball's `package.json` 1 MB.

## The `~safe` view

Prefix any path with `/~safe` to read through the safe view: `https://registry.apmjs.dev/~safe/<package>`. Package documents, versions and tarballs then leave out versions that are revoked, pending revocation, yanked, younger than 24 hours, unscored, or scoring under 40, and `latest` points at the newest version that passes. A hidden version answers `404` with the reason (for a withheld version, only "revoked by its owner" or "revocation pending"). See [The ~safe view](/guides/safe-view).

## npm protocol routes

| Method and path | Auth | Answers |
| --- | --- | --- |
| `GET /-/ping` | none | `{}` |
| `GET /<package>` | none | The package document (packument). Supports the abbreviated form (`Accept: application/vnd.npm.install-v1+json`) and `ETag`. Each version carries apm's score as `_apmScore`. |
| `GET /<package>/<version or tag>` | none | One version's document. Revoked versions answer `404`. |
| `GET /<package>/-/<file>.tgz` | none | The tarball, checked against its published sha512 before it is sent. An npm tarball over 32 MiB is streamed instead and checked as it passes: one that fails ends before its last bytes, and the client's own integrity check refuses it. A revoked version answers `410` with `{ error, revoked: true, revokeReason }`; `error` is the line npm prints, so it ends with the owner's reason too. |
| `PUT /<package>` | token | Publish one version. With a login token it is staged and answers `202` with `approvalUrl`, `expiresAt` and an `npm-notice` header holding the link. `npm deprecate` uses this route too; with a login token it needs a code in `npm-otp`. |
| `GET /-/package/<package>/dist-tags` | none | The dist-tags. |
| `PUT /-/package/<package>/dist-tags/<tag>` | token, factor | Move a tag. A login token needs a code (npm sends it as `npm-otp`). |
| `DELETE /-/package/<package>/dist-tags/<tag>` | token, factor | Remove a tag. |
| `PUT /<package>/-rev/<rev>` | token, factor | `npm owner add` and `npm owner rm`. Needs a code in `npm-otp`. |
| `DELETE /<package>/-rev/<rev>` | | Always `405`. apm does not unpublish; use yank or revoke. |
| `GET /-/v1/search?text=&size=&from=` | none | Search across apm and npm. `size` at most 250. |
| `POST /-/npm/v1/security/advisories/bulk` | none | Advisories for `bun audit` and `npm audit`. Revoked versions are critical advisories. |
| `GET /-/whoami` | token | `{ "username": "..." }` |
| `DELETE /-/user/token/<token>` | token | Revoke the token that made the request. |
| `PUT /-/user/org.couchdb.user:<name>` | none | npm password login. Only on self-hosted registries with `APM_LEGACY_AUTH=1`. |

Packages that are not on apm are fetched from `https://registry.npmjs.org/`, checked against npm's checksum, and scored on first request. When npm cannot be reached, or sends a packument apm refuses to read (below), `GET /<package>` answers `503` with `Retry-After: 30`, so npm reports a registry error and tries again instead of saying the package does not exist.

### What apm's packuments leave out

For a package that is only on npm, apm reads npm's packument as a stream and keeps only what it serves, so a 39 MB packument (vite's) costs a few MB. Compared with npm's own packument:

- No version has `licenseText`, `readme` or `readmeFilename`. npm repeats this text in every version (vite's `licenseText` is 35 MB of its 39 MB packument), and no install reads it. Each version's `license` field is kept, so `npm view <package> license` works, and so is the package's top-level `readme`.
- The abbreviated packument (`Accept: application/vnd.npm.install-v1+json`, which npm, pnpm, yarn and bun install from) has no `devDependencies`. npm's has them, but no package manager installs a dependency's devDependencies.
- The full packument (`Accept: application/json`, which `npm view` and yarn 1 read) has each version's `devDependencies`, read separately from the rest. If that read fails or goes over the limits below, the answer leaves them out.
- At the top level it has `_id`, `name`, `description`, `dist-tags`, `versions`, `time`, `readme` and `maintainers`. npm's `_rev`, `users`, `keywords`, `repository`, `homepage`, `bugs`, `author`, `license` and `readmeFilename` at the top level are left out; each version keeps its own. `time` has one entry per version served, and no `created` or `modified`.
- Each version also has `_apmScore`, which npm's does not.

apm refuses an npm packument larger than 160 MB, one that would keep more than 24 MB or 1.5 million values, or one nested more than 100,000 levels deep. It refuses invalid JSON too, even in fields it does not keep. A refused packument answers `503`, like an unreachable npm. No real package comes near these limits: next keeps 15 MB and 0.8 million values.

## apm API

### `GET /-/apm/v1/resolve`

What `apm add` installs. Query: `name`, `range` (default `latest`), `cooldown` (`24h`, `90m`, `2d`, `0`; a bare number is hours; default 24h), `floor` (default `40`), `strict` (`1` for strict mode), `os` and `cpu` (the install's platform as node names it, such as `linux` and `x64`; default `any`), `installed` (the names the project's `package.json` already lists, comma-separated, at most 500). A lower floor applies to the named package only; its dependencies are checked at 40 or the stricter floor.

A score informs; it does not block. By default the answer picks the newest version that is not revoked, yanked or confirmed malicious by an apm reviewer (however many of those are newer), and a version inside the cooldown (the package or a dependency: npm and bun install it from the plain registry whatever its age, so it is the version checked), a score under the floor, an incomplete analysis, a version apm cannot score, one still pending after the wait, a dependency the registry could not look up, a dependency it could not check (a git, URL or file spec, a missing package, a peer it cannot pick a version for: one `unchecked` warning each) and a walk cut short at its limits are each a warning on a `200`. With `strict=1` each of them refuses, as below; for the package itself, a version inside the cooldown or under the floor is skipped for the newest older one that passes. The walk follows `dependencies`, `optionalDependencies` and each required peer (one `peerDependenciesMeta` does not mark optional). A peer counts as met only by the peer's own package installed under the peer's name, beside its parent or an ancestor or as an ancestor itself, at a version in range; a package installed under an alias (`alias: npm:foo@1.0.0`) never meets a peer `foo`. An optional dependency built for another platform than `os` and `cpu` is skipped with what it depends on. The walk has no project state: it cannot see the versions the project's own `package.json` or lockfile already pins, so a peer the project meets is still walked at the version its range picks, and `tree.projectPeers` names those whose names `installed` lists.

- `200`: `{ name, version, report, skipped, source, tree, warnings, policy }`. `tree.packages` lists every package the registry walked; `tree.uncheckedDeps` lists those it could not check (git and URL specs, missing packages, past the 300-package walk limit, a peer it cannot pick a version for); `tree.skippedForPlatform` lists the optional packages built for another platform (`{ dependency, version, reason, via }`, at most 50; `tree.platformSkips` counts them all), which are not unchecked; `tree.projectPeers` lists the required peers nothing in the tree installs whose names `installed` lists (`{ dependency, via }`, at most 50); `tree.pending`, `tree.unscorable` and `tree.unavailable` list the versions still being analysed, the ones apm can never score, and the dependencies whose metadata could not be fetched. `warnings` holds one `{ name, version, kind, score, grade, text, reasons, url, via }` per flagged package: `kind` is `cooldown`, `low-score`, `incomplete`, `unscorable`, `pending`, `unavailable` or `unchecked`; `reasons` are up to three, each with its file and line; `url` is the version's page; `via` is the path from the package asked for. `policy.strict` says which mode answered, and `policy.os` and `policy.cpu` the platform.
- `202` (strict only): the version, or a version in its tree, is queued for analysis and has no score yet. The registry waited up to about 20 s for it first. `{ error, name, range, version, pending: [{ name, version, via }], pendingCount, retryAfter, skipped }`, with a `Retry-After` header. Ask again later; nothing in it is a pass. The default mode answers a `200` with a `pending` warning instead.
- `503`: the package itself could not be looked up (both modes), or, in strict mode, a dependency's metadata could not be fetched: `{ error, unavailable: [{ dependency, via }], retryAfter }`, with a `Retry-After` header. A retry may succeed.
- `422`: nothing installs. `{ error, name, version: null, skipped, newest, tree }`, where `skipped` gives each version's `reason` (revoked, revocation pending, yanked, confirmed malicious by an apm reviewer; in strict mode also the cooldown, the score floor and a missing score; at most 20 are listed, and strict mode looks at no more than the newest 200 candidates), and for a revoked or revoke-pending version the owner's words in `revokeReason`. A dependency confirmed malicious (then also `confirmed: [{ name, version }]`) refuses in both modes; in strict mode so does anything that would be a warning, a dependency inside its cooldown included, listed in `tree.blocks`. When `newest` is revoked or pending revocation, its `report` is the score answer's withheld form (`redacted: true`, no evidence lines, each skipped file named `file <n>`).
- `404`: no such package.

### `GET /-/apm/v1/score/<package>[/<version or tag>]`

One version's score. Without a version, `latest`.

```json
{
  "name": "zod", "version": "4.6.7", "status": "active",
  "score": 90, "grade": "A",
  "signals": [{ "id": "eval", "label": "Evaluates code built at runtime (eval, Function, vm)", "points": -10, "confidence": "confirmed", "evidence": ["v4/core/compile.js:184: const factory = new F(...constantNames, factoryCode);"] }],
  "notChecked": ["runtime behavior: code that downloads, decrypts or builds a second stage while running"],
  "publishedAt": "2026-10-12T16:29:37.778Z", "publishedBy": "GitHub Actions",
  "previous": { "version": "4.6.6", "score": 90, "grade": "A" },
  "changes": []
}
```

### `GET /-/apm/v1/names?q=<name>`

Name check, as `apm name` shows it: `{ query, valid, taken, available, owners, latest, conflicts, similar, suggestions }`. Optional `user` says whose scope to check against; it defaults to the caller.

### `POST /-/apm/v1/scan`

The Bun scanner's check. Body: `{ "packages": [{ "name": "zod", "version": "4.6.7" }], "strict": false }`. Every package is checked whatever platform it is built for: the scanner is handed exactly what the package manager installs, so nothing is skipped (an `os` or `cpu` an older scanner sends is ignored). At most 200 packages without a token, 2,000 with one; the rest come back as unchecked.

- `200`: `{ advisories: [{ package, version, level, description, url }], warnings, unchecked: [{ package, version, reason }], pending: [{ package, version }], unscorable: [{ package, version, reason }], unavailable: [{ package, version }], strict, retryAfter? }`. A revoked version (or one pending revocation), or one an apm reviewer confirmed malicious, comes back with `level: "fatal"` in both modes, which makes Bun cancel the install. A version published inside the 24-hour cooldown, one scoring under 40 or with an incomplete analysis, one the registry decided it can never score (too large, unavailable, unreadable, past the analysis limits), and a package the registry could not look up ("could not be checked: registry or upstream unavailable") come back with `level: "warn"`, or `fatal` with `"strict": true`, and their warning in `warnings` (the same shape as resolve's). A version queued for analysis is listed in `pending`, and in `unchecked` too so older scanners never read it as clean.

### `POST /-/apm/v1/audit`

Body: `{ "<package>": ["<version>", ...] }`. Answers `{ advisories, unavailable }`: npm-style advisories per package, and the packages whose upstream advisories could not be fetched.

### `GET /-/apm/v1/packages/<package>`

The package as the website shows it: versions with status, scores and dist-tags. `HEAD /-/apm/v1/packages/<package>` answers only whether the package exists, here or on npm (`200`, `404`, or `503` when npm could not be asked), without building the answer. `GET /-/apm/v1/packages/<package>/events` is its public log: publishes, yanks, revokes, restores, owner changes and evidence dismissals, with who and why. An event about a revoked or revoke-pending version keeps its kind, actor, time, version and the reason given for the action, and drops the publisher's text (a deprecation message, a dist-tag name, a file path), with `detail.withheld: true`.

### `GET /-/apm/v1/recent?limit=<n>`

Recent events across the registry, newest first. `limit` 1 to 50, default 12.

### `GET /-/apm/v1/file/<package>/<version>?path=<path>`

One file of a version, as text, from the same verified tarball the install routes serve. Up to 1 MB whole. Add `&line=<n>&context=<k>` (k at most 100) for lines n-k to n+k of a file of any size. A file that is not UTF-8 answers its size and no text; a line past the end answers `416`; a revoked or revoke-pending version answers `410` with `{ error, revoked: true, revokeReason }`.

### `GET /-/apm/v1/readme/<package>/<version>`

The README in the version's tarball, picked the way npm picks one.

### `GET /-/apm/v1/review/<package>/<version or tag>`

The AI review result for a version, when the registry runs the review. A dist-tag such as `latest` answers for the version it points to, named in the answer's `version`. `POST .../request` asks for one (signed-in users, 5 an hour).

### Version state

All take a JSON body and a token, and need the caller to own the package.

| Method and path | Body | Factor |
| --- | --- | --- |
| `POST /-/apm/v1/yank` | `{ name, version, reason? , otp? }` | A login token needs `otp`. |
| `POST /-/apm/v1/unyank` | `{ name, version, otp? }` | A login token needs `otp`. |
| `POST /-/apm/v1/revoke` | `{ name, version, reason, otp }` | Required. |
| `POST /-/apm/v1/restore` | `{ name, version, reason?, otp }` | Required. |
| `POST /-/apm/v1/incident` | `{ since, reason?, dryRun?, otp }` | Required. `since` is ISO, at most 30 days back. |
| `POST /-/apm/v1/owners` | `{ name, user, otp }` | Required. Adds an owner. |
| `DELETE /-/apm/v1/owners` | `{ name, user, otp }` | Required. Removes an owner. |

Revoke answers `{ ok, name, version, status, finalAt?, note? }`; `status` is `revoked`, or `revoke-pending` with `finalAt` 24 hours later. Incident answers `{ ok, revoked, tokensRevoked, dryRun? }`.

## Routes for the website and the reviewer

These exist for apmjs.dev and the AI reviewer process. They need a website session with the website's `Origin`, or the reviewer's service token, and are not a stable API:

- sign-in: `/api/auth/*`, `GET /-/apm/v1/auth/config`, `POST /-/apm/v1/login/device` and `/login/device/token` (the device flow `apm login` uses);
- account: `GET /-/apm/v1/account`, `POST /-/apm/v1/account/tokens/revoke`;
- second factors: `POST /-/apm/v1/factor/passkey-challenge`, `POST /-/apm/v1/factor/confirm`, `POST /-/apm/v1/verify`;
- staged uploads: `GET /-/apm/v1/staged`, `GET /-/apm/v1/staged/<id>`, `GET .../file`, `POST .../approve`, `POST .../reject`;
- evidence review: `/-/apm/v1/evidence-admin/*`;
- AI review queue: `/-/apm/v1/review-jobs*`, `/-/apm/v1/review-admin/*`.
