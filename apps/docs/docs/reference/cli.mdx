`apm` 0.1.0 checks before you install, run or publish, then hands the work to the package manager your project uses. Any command it does not know goes straight to that package manager: `apm run dev` is `bun run dev` in a bun project.

To install it, see [Quick start](/quickstart#2-get-the-apm-cli).

## Global flags

| Flag | Meaning |
| --- | --- |
| `--pm bun\|npm\|pnpm\|yarn` | The package manager to run. Default: found from the lockfile, then `packageManager` in `package.json`, then bun if it is installed, else npm. |
| `--json` | Print exactly one JSON document on stdout. Human output goes to stderr. Applies to `add`, `install`, `score`, `name`, `audit`, `yank`, `unyank`, `revoke`, `restore`, `incident`, `publish`, `login` and `whoami`. |
| `--otp <code>` | A six-digit code from your authenticator app, for commands that need a fresh second factor. |
| `--help`, `-h` | Print the command list. |
| `--version`, `-v` | Print the version. |

Exit codes: `0` success, `1` refused or failed, `2` wrong usage. A passed-through command exits with the package manager's code.

## apm add

```bash
apm add <package>[@range]... [--strict] [--force] [--no-cooldown] [--cooldown <duration>] [--floor <n>] [-D]
```

Resolves each package to the newest version that is not revoked, yanked or confirmed malicious and checks its whole dependency tree, including every platform's optional binaries (see [Platform](#platform)). Then your package manager computes the add's lockfile in a copy of your project, installing nothing, and apm checks every package of that lockfile (see [Lockfile first](#lockfile-first)). Only a lockfile that passes is written to your project and installed, with install scripts held back until apm confirms the install matches it. `apm install <package>` and `apm i <package>` are the same command. With no packages, it runs your package manager's own install.

A score informs; it does not block. When the package or a dependency was published inside the 24-hour cooldown ("published 5 hours ago, inside apm's 24-hour cooldown"), scores under 40, has an incomplete analysis, can never be scored, is still being analysed after the wait, or could not be looked up because the registry or npm did not answer, `apm add` prints a warning block for each, then installs:

```text
WARNING left-pad@1.3.0 scores 30/100 (F), under the floor of 40
  - Sends what it collected: index.js:12: fetch(…) (sends the whole environment in a request)
  - Starts processes at install time: package.json scripts.postinstall: node setup.js
  https://apmjs.dev/package/left-pad/v/1.3.0
apm installs it anyway: a score or a fresh publish informs, it does not block. To refuse these instead, run with --strict (or APM_STRICT=1).
```

A version nobody has scored yet, the package or one of its dependencies, is queued for analysis. The registry waits up to about 20 s for the score, and the warning then says what it found; a cold package usually has its score after a few seconds. What is still pending then installs with a `not scored yet` warning.

With `--strict` (or `APM_STRICT=1`), each of those refuses instead, as apm did before: a version inside the cooldown (for the package itself, the newest older version is used instead), a score under the floor, an incomplete analysis, a version apm cannot score (`apm cannot score this version: …`), a dependency the registry could not look up, and a version still pending after `apm add` has kept asking for 90 s (`still being analysed, try again in a minute`). Revoked and yanked versions and versions an apm reviewer confirmed malicious are refused in every mode.

| Flag | Meaning |
| --- | --- |
| `--cooldown <duration>` | Warn about (with `--strict`, skip or refuse) versions younger than this, in the package and its tree. `24h` (default), `90m`, `2d`, `0`. A bare number is hours. |
| `--no-cooldown` | Same as `--cooldown 0`. |
| `--strict` | Refuse instead of warning: a version inside the cooldown, a score under the floor, an incomplete analysis, no score yet or ever, a dependency the registry could not look up, any dependency it could not check (a git, URL or file spec, a missing package, a peer it cannot pick a version for), and a dependency walk cut short at its limits. `APM_STRICT=1` does the same, and `apm explain` honours both. |
| `--floor <n>` | Warn about (with `--strict`, refuse) versions scoring below `n`. Default `40`. Dependencies are always checked at 40 or the stricter floor you ask for. |
| `--force` | Lift the cooldown and the score floor of the exact versions you name, and nothing else: every other package in the lockfile keeps the cooldown and the floor you asked for (a stricter `--floor` included). Revoked and yanked versions, versions apm reviewers confirmed malicious and unknown names stay blocked, and so, in strict mode, do versions apm has not scored or cannot score. |
| `-D`, `--dev` | Add as a dev dependency. |

### Lockfile first

The registry's first answer is a prediction: the package manager can reuse a version your lockfile already pins, meet a peer with a version below the top level, follow your `overrides`, `pnpm.overrides` or `resolutions`, or take the version your `package.json` pins. So `apm add` has the package manager answer instead, before anything is installed:

1. It copies your `package.json`, the lockfile (`npm-shrinkwrap.json` before `package-lock.json`, as npm reads them), `.npmrc`, `pnpm-workspace.yaml`, `.pnpmfile.cjs`, `bunfig.toml`, `.yarnrc.yml` and, in a workspace, each member's `package.json`, into a new temporary directory, and nothing else.
2. There the package manager computes the add's lockfile with every script off: `npm install --package-lock-only`, `pnpm add --lockfile-only` or `bun add --lockfile-only`.
3. apm asks the registry about every package of that lockfile at its exact version and integrity, 200 at a time, with nothing left out:

```text
apm: checked the 3 packages in the package-lock.json npm computed for this add, at the exact versions and integrity it locks, before installing anything
  leaf: the early check read 1.1.0, the lockfile holds 1.0.0; that is the version checked here

WARNING leaf@1.0.0 published 1 hour ago, inside apm's 24-hour cooldown
```

A revoked or yanked version, one apm reviewers confirmed malicious, or one whose integrity is not what the registry serves refuses the add in every mode; `--strict` refuses every warning too. An integrity the registry cannot compare (a hash algorithm it does not know) is a warning, never a match. A git, file, link or remote-tarball entry cannot be checked by a registry: it is a warning, which `--strict` refuses. Your workspace's own members are trusted as your source, and not asked about, when the lockfile names them by their folder, name and version; their dependencies are checked like any other. A bundled dependency ships inside its parent's tarball, so the parent's score covers its code; apm still refuses it if that version was revoked, yanked or confirmed malicious. Warnings already printed by the first answer are not printed twice.

A refused add exits 1 and names what it refused. Your project was never touched: `package.json`, the lockfile and `node_modules` are byte for byte as they were.

When the check passes, apm writes the checked `package.json` and lockfile over yours (those two files only, and only if nothing it copied changed while it checked), installs exactly that lockfile with scripts held back (`npm ci --ignore-scripts`, or `npm install --ignore-scripts` when there is a `node_modules` to keep; `pnpm install --frozen-lockfile --ignore-scripts`; `bun install --frozen-lockfile --ignore-scripts`), and confirms that what installed is that lockfile: every dependency resolves, the way Node loads it, to the version the lockfile locks; every required package is there; and nothing else is in `node_modules`. A package left there from before, outside the lockfile, or a package directory apm cannot read, is a warning, which `--strict` refuses. Then apm runs the install scripts of the packages this install put in place, at those locations only (`npm rebuild <directory>`, `pnpm rebuild <name@version>`; bun installs them again). apm does not run your project's own `postinstall` or `prepare` scripts under npm and pnpm, and says so.

If what installed is not the checked lockfile, no script runs and apm leaves the files as installed: it never undoes an install. It prints the commands that put your `package.json` and lockfile back (it keeps a copy of both until the add finishes), and the `git checkout` alternative, also when the package manager fails to start or a file operation fails after apm wrote the checked files.

With yarn, which runs install scripts while it installs, `--strict` refuses before anything runs: "apm cannot check yarn installs before yarn runs their scripts." Without it, apm warns first. Yarn 2 and later compute the lockfile in a copy (`yarn add --mode update-lockfile`), which apm checks before yarn installs it with `yarn install --immutable`, then confirms yarn installed nothing else; yarn 1 has no such mode, so apm checks `node_modules` after yarn installed it and ran its scripts, and says so.

With `--json`:

```json
{ "ok": true, "pm": "bun", "error": null, "packages": [{ "name": "zod", "version": "4.6.7", "score": 90, "grade": "A", "signals": [{ "id": "eval", "points": -10 }], "skipped": [], "unchecked": [], "warnings": [], "blocked": false, "reason": null, "forceable": false }], "installed": { "source": "lockfile", "checked": 1, "blocked": [], "warnings": [], "refused": false, "touched": true, "stage": "done", "recovery": null } }
```

`installed` is the check of the computed lockfile (null when apm stopped before it): `checked` counts its packages, `blocked` lists `{ name, version, reason }` refused in every mode, `warnings` its warnings, `touched` whether apm wrote to your project (never before the check passes), `stage` where the add stopped (`check`, `install`, `verify`, `scripts` or `done`), and `recovery` the commands that put the project back when it stopped after apm wrote the checked files. `source` is `node_modules` only under yarn 1.

Each entry in `warnings` is `{ name, version, kind, score, grade, text, reasons, url, via }`: `kind` is `cooldown`, `low-score`, `incomplete`, `unscorable`, `pending`, `unavailable` (the registry or npm did not answer) or `unchecked` (a dependency apm could not check, or the walk stopped at its limits); `score` and `grade` are set for `low-score` and `incomplete`; `reasons` holds up to three, each with its file and line; `via` is the dependency path, empty for the package itself. `projectPeers` lists the peers your project provides (see [Peers your project already has](#peers-your-project-already-has)) as `{ dependency, via, kind, version }`.

### Platform

`apm add`, `apm x`, `apm explain` and `apm audit` check every platform. They send the registry no `os` or `cpu`, so it checks every optional package, whichever platform it is built for. A force flag, an `os`/`cpu` setting, pnpm's `supportedArchitectures` or a `.pnpmfile.cjs` hook can make a package manager install a binary for another platform, and apm does not try to predict which: a package manager can install nothing apm did not check.

The cost is more packages to check: `apm add next` checks the `@next/swc-*` and `@img/sharp-*` binaries for every platform, about 27 more packages than one platform needs. The printed warnings group them by family, one line each:

```text
WARNING 8 platform binaries (@next/swc-*): 8 too large to analyze
19 platform binaries (@img/sharp-*): no warnings
```

`--json` lists each warning.

### Peers your project already has

The registry walks each required peer at the version its range picks, unless something in the tree installs the peer's own package under the peer's name at a version in range (a package installed under an alias does not count). A peer nothing in the tree installs but your `package.json` lists (`dependencies`, `devDependencies`, `optionalDependencies`, `peerDependencies`) is your project's, and the package manager uses your version. `apm add` reads which one from your lockfile (`package-lock.json`, `pnpm-lock.yaml` or `bun.lock`) and sends each name with the version the lockfile pins:

- Pinned: the registry checks that exact version, under the usual policy (a warning by default, refused with `--strict`). A pinned version that was revoked or yanked is refused in every mode.
- No lockfile, or no entry for that name: the registry checks the newest version in range and `apm add` prints a note saying so. Your `package.json` may pin an older one; the check of the computed lockfile reads the version the package manager really picked.
- A lockfile apm cannot read (`yarn.lock`), or an entry it cannot pin to a registry version (an alias, a git, file or workspace entry): the peer is reported as not checked, a warning that `--strict` refuses.

## apm x

```bash
apm x <package>[@version] [args...]
```

Shows the package's score card, then in a temporary project of its own has your package manager (npm for yarn projects) compute the lockfile, checks every package of it as `apm add` does, and only then installs it with install scripts held back, confirms the install matches it, runs the install scripts and runs the package's binary (the only one, or the one named like the package) in your directory. The binary runs with the temporary project's `node_modules/.bin` first on `PATH`, so a helper binary it calls is one apm checked. The directory is removed afterwards. Aliases: `apm exec`, `apm dlx`. Takes the same `--strict`, `--force`, `--no-cooldown`, `--cooldown` and `--floor` flags as `add`, warns the same way, and waits for a version still being analysed the same way. Put apm's own flags before the package: what follows the package goes to its binary.

## apm score

```bash
apm score <package>[@version] [--json]
```

Prints a version's score: every signal with its points and evidence, the publisher, the previous version's score, and the list of what was not checked. Without a version, it scores `latest`.

## apm name

```bash
apm name <name> [--json]
```

Says whether a name is free, taken, or free but refused (with the reason), plus similar names and available alternatives. When you are logged in it also says whether you already own it. See [Names and scopes](/guides/names).

## apm audit

```bash
apm audit [--json]
```

Checks every installed version with the same check `apm add` runs after an install, plus the upstream advisories, whatever platform each is built for: nothing installed is skipped. A revoked, yanked or confirmed malicious version is a `critical` finding, a fresh, low-scoring or unscorable one a `warning`. Exits `1` on any finding and also when anything could not be checked.

```json
{ "ok": false, "checked": 412, "findings": [{ "id": "some-package@1.0.3", "severity": "critical", "text": "..." }], "unchecked": [] }
```

## apm publish

```bash
apm publish [--bump patch|minor|major|<version>] [--dry-run] [--tag <tag>]
```

Checks, packs with your package manager, previews the score, then uploads. With a login token the version is staged and the command prints the approval link. See [Publish a package](/guides/publishing).

| Flag | Meaning |
| --- | --- |
| `--bump` | `patch`, `minor`, `major` or an exact version. Writes the new version to `package.json` (not with `--dry-run`). |
| `--dry-run` | Run every check and print the preview. Upload nothing. |
| `--tag <tag>` | The dist-tag. Default: `latest`, or `next` for a prerelease. |

`--json` prints `status` as `dry-run`, `staged` (with `approval`, the link) or `published`, plus `name`, `version`, `registry`, `files`, `score` and `grade`.

## apm yank, apm unyank

```bash
apm yank <package>@<version> [--reason "..."] [--otp <code>]
apm unyank <package>@<version> [--otp <code>]
```

Hide a version from new installs, or show it again. Lockfiles that pin it keep working. A login token needs `--otp`.

## apm revoke

```bash
apm revoke <package>@<version> --reason "..." [--otp <code>]
```

Pulls a malicious version. `--reason` is required. Needs a fresh second factor: `--otp`, a code typed at the prompt, or a website approval of this exact command within the last 10 minutes. A version under 72 hours old is revoked at once; an older one is `revoke-pending` for 24 hours unless a second owner runs the same command. See [Yank, revoke and incident response](/guides/pull-a-version).

## apm restore

```bash
apm restore <package>@<version> [--reason "..."] [--otp <code>]
```

Undoes a mistaken revoke. The version goes back to `yanked`. Needs a fresh second factor.

## apm incident

```bash
apm incident --since <ISO time> [--reason "..."] [--dry-run] [--otp <code>]
```

Revokes every version you published since `--since` (at most 30 days back) and every token on your account. `--dry-run` lists what it would do and changes nothing. `--reason` defaults to `account compromised`. Needs a fresh second factor.

## apm login

```bash
apm login [--no-browser]
apm login --username <name> --password-stdin [--email <address>]
```

The first form signs you in through the browser with a device code and saves a staging token to your user `.npmrc`. `--no-browser` only prints the link. The second form is npm's password login, for self-hosted registries that run with `APM_LEGACY_AUTH=1`.

## apm whoami

```bash
apm whoami [--json]
```

Prints the user the current token belongs to, and the registry.

## Environment

| Variable | Meaning |
| --- | --- |
| `APM_REGISTRY` | The registry to use. Wins over every config file. |
| `APM_TOKEN` | A token to use instead of the one in `.npmrc`. Sent only to the registry it was issued for: `APM_REGISTRY`, else `registry=` in your user `.npmrc`, else the default. |
| `npm_config_registry` | Used when `APM_REGISTRY` is not set. |
| `npm_config_userconfig` | Path of the user `.npmrc`. Default `~/.npmrc`. |
| `NO_COLOR` | Turn off colors. |
| `APM_PENDING_WAIT_MS` | How long `apm add --strict` and `apm x --strict` keep asking about versions still being analysed. Default `90000`. |
| `APM_STRICT` | `1` makes `apm add`, `apm x` and `apm explain` strict, as `--strict` does. |

Without `APM_REGISTRY` or `npm_config_registry`, apm reads `registry=` from the nearest project `.npmrc`, then your user `.npmrc`, then uses `https://registry.apmjs.dev/`. The token is the `_authToken` line for that exact registry host; a `${VAR}` value is read from the environment.
