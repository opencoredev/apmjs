`apm` 0.1.0 checks before you install, run or publish, then hands the work to the package manager your project uses. Any command it does not know goes straight to that package manager: `apm run dev` is `bun run dev` in a bun project.

To install it, see [Quick start](/quickstart#2-get-the-apm-cli).

## Global flags

| Flag | Meaning |
| --- | --- |
| `--pm bun\|npm\|pnpm\|yarn` | The package manager to run. Default: found from the lockfile, then `packageManager` in `package.json`, then bun if it is installed, else npm. |
| `--json` | Print exactly one JSON document on stdout. Human output goes to stderr. Applies to `add`, `install`, `score`, `name`, `audit`, `yank`, `unyank`, `revoke`, `restore`, `incident`, `publish`, `login` and `whoami`. |
| `--otp <code>` | A six-digit code from your authenticator app, for commands that need a fresh second factor. |
| `--help`, `-h` | Print the command list. |
| `--version`, `-v` | Print the version. |

Exit codes: `0` success, `1` refused or failed, `2` wrong usage. A passed-through command exits with the package manager's code.

## apm add

```bash
apm add <package>[@range]... [--strict] [--force] [--no-cooldown] [--cooldown <duration>] [--floor <n>] [-D]
```

Resolves each package to the newest version that is not revoked, yanked or confirmed malicious, checks its dependency tree for the platform your package manager will install for (optional packages built for another, such as `@next/swc-win32-*` on Linux, are skipped as your package manager skips them; see [Platform](#platform)), installs the exact version with install scripts held back, verifies every installed package against the registry, then runs the scripts. `apm install <package>` and `apm i <package>` are the same command. With no packages, it runs your package manager's own install.

A score informs; it does not block. When the package or a dependency was published inside the 24-hour cooldown ("published 5 hours ago, inside apm's 24-hour cooldown"), scores under 40, has an incomplete analysis, can never be scored, is still being analysed after the wait, or could not be looked up because the registry or npm did not answer, `apm add` prints a warning block for each, then installs:

```text
WARNING left-pad@1.3.0 scores 30/100 (F), under the floor of 40
  - Sends what it collected: index.js:12: fetch(…) (sends the whole environment in a request)
  - Starts processes at install time: package.json scripts.postinstall: node setup.js
  https://apmjs.dev/package/left-pad/v/1.3.0
apm installs it anyway: a score or a fresh publish informs, it does not block. To refuse these instead, run with --strict (or APM_STRICT=1).
```

A version nobody has scored yet, the package or one of its dependencies, is queued for analysis. The registry waits up to about 20 s for the score, and the warning then says what it found; a cold package usually has its score after a few seconds. What is still pending then installs with a `not scored yet` warning.

With `--strict` (or `APM_STRICT=1`), each of those refuses instead, as apm did before: a version inside the cooldown (for the package itself, the newest older version is used instead), a score under the floor, an incomplete analysis, a version apm cannot score (`apm cannot score this version: …`), a dependency the registry could not look up, and a version still pending after `apm add` has kept asking for 90 s (`still being analysed, try again in a minute`). Revoked and yanked versions and versions an apm reviewer confirmed malicious are refused in every mode.

| Flag | Meaning |
| --- | --- |
| `--cooldown <duration>` | Warn about (with `--strict`, skip or refuse) versions younger than this, in the package and its tree. `24h` (default), `90m`, `2d`, `0`. A bare number is hours. |
| `--no-cooldown` | Same as `--cooldown 0`. |
| `--strict` | Refuse instead of warning: a version inside the cooldown, a score under the floor, an incomplete analysis, no score yet or ever, a dependency the registry could not look up, any dependency it could not check (a git, URL or file spec, a missing package, a peer it cannot pick a version for), and a dependency walk cut short at its limits. `APM_STRICT=1` does the same, and `apm explain` honours both. |
| `--floor <n>` | Warn about (with `--strict`, refuse) versions scoring below `n`. Default `40`. Dependencies are always checked at 40 or the stricter floor you ask for. |
| `--force` | Lift the cooldown for the named packages only, and in strict mode their floor. Revoked and yanked versions, versions apm reviewers confirmed malicious and unknown names stay blocked, and so, in strict mode, do versions apm has not scored or cannot score and dangerous dependencies. |
| `-D`, `--dev` | Add as a dev dependency. |

With `--json`:

```json
{ "ok": true, "pm": "bun", "error": null, "packages": [{ "name": "zod", "version": "4.6.7", "score": 90, "grade": "A", "signals": [{ "id": "eval", "points": -10 }], "skipped": [], "unchecked": [], "warnings": [], "blocked": false, "reason": null, "forceable": false }] }
```

Each entry in `warnings` is `{ name, version, kind, score, grade, text, reasons, url, via }`: `kind` is `low-score`, `incomplete`, `unscorable`, `pending`, `unavailable` (the registry or npm did not answer) or `unchecked` (the walk stopped at its limits); `score` and `grade` are set for the first two; `reasons` holds up to three, each with its file and line; `via` is the dependency path, empty for the package itself.

### Platform

apm sends the registry this machine's `os` and `cpu` only when nothing in effect for the package manager it runs can make it install packages built for another platform. Otherwise it sends `any`, says why on stderr, and the registry checks every optional package. It counts as overridden when:

- npm, pnpm or bun: `npm_config_force`, `npm_config_os` or `npm_config_cpu` is set in the environment (in any case; `force=false` does not count), or `force`, `os` or `cpu` is in a project `.npmrc`, the user `.npmrc` or the `.npmrc` that `npm_config_globalconfig` names.
- pnpm also: `pnpm_config_*` for those keys, `supported-architectures` in an `.npmrc`, `pnpm.supportedArchitectures` in `package.json`, and `supportedArchitectures` or `force` in `pnpm-workspace.yaml`.
- bun also: `[install]` `os`, `cpu` or `force` in `bunfig.toml` or the user's `.bunfig.toml`.
- yarn: always, since apm does not read yarn's `supportedArchitectures`.

### Peers your project already has

The registry walks each required peer at the version its range picks, unless something in the tree installs the peer's own package under the peer's name at a version in range (a package installed under an alias does not count). `apm add` sends the names your `package.json` lists (`dependencies`, `devDependencies`, `optionalDependencies`, `peerDependencies`); for a peer nothing in the tree installs but your project lists, it prints that your project's own version is used if it fits. apm checked the newest version in range, not yours: the registry does not see your lockfile, so `apm audit` is what checks the version you have installed.

## apm x

```bash
apm x <package>[@version] [args...]
```

Shows the package's score card, then runs it with `bunx` (bun), `pnpm dlx` (pnpm) or `npx --yes` (npm and yarn). Aliases: `apm exec`, `apm dlx`. Takes the same `--strict`, `--force`, `--no-cooldown`, `--cooldown` and `--floor` flags as `add`, warns the same way, and waits for a version still being analysed the same way. Scopes are pinned to the checked registry, but the tool's own cache is not verified afterwards.

## apm score

```bash
apm score <package>[@version] [--json]
```

Prints a version's score: every signal with its points and evidence, the publisher, the previous version's score, and the list of what was not checked. Without a version, it scores `latest`.

## apm name

```bash
apm name <name> [--json]
```

Says whether a name is free, taken, or free but refused (with the reason), plus similar names and available alternatives. When you are logged in it also says whether you already own it. See [Names and scopes](/guides/names).

## apm audit

```bash
apm audit [--json]
```

Checks every installed version against apm's revocations and the upstream advisories, whatever platform each is built for: nothing installed is skipped. Exits `1` on any finding and also when anything could not be checked.

```json
{ "ok": false, "checked": 412, "findings": [{ "id": "some-package@1.0.3", "severity": "critical", "text": "..." }], "unchecked": [] }
```

## apm publish

```bash
apm publish [--bump patch|minor|major|<version>] [--dry-run] [--tag <tag>]
```

Checks, packs with your package manager, previews the score, then uploads. With a login token the version is staged and the command prints the approval link. See [Publish a package](/guides/publishing).

| Flag | Meaning |
| --- | --- |
| `--bump` | `patch`, `minor`, `major` or an exact version. Writes the new version to `package.json` (not with `--dry-run`). |
| `--dry-run` | Run every check and print the preview. Upload nothing. |
| `--tag <tag>` | The dist-tag. Default: `latest`, or `next` for a prerelease. |

`--json` prints `status` as `dry-run`, `staged` (with `approval`, the link) or `published`, plus `name`, `version`, `registry`, `files`, `score` and `grade`.

## apm yank, apm unyank

```bash
apm yank <package>@<version> [--reason "..."] [--otp <code>]
apm unyank <package>@<version> [--otp <code>]
```

Hide a version from new installs, or show it again. Lockfiles that pin it keep working. A login token needs `--otp`.

## apm revoke

```bash
apm revoke <package>@<version> --reason "..." [--otp <code>]
```

Pulls a malicious version. `--reason` is required. Needs a fresh second factor: `--otp`, a code typed at the prompt, or a website approval of this exact command within the last 10 minutes. A version under 72 hours old is revoked at once; an older one is `revoke-pending` for 24 hours unless a second owner runs the same command. See [Yank, revoke and incident response](/guides/pull-a-version).

## apm restore

```bash
apm restore <package>@<version> [--reason "..."] [--otp <code>]
```

Undoes a mistaken revoke. The version goes back to `yanked`. Needs a fresh second factor.

## apm incident

```bash
apm incident --since <ISO time> [--reason "..."] [--dry-run] [--otp <code>]
```

Revokes every version you published since `--since` (at most 30 days back) and every token on your account. `--dry-run` lists what it would do and changes nothing. `--reason` defaults to `account compromised`. Needs a fresh second factor.

## apm login

```bash
apm login [--no-browser]
apm login --username <name> --password-stdin [--email <address>]
```

The first form signs you in through the browser with a device code and saves a staging token to your user `.npmrc`. `--no-browser` only prints the link. The second form is npm's password login, for self-hosted registries that run with `APM_LEGACY_AUTH=1`.

## apm whoami

```bash
apm whoami [--json]
```

Prints the user the current token belongs to, and the registry.

## Environment

| Variable | Meaning |
| --- | --- |
| `APM_REGISTRY` | The registry to use. Wins over every config file. |
| `APM_TOKEN` | A token to use instead of the one in `.npmrc`. Sent only to the registry it was issued for: `APM_REGISTRY`, else `registry=` in your user `.npmrc`, else the default. |
| `npm_config_registry` | Used when `APM_REGISTRY` is not set. |
| `npm_config_userconfig` | Path of the user `.npmrc`. Default `~/.npmrc`. |
| `NO_COLOR` | Turn off colors. |
| `APM_PENDING_WAIT_MS` | How long `apm add --strict` and `apm x --strict` keep asking about versions still being analysed. Default `90000`. |
| `APM_STRICT` | `1` makes `apm add`, `apm x` and `apm explain` strict, as `--strict` does. |

Without `APM_REGISTRY` or `npm_config_registry`, apm reads `registry=` from the nearest project `.npmrc`, then your user `.npmrc`, then uses `https://registry.apmjs.dev/`. The token is the `_authToken` line for that exact registry host; a `${VAR}` value is read from the environment.
