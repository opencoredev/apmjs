---
title: The ~safe registry view
description: An opt-in strict registry URL that hides versions under 24 hours old, versions scoring under 40, versions not fully analysed, and pulled versions, for any client with no extra tools.
---

`https://registry.apmjs.dev/~safe/` is the same registry with a filter in front. Any client that lets you set the registry URL gets the filter, with no apm tools installed.

It is the strict option for npm and pnpm. `apm add`, the registry's resolve and scan answers and the Bun scanner warn about a low or missing score and install anyway; the view still hides such versions, because using it is the choice to filter them. It matches `apm add --strict`, and `APM_SCANNER_STRICT=1` for Bun.

It is opt-in. The default for every client is the plain registry, `https://registry.apmjs.dev/` (see the [quick start](/quickstart)). Because the view hides every version apm has not fully analysed, a very large package can have no version in it at all, and `npm install` then fails with `No versions available`. Today that includes `next` (Next.js). If you accept that gap, keep the plain registry (`registry=https://registry.apmjs.dev/`) and run `apm add` without `--strict` (and with `APM_STRICT` unset): it warns that apm read only part of the package and installs it. `apm add --strict` refuses the same partial read, and `apm audit` reports it and exits non-zero, so a CI job that fails on audit fails on that package too. If you need full coverage, skip the package or pick a version that passes.

```ini title=".npmrc"
registry=https://registry.apmjs.dev/~safe/
```

## What it hides

A version is served only when all of these hold:

| Rule | Hidden when |
| --- | --- |
| Not pulled | It is revoked, waiting to be revoked, or yanked. |
| Cooldown | It was published less than 24 hours ago. |
| Fully analysed | apm did not read all of it, whatever its score. |
| Score floor | It scores under 40 out of 100. |
| Scored | apm has not scored it yet, or can never score it. |

The same rules apply everywhere in the view: the package document, a single version, and the tarball. A hidden version's tarball answers 404 with the reason (410 when it is revoked or confirmed malicious, otherwise 403 when the OSSF malicious-packages feed lists it), for example `some-package@2.0.0 is not in this view: published 3h ago (cooldown 24h).`

## How `latest` moves

Dist-tags point at what the view serves. If the newest version is hidden, `latest` points at the newest version that passes; when no version passes, there is no `latest` and the package lists no versions. `npm install some-package` then installs that one, without any change to your `package.json`.

## Scoring on first request

Every npm package is scored the first time apm sees it. When a client asks the view for a package, apm queues the five newest versions past the cooldown for analysis. Versions that are still unscored stay hidden, so a version can be missing for a short time and then appear. No request analyses a tarball itself; the queue does, whoever asked.

## When to use it, and when not

Use `~safe` when you want the checks with stock tools and no CLI. Compared with `apm add`:

- `apm add` also checks every package of the lockfile your package manager computes for the add, before anything is installed, verifies the install matches it, and runs install scripts only after that.
- `~safe` filters each version on its own. A package that depends on a hidden version fails to install, with the reason in the error.

The view cannot be tuned. To install one version it hides, use the plain registry for that install, or `apm add <package> --force`, which lifts the floor and cooldown for that package only. Neither installs a version the OSSF malicious-packages feed lists: the plain registry withholds those too.
