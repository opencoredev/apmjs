---
title: Bun scanner
description: Make stock bun install and bun add ask apm about every package, cancel the install on revoked or confirmed-malicious versions, and warn about low scores. Strict mode refuses those too.
---

`@apm/bun-scanner` plugs into Bun's security scanner hook. Before `bun install` or `bun add` installs anything, Bun hands the scanner the package list and the scanner asks the apm registry about each package.

Bun cancels the install when a version is:

- revoked, or waiting to be revoked;
- confirmed malicious by an apm reviewer.

A score informs; it does not block. The scanner warns, and the install goes ahead, when a version:

- scores below 40, or its analysis is incomplete;
- can never be scored (too large, not served in a form apm can check, unreadable, or past the analysis limits);
- is still being analysed after the scanner has waited 60 s for it;
- could not be checked because the registry or npm did not answer.

Each warning names the package, the score and grade or the state, up to three reasons with the file and line they cite, and a link to the version's page. With `APM_SCANNER_STRICT=1` each of these cancels the install instead.

You keep using plain `bun`. No wrapper, no alias.

## Install it

:::note
`@apm/bun-scanner` is not published to a registry yet. Until it is, install it from a clone of apm as a file dependency. See the [limit this causes in strict mode](#strict-mode-for-ci).
:::

```bash
git clone https://github.com/opencoredev/apmjs.git ~/src/apmjs
bun add -d ~/src/apmjs/packages/bun-scanner
```

Bun needs the scanner in the project's own dependencies; a global install is not enough.

Then point Bun at apm and turn the scanner on:

```toml title="bunfig.toml"
[install]
registry = "https://registry.apmjs.dev/"

[install.security]
scanner = "@apm/bun-scanner"
```

Run `bun install`. A cancelled install stops with the package, the version and the reason; a warning is printed and the install goes on.

## How a warning reaches you

Bun treats a `warn` advisory differently in a terminal and elsewhere: in a terminal it shows the advisory and asks whether to continue, and anywhere else (CI, a script) it cancels the install. So the scanner hands Bun `warn` advisories only when Bun can ask. Elsewhere it prints the same text to stderr and lets the install continue:

```text
apm scanner: warning: left-pad@1.3.0: scores 30/100 (F), under the floor of 40
    - Sends what it collected: index.js:12: fetch(…) (sends the whole environment in a request)
    https://apmjs.dev/package/left-pad/v/1.3.0
  apm lets it install; APM_SCANNER_STRICT=1 refuses it.
```

## Which registry it asks

The scanner asks exactly one registry:

1. `APM_REGISTRY`, when it is set;
2. otherwise `[install] registry` from `bunfig.toml`, the project's first, then your global one.

It never takes a registry from package data, so a tarball URL in a lockfile cannot choose who checks it or who sees your package list.

## Versions still being analysed

A version nobody has scored yet is queued for analysis. The scanner treats it as pending, never as clean: it asks again every few seconds for up to 60 s, printing which packages it is waiting for. A cold package usually gets its score in a few seconds, and the install then goes ahead, with a warning if the score is under 40. Anything still pending after 60 s is a warning ("not scored yet"), and with `APM_SCANNER_STRICT=1` it cancels the install:

```text
apm scanner: waiting for 1 package(s) the registry is still analysing (0s of 60s): left-pad@1.3.0
error: left-pad@1.3.0 is still being analysed by https://registry.apmjs.dev/ (waited 60s). APM_SCANNER_STRICT=1 installs no version before it has a score; try again in a minute.
```

Set `APM_SCANNER_WAIT_MS` to wait longer or shorter.

Some versions never get a score: a tarball too large to download or unpack, one the upstream serves in no form apm can check, one apm cannot read, or one whose analysis keeps running past the registry's limits. The registry answers each with an advisory naming the reason: a warning by default, fatal in strict mode, including when the version was pending at first and its analysis ended that way while the scanner waited. A package the registry could not look up because it or npm did not answer gets its own advisory, "could not be checked: registry or upstream unavailable", on the same terms.

## What it cannot check

The scanner prints one warning per package it could not check:

- no registry is configured;
- the registry is unreachable, or is not an apm registry;
- Bun downloads the package from a different host than the configured registry;
- the version is a git, file or link dependency, which no registry serves.

By default those installs go ahead, so a registry outage does not stop your work. Prereleases (`1.0.0-beta.1`) are checked like any other version.

## Strict mode for CI

In CI, set `APM_SCANNER_STRICT=1`. The scanner then asks the registry for strict answers, so a score under 40, an incomplete analysis, a version with no score and a package the registry could not look up each cancel the install, and so does any package the scanner could not check:

```bash
APM_SCANNER_STRICT=1 bun install --frozen-lockfile
```

```text
apm scanner: not checked: my-tool@file:../my-tool: not a registry version (git, file or link dependency), so no registry can check it
error: Security scanner failed: apm scanner: 1 package(s) not checked and APM_SCANNER_STRICT=1, so the install is cancelled
```

:::warning
While the scanner itself is installed from a path, strict mode reports it as a file dependency it cannot check, and cancels every install. Strict mode becomes usable once `@apm/bun-scanner` is on the registry. Until then, use strict mode only in projects that list no git, file or link dependencies, which rules out this way of installing the scanner.
:::
