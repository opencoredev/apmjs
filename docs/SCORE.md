# The apm score

Every version gets a number from 0 to 100, computed once from its tarball, its `package.json` and its publish history (`analyze` and `finalize` in `packages/core/src/score.ts`). It starts at 100 and every deduction is a named signal with the file and line that caused it. Below 40 (the floor), `apm add`, the `~safe` registry view and the scanners refuse the version unless you pass `--force`.

The score is a static read of text. It is a strong filter for the droppers that make up most npm malware, and a weak one against an author who knows it exists and is willing to write code that only reveals itself at runtime. Read a high score as "nothing on this list was found", not as "safe".

## What it reads, in order

1. **Lifecycle scripts.** `preinstall`, `install` and `postinstall` run on every install. `prepare`, `prepack` and `postpack` run when the package is installed from a git URL. Each one is followed the way the package managers follow it: `npm run x` (with `prex` and `postx`), `yarn x`, `pnpm x`, `bun run x`, `npm-run-all` and `run-s`/`run-p` patterns, `sh -c '...'`, and base64 payloads passed to `node -e`. Every command they reach is checked, and every word in them that names a file in the tarball is read first.
2. **binding.gyp.** Its `action` lists and `<!(...)` command expansions are commands like any install script. A `Makefile` or `CMakeLists.txt` is checked too when an install script runs `make` or `cmake-js`.
3. **Entry points**: `bin`, `main`, `module`, `browser`, `exports` and `imports` (every subpath and condition), then every file those load through a path apm can read: a literal `require`/`import`, `require.resolve('./x')`, `path.join(__dirname, 'lib', 'x')` and `__dirname + '/x'`, with node's extension and index probing (`.js`, `.cjs`, `.mjs`, `.json`, `.node`, `.ts`, `/index.*`). A subpath pattern (`"./*": { "node": { "require": "./docs/*.txt" } }`) or folder mapping (`"./lib/": "./lib/"`) is matched against the tarball, each `*` standing for the same text as node substitutes it, and every file it exposes is an entry point read as JavaScript whatever its extension: node runs `require('pkg/payload')` from `docs/payload.txt`. JSON, type declarations and `.node` files a pattern exposes are data. A README or LICENSE that `"./*": "./*"` exposes and no parser accepts is left out: node would throw a SyntaxError loading it, so nothing in it runs.
4. **Every other file that could be code**, whatever its extension (`lib/payload.dat` is read). Left out unless code reaches them: docs (`README`, `*.md`, `*.txt`), type declarations, source maps, JSON, YAML, styles and markup. Images, fonts, archives and WebAssembly are recognised by their first bytes and skipped; executables and `.node` files are listed as `binary`.

A file's bytes are read whatever they look like: a NUL byte does not make a file "binary". One file over 32 MB is not read and makes the analysis `incomplete`. All files together are read up to 200 MB, the most a tarball may unpack to; a caller analysing its own file list can pass a smaller `maxScannedBytes`. Because install targets and entry points come first, padding a package with filler can only push other filler out of the budget. A file that runs but did not fit makes the analysis `incomplete`; one that nothing was seen loading adds `unanalyzed-files`.

## How each file is read

The rules run three times: on the text as written; on the text with split strings joined (`'chi' + 'ld_' + 'process'` becomes `'child_process'`, `x['ex' + 'ec']` becomes `x.exec`, and `\x63hild` escapes are decoded); and on strings decoded from base64, hex (`Buffer.from('…', 'hex')`), char codes (`String.fromCharCode(102, 101, …)`) and URI escapes. A dangerous name or rule match that only appears after joining or decoding also counts as `obfuscated`. For JavaScript and TypeScript these passes run on the parsed program (below); for everything else, on the text.

### The floor: what v3 found stands unless the tree proves it harmless

Since **apm-score-v7** the analysis cannot score a file above what apm-score-v3 scored it by failing to follow its code. Every parsed program is also read by v3's text rules (`scanTextRules` in `textrules.ts`, with joining, decoding and the environment-dump rule) over its source with only **comments and regex literals blanked**. Strings, template text and JSX text are read. Each match rests on one token, the last name or string it touches, and **stands, confirmed, unless the tree proves that token harmless** for that signal (`floor` and `judge` in `js.ts`). A proof is one of:

- **Where it is written**: a definition's name (`function fetch(…)`, a method, a parameter, a declared variable), a property name written as a name (`{ fetch: … }`), type-only syntax, or shell text in code rather than a string (`a || sh`, `curl - x`).
- **A binding in scope that never holds a dangerous value**: the name is declared once there, never assigned, and bound to a function, class, object, array or literal the file makes (`const fetch = () => 1; fetch(u)`). The binding must also be out of reach of anything that could assign it unseen. That means a `const` or an import; or any binding not at the top level of a script, which other scripts share, in a program with no direct `eval`. A parameter, a destructured value, a module import or a value apm resolved through members proves nothing.
- **A value that goes nowhere that runs it**: the string, and everything that holds it (a `+` join, a template, an array, an object literal, a `const`), only ever reaches a comparison, a test, `typeof` or `!`, a discarded statement inside a function, or a binding nothing reads. A binding counts only if it is not at a script's top level (another script could read it), not exported, and not in a program with a direct `eval` or a `with`. A quoted key goes where its object goes, because `Object.keys` can hand it on. A statement at a program's top level is not discarded, because it can be the program's completion value, which `eval` and `vm` return.
- **A place that does not run it**: calling what an async or generator function returns (a Promise or generator object, which throws before the arguments are used); `eval`'s second and later arguments (`eval.apply(null, [, code])`); `fetch` with a constant `data:` URL (inline data, for the network signal only); `process.binding('util')` and other bindings that only read type helpers.
- **A builtin apm can name for certain** (a *sink* proof): a URL or request body sent by `fetch`, `http(s).request`/`get`, `WebSocket` or `sendBeacon`; a path read by `fs.readFile`, `readFileSync`, `createReadStream` or `open` (which still confirms a credential path, as before); a string built by `path.join`, `resolve` and their kin, an `Error`, `String`, `encodeURIComponent` or `JSON.stringify`, which goes where the call's value goes; text handed to `eval` or `String.raw` as a tag. The callee must be a global no scope in the program declares or assigns, or a member of a module loaded by a literal specifier, by names apm knows. Members of local values never count, because their members can be written through aliases.

A sink proof rests on the builtin being what its name says, so it holds only while **no file in the package could replace one**. A file could if it has a `with`, assigns or declares (where it becomes the global) a global the proofs use, or writes a member of the global object, `Object`, `Array`, `String`, `Function`, `JSON`, `navigator`, an `Error` class or a builtin module. Handing one of those, or `eval` or `Function`, to anything but a member read, a call or a check also counts. So does writing a member a builtin looks up (a conversion hook such as `toString`, or a key `fetch` reads from its options) on an object apm cannot identify, or one apm cannot name. Code apm did not read in full counts too: an evaluator finding that stands, code run from a string apm could not read in full, a template tag or a constructor apm cannot name, a module loaded by a computed name, and code loaded from a URL. When any file could, every finding a sink proof removed is added back, and the not-checked list names the file and the reason (`checkPatches`, `sinkOnly`). In the 70 packages below, 64 contain such a file. The sink proofs matter for small, plain packages and the review fixtures; on large packages the floor reads strings as v3 did.

The tree still adds what it sees and v3 missed (escaped names, a `fetch` reached through a getter, code run through a constructor chain), confirms what v3 only named, and chooses the citation: a call or load the tree confirmed is cited before a text match, in each file and in each signal's evidence list. Failing to resolve a value, meeting syntax apm does not model, or hitting a limit proves nothing, so the text rules decide.

**No silent limits.** Every bound on the analysis keeps an unknown value for what it did not follow, and an unknown value proves nothing harmless. That covers more than 6 values one expression can be, more than 32 `return` statements in one function, more than 8 `this.x = …` writes to one field in a constructor, more than 24 levels of nested values, more than 3 levels of code run from strings, 256 KB of decoded or evaluated text per file, and more than 32 steps following one value. Each one hit is named in the score's not-checked list with the files it was hit in.

The floor is tested as a property (`packages/core/test/floor-fuzz.test.ts`): generated packages wrap an inert payload in two or three shapes taken from all four reviews' fixtures, and apm-score-v7 must score each at or below apm-score-v3. The v3 reference is `packages/core/test/v3/`, copied from commit `5437674`. The shapes are template tags, `Function` subclasses and constructor chains, generators, Symbol keys, bind/apply/call/Reflect, Proxies, getters, TypeScript namespaces, logical, ternary and comma callees, shadowing decoys, `with`, exports wildcards, comments ended by every line terminator, HTML comments, JSX text, padding past the parse limit and token-window boundaries. They also include ones aimed at the proofs themselves: a replaced `fetch`, a patched `Error.prototype` or `Object.prototype`, a key read back with `Object.keys`, a completion value, a string round-tripped through `String`, `JSON` and URI encoding. CI runs 300 composed cases on a fixed seed, plus every shape alone in each language it is valid in. `APM_FUZZ_CASES=10000 APM_FUZZ_SEED=random` runs the long mode.

### JavaScript and TypeScript are parsed

Since **apm-score-v5**, JavaScript and TypeScript files are parsed, not lexed by hand (`packages/core/src/parse.ts` and `js.ts`):

- **JavaScript and JSX**: [acorn](https://github.com/acornjs/acorn) 8.19 with [acorn-jsx](https://github.com/acornjs/acorn-jsx). Each file is parsed as a script first (CommonJS, with `return` allowed at the top, and the HTML-like `<!--` and `-->` comments old browser scripts have), then as a module, then, for a `.js` file, with JSX. `.jsx` files are parsed with JSX.
- **TypeScript and TSX**: [Babel's parser](https://babeljs.io/docs/babel-parser) 8.0 with its `typescript` and `estree` plugins, as a module, then as a script, with TypeScript's legacy decorators (`experimentalDecorators`, parameter decorators) and then the standard ones (`export @dec class`). Both parsers give the same ESTree nodes with source offsets, so one reader reads both.
- **JavaScript acorn rejects** (decorators, which acorn does not parse) is offered to Babel with JSX and the same two decorator dialects, up to 1 MB. Flow is not enabled: its type annotations would read as code.

Two things parse under both goals but mean different code. An HTML-like comment hides the rest of its line in a script but is code in a module (`x <!-- y` is `x < !(--y)`), and `await` is a name in a script (`await (f)(x)` calls `await`) but an operator in a module (it calls `f`). A script that holds either is parsed as a module too, and both programs are read: node runs `.mjs` and `"type": "module"` files as modules.

Comments, strings, regex literals, template text and JSX text are whatever the parser says they are, so every ECMAScript line terminator ends a comment (CR, U+2028 and U+2029 as well as LF, in hashbangs too), `1. / x / 1` is a division, `of` and `await` are names where they are names, and `// {require(x)}` inside a JSX element is text holding an expression. TypeScript types (annotations, interfaces, `import type`, `type X = import('net').Socket`, `declare` blocks) are erased before anything runs and are not read; `import('node:http')` in a `.js` file is code whatever follows it.

**No tree is not a pass.** A file no goal accepts (invalid syntax, or Flow), or one whose tree would not fit in a Worker (more than 480,000 tokens of JavaScript, about 45 MB of tree, as acorn takes 90 to 95 bytes a token in V8; or more than 1 MB of TypeScript), is read two ways (`scanUnparsed` in `source.ts`):

- **Raw, as apm-score-v3 read every file**: every match counts, comments and strings included, and nothing is taken for a definition or a type. Here the alias patterns (`x.fetch(…)`, `= globalThis.Function`, `XMLHttpRequest`, `= require`) confirm too, as they did in v3, so a file can never score higher for losing its tree than v3 scored it. Every detection fixture of both reviews is tested that way behind a 1 MB comment.
- **Token by token**: acorn's tokenizer streams tokens without building a tree, so its memory stays flat at any size. Each token is written back in plain form at its own offset (`requ\u0069re` as `require`, `'ch\u{69}ld_process'` as `'child_process'`, comments as blanks; nothing gets longer, so citations point at the file as written), and the same rules read the result in windows of about 4 MB that end only just after a `;` token (`tokenWindows`), so no comment, string, template or escape is split and no call is cut from its arguments, however much blank space or comment sits between them. Each window also reaches 64 KB back. That undoes what only a tokenizer sees through: escaped names, braced escapes and comments between joined pieces. A character the tokenizer cannot read (a decorator's `@`) is kept and reading resumes after it. This pass only adds signals the raw pass did not confirm.

Padding a payload past the token limit (`'0;'.repeat(240001)`) or behind a 1 MB comment, or wrapping it in a decorator, therefore scores it as it scores unpadded: 30, refused. A file node runs because code `require`s or `import`s it, or because it is an entry point, is parsed as JavaScript whatever its extension (node runs `require('./x.c')` as JavaScript), so C-style comment rules cannot hide code in it. In the 70 tarballs below, 3 JavaScript files have no tree, all for size: `sass.dart.js` (5.7 MB), next's bundled webpack (2.5 MB) and a three.js Draco decoder (0.7 MB of asm.js).

C-family and Python files are lexed for comments and strings (`lexer.ts`): nothing in a package runs them as JavaScript. With no tree to prove a string harmless, only their comments are left out; shell text counts in their strings, not in their code (`a || sh` in C is not a pipe), and every other match counts as v3 counted it. Install commands and shell scripts are read raw. JSON files and type declarations (`.d.ts`) are data: what they name is possible at most, and they load nothing.

### What the code does, read from the tree

- **Calls are calls.** A function or method *definition* named `fetch` or `exec` is not a call, and nothing in a comment or string can make a call look like one. Optional calls (`require?.('x')`, `globalThis.fetch?.(u)`), escaped identifiers (`requ\u0069re`, `f\u0065tch`), `f.call(that, …)`, `f.apply(that, […])`, `Reflect.apply` and `Reflect.construct` are calls to `f`.
- **Names are followed, by scope.** Since **apm-score-v6** every name is resolved to the binding that covers it: `var` and parameters belong to their function, `let`, `const`, classes and functions declared in a block to the block, a TypeScript namespace to its body. A `const fetch` inside an unused function does not hide the global `fetch` the file calls, an ambient `declare` or a type's parameter declares nothing, and a name read inside a `with` body is taken for the global (it may be a property of the `with` object). A name with one declaration in its scope and never reassigned resolves to what it holds: `const cp = require('child_process'); cp.exec(…)`, `const { execSync } = require('node:child_process')`, `import { spawn } from 'child_process'`, `const Fn = globalThis.Function; Fn('…')()`, `const read = require('fs').readFileSync; read('.npmrc')`, `const fetch = globalThis.fetch`, `const r = createRequire(import.meta.url)`, `const { ['fe' + 'tch']: send } = globalThis`, `const { run = eval } = {}`, `const [send] = [fetch]`, a parameter's default (`function f(go = eval)`). A name declared twice in one scope, or assigned after it is declared, is read by its name only. Constants work as module targets: `const cfWorkers = "cloudflare:workers"; import(cfWorkers)` loads `cloudflare:workers` and is not a dynamic load.
- **Every operand that can be the callee.** `(a || b)(x)`, `(a && b)(x)`, `(a ?? b)(x)` and `(c ? a : b)(x)` are read as a call to each operand that can be the value: the one apm can tell is chosen when the test is a literal (`(null || eval)` is `eval`, `(true ? fetch : f)` is `fetch`), both when it cannot. Each argument takes the strongest role any of them gives it. `(0, eval)` and other comma expressions are their last operand.
- **Members of values the file makes.** An object literal's property, getter (`{ get run() { return eval } }`), spread (`{ ...globalThis }`) and `__proto__`; an array's element; a class's static members and, on `new C()`, its methods, getters, fields and `this.x = …` in its constructor; every member of a Proxy whose `get` trap returns something apm can read; a member of `Object.create(proto)`; and later writes to the object (`obj.fetch = globalThis.fetch`, `Object.assign(obj, globalThis)`, `Reflect.set`, `Object.defineProperty(obj, 'run', { get: () => eval })`, `Object.setPrototypeOf`). A getter that returns the value directly is that value, so `obj.run(code)` is `eval(code)`; one apm cannot read, or a write under a key it cannot work out, is read by the property's name (possible at most). Calling a function the file defines gives what its own `return` statements give (`const get = () => eval; get()(code)`), and `Function('return this')()` and `Reflect.get(globalThis, 'fetch')` are the global object and its `fetch`.
- **Promises and generators.** Calling what an async function or a generator returns calls a Promise or a generator object, which throws: it runs neither what the function returns nor what it is handed. Awaiting the call gives what the function returns.
- **Evaluators.** `eval`, `(0, eval)`, `globalThis.eval`, `Function` and `new Function` (called directly, parenthesized, through an alias or a constructor chain such as `[].constructor.constructor` or `(async () => {}).constructor`), string `setTimeout`/`setInterval`/`setImmediate`, `vm.runInThisContext`/`runInNewContext`/`runInContext`/`compileFunction`/`Script` and `module._compile`. What they are given is read as code: a literal, a template, pieces joined with `+`, a constant, or a payload decoded with `atob` or `Buffer.from` is parsed and read like the file, so `(Function)(\`fetch(u)\`)()` confirms both `eval` and `network`. Up to three levels of code running code are followed. `Function('return this')` finds the global object and is not eval. `eval` handed on as a value (`run(eval, code)`, `{ go: eval }`) is a possible eval, and the call it is handed to has its other string arguments read as code.
- **Arguments keep their positions** through `f.call(that, a)`, `f.apply(that, list)`, `Reflect.apply(f, that, list)`, `Reflect.construct(F, list)`, `f.bind(that, a)(b)` (bound arguments first, also through a constant holding the bound function) and spreads (`eval(...args)`), where `list` and `args` are array literals or constants holding one. Holes keep their place, so `eval.apply(null, [, code])` passes `undefined` and does not run `code`. Past a spread apm cannot read, positions are unknown and the remaining arguments are read as plain values.
- **Module loaders.** `require`, `import()`, `import`/`export … from`, `import x = require()`, `module.require`, `require.main.require`, `process.getBuiltinModule`, `Module._load`, `createRequire(…)`, and a `require` passed in as a parameter (bundles and module wrappers pass it that way).

### What a string is for

A string's **role** comes from where the code uses it, and each role confirms only what fits it:

| Role | Where | Confirms |
| --- | --- | --- |
| Module specifier | `require('x')`, `import`, `from 'x'` | the module load: `child_process` is `shell-exec`, `http`/`net`/`ws`/`axios` and `import('https://…')` are `network`, `vm` is `eval` |
| Code | passed to eval, Function, vm or a string timer | whatever the code does, read as code |
| Command | passed to `exec`, `spawn`, `execFile`, `fork`, `execa`, `Bun.spawn`, `` Bun.$`…` ``, `` $`…` `` | shell text (`curl …`, `\| sh`, `wget`, `powershell`), download commands and credential paths in it |
| Path read | passed to `readFile`, `readFileSync`, `createReadStream`, `open`, `copyFile`, `Bun.file`, `Deno.readTextFile`, also through `path.join(os.homedir(), '.npmrc')` | a credential path in it |
| Request | a URL or body passed to `fetch`, `http.request`, `WebSocket`, `sendBeacon`, `dns.lookup` | nothing beyond the request itself: shell text in a URL is sent, not run |
| Plain | anywhere else | nothing; what it names is possible |

Decoded content takes the role of the place it is used: `eval(atob('…'))` runs what the base64 holds, so what it does is confirmed; a base64 request body is sent, so what it decodes to is possible. Shell text in a URL (`fetch('https://x/curl … | sh')`), `.npmrc` in a path that is only built (`path.join('.npmrc')`), `readFileSync('child_process')` (a file name, not a module) and a token name in a request body are all possible, not confirmed.

### Evidence cites the occurrence that matched

Every finding carries the source position of the node it came from, through every transformation: a joined string is cited where its first piece is, a decoded payload where the decoder is called, and code read from a string where the string is. A comment or an earlier string with the same text cannot take the citation. (Text read raw keeps an edit map through the joining pass for the same reason.) In each file a call is cited before a reference, a reference before a module load, and a load before a string, so `vm.runInNewContext(…)` is cited rather than the `import vm from 'node:vm'` above it. A citation from a test file the package ships (under `test/`, `tests/`, `__tests__/` or `spec/`, or named `*.test.*` or `*.spec.*`) says `(in a test file)`, and a signal lists the package's own files before its tests.

### Confirmed and possible

Every code signal carries `confidence`. **Confirmed**: apm saw the code do it or load the module that does. **Possible**: the text names it (a string, an alias kept but never called, a method on an object apm cannot identify such as `config.fetch(…)` or `this.fetch(…)`) but apm did not see it used. A possible signal is labelled as one ("Possible shell use: …"), costs about a third of the points, and lists only possible evidence, each line saying why it is not confirmed. One confirmed finding makes the whole signal confirmed, and then only confirmed evidence is shown.

`prepublishOnly` and `prepublish` run only on the publisher's machine. Their commands are checked with the same rules, so a `curl … \| sh` there shows up as `shell-exec` and `network`, without a lifecycle signal. Scripts no hook reaches (`test`, `build`) never run on an installer's machine; only credential access or obfuscation in them is reported.

## What it cannot catch

Each of these is also in the `notChecked` list every score carries.

- **Runtime behaviour.** Code that downloads, decrypts or assembles a second stage while running looks like whatever its loader looks like. A loader still needs `fetch`, `eval`, `vm` or `child_process`, so it usually scores low, but the score cannot say what the second stage does.
- **Other encodings.** XOR, compression, a custom alphabet, or base64 that decodes to more base64. Only base64, hex, `\x` escapes, char codes and joined string literals are undone.
- **Names built any other way**: array lookups, computed indexes, values read from a file at runtime, or a value passed through a function apm does not follow. Constants are followed (literals, joins, templates, `[…].join('')`, `'…'.split('').reverse().join('')`, base64, hex, char codes and URI escapes), but only within one file and only for names declared once and never reassigned.
- **Files only a computed path loads.** Docs, type, JSON, style and markup files are read only when code reaches them by a path apm can resolve. Node runs any required file as JavaScript, so `require(name)` pointing at `docs/notes.md` would run code apm did not read; that call shows up as `dynamic-require` with no points.
- **Files with no tree.** A file no parser accepts, or one too large to hold as a tree, is read raw and token by token: every match counts. That cannot hide code from what apm-score-v3 caught, but it can over-report (a comment that mentions `curl … | sh` counts), and it reads nothing a tree would add (scopes, getters, argument positions). Flow-typed JavaScript is one such case.
- **Values that cross a function boundary, read by the tree.** A parameter is read by its name: `function run(f, c) { f(c) }` cannot tell that `f` is `eval`. Writes to an object through another name (`const h = g; h.fetch = …`), through a function it is passed to, or into `this` outside a constructor are not seen, and a getter or Proxy trap that computes what it returns is read by the property's name. None of this lowers a score below the floor: what the tree cannot follow it cannot prove harmless, so the text in the file counts as apm-score-v3 counted it. It means the tree adds nothing there, and that a call v3's rules do not match (`run(f, c)` with `f` an alias of eval and `c` built at runtime) is not seen. A method on an object apm cannot identify (`config.fetch(…)`, `this.fetch(…)`) counts as v3 counted it, confirmed.
- **Text that becomes code at runtime.** A comment or a regex literal is left out of the floor (that is where most of v4's precision came from), but code can read a regex's source (`re.source`) or a function's own source (`fn.toString()`, which includes its comments and strings) and run it. apm reads `/…/.source` handed straight to an evaluator, but not a regex or a function handed to code it cannot follow, and a string it proved harmless inside a function stays harmless even though `toString` could recover it.
- **Builtins replaced from outside the package.** A sink proof assumes `fetch`, `path.join`, the `fs` reads and `Error` are the builtins. apm checks every file of the package for anything that could replace one (above), but not a dependency, the runtime, or a preload script that does; a package whose own file hands the global object or a builtin module to a dependency counts as one that could.
- **Top-level bindings of scripts.** A file that is not an ES module may run as a classic script, whose top-level bindings every other script on the page can read and reassign. apm takes no proof that rests on such a binding never being read or reassigned, so a string held there counts as v3 counted it. This costs precision (`const help = 'NPM_TOKEN'` at a script's top level confirms credential access), not detection.
- **What a possible signal hides.** A command or credential path held in an ordinary string and run later through a variable (`const c = 'curl …'; spawn(sh, ['-c', c])`) is possible, not confirmed: apm cannot follow the value. Loading `child_process` is still confirmed, so the shell use itself shows.
- **Native code and WebAssembly.** Listed as `binary` (native) or skipped (WebAssembly), never read.
- **A popular name under another scope.** `@someone/react` is not a typosquat: scopes exist so names can be reused, and `@sentry/react` and `@types/node` are real.
- **Dependencies' code.** Each dependency has its own score; `risky-dependency` and the resolve tree walk use them. Git, URL and file dependencies cannot be scored and are listed by name.
- **The publisher's machine or CI.** A compromised build that publishes clean-looking code with a subtle backdoor scores well.

## Checking the false positives

Changes to the rules are checked against real packages: 70 popular tarballs (zod, react, hono, next, lodash, express, typescript, vite, webpack, esbuild, sharp and others), scored with the previous and the new scorer, and every code-signal citation read by hand.
