# The apm score

Every version gets a number from 0 to 100, computed once from its tarball, its `package.json` and its publish history (`analyze` and `finalize` in `packages/core/src/score.ts`). It starts at 100 and every deduction is a named risk signal with the file and line that caused it. Below 40 (the floor), `apm add`, `apm x`, the registry's resolve and scan answers and the Bun scanner warn, with the score, the top reasons and a link, and the install goes ahead; `--strict`, `APM_STRICT=1`, `APM_SCANNER_STRICT=1` and the `~safe` registry view refuse the version instead (see "A score informs; it does not block").

Since **apm-score-v10** the number measures what is suspicious, not what a package can do. What it can do (the network, environment variables, the filesystem, child processes, dynamic code, native code, install scripts) is listed beside the score as **capabilities**, each with its evidence, and costs nothing. Points go to what malware does: code that runs at install and reaches the network or starts processes, credential files read, the environment collected and sent, request bins and webhooks, remote shells and code run from a download, obfuscation, look-alike names, new publishers, risky dependencies, and capabilities a package's own declaration leaves out. The next section has the model and its weights. Before launch the model was hardened against an independent review: the parser now follows values from what a stealer collects to the request that sends it, and from a download to the evaluator or process that runs it, across files and through aliases; a flow it confirms puts the version under the floor on its own. "Where values go" below describes it; the rest of this page describes how files are read, which has not changed since v9.

The score is a static read of text. It is a strong filter for the droppers that make up most npm malware, and a weak one against an author who knows it exists and is willing to write code that only reveals itself at runtime. Read a high score as "nothing on this list was found", not as "safe".

## apm-score-v10: capabilities and risk signals

### Why

v9 deducted points per capability. `@opencoredev/email-sdk` 3.0.1, a legitimate SDK, scored 50: 25 points for the strings `"AWS_ACCESS_KEY_ID", "AWS_SECRET_ACCESS_KEY"` in its CLI help, 15 because bundled nodemailer loads `child_process` for its sendmail transport, 10 for calling email APIs. Popular packages lost points the same way (41 of 70 scored 80 or more), while a dependency-confusion probe whose postinstall sends the machine's identity to a request bin scored 75: an install script and a `fetch` cost the same as any SDK's. The AI release review evaluation (`research/ai-review-eval.md`) found the v9 rules caught 9 of 40 malicious samples below 60.

### Capabilities (0 points)

| Capability | From | Evidence |
| --- | --- | --- |
| `network` | v9's `network` findings | every citation v9 made |
| `env` | `process.env.X`, `process.env['X']`, `const { X } = process.env`, `Bun.env`, `Deno.env.get`, and reads by a computed name; in parsed code also through an alias (`const e = process.env; e.X`) or `globalThis.process.env`; plus whole-environment uses (`{ ...process.env }`, `JSON.stringify(Bun.env)`, `Deno.env.toObject()`) | the line of each, and the variable names |
| `filesystem` | loading `fs`, `fs/promises`, `fs-extra`, `graceful-fs`, `Bun.file`/`Bun.write`, `Deno` file calls | the load |
| `shell` | v9's `shell-exec` findings | every citation v9 made |
| `eval` | v9's `eval` findings (eval, Function, vm, string timers, a Worker from a string, inspector evaluation) | every citation v9 made |
| `native` | v9's `binary` findings, and `binding.gyp` | the file |
| `install` | v9's `install-script` findings | the hook |

Each capability says what its evidence rests on: `code` (a call or load the parsed program showed, a command, a file), `text` (only text matches, such as a variable name in help output or `curl` in a comment), or `possible`. Each line of evidence keeps v9's wording, so "(text match)" and "(text match in a comment)" still say where a match sits. The version page lists capabilities in their own section, apart from the score; `apm score`, `apm add` and the publish preview print them under the score.

**Detection does not shrink.** Every v9 finding is still in the analysis, as a capability or as a risk signal. `findingsOf(analysis)` names each finding by the id v9 gave it (a capability by its v9 code signal, `credential-read` and `credential-mention` as `credential-access`, `encoded-data` as `obfuscated`), and `test/superset.ts` checks the property v9 established, now in this form: on any package, v10's findings include every finding apm-score-v3 makes, confirmed where v3 confirmed it, citing every file v3 cites. The score is no longer compared with v3's; v10 scores capabilities at 0 by design.

### Where values go

The parser's reading of a JavaScript or TypeScript file (`flow.ts`) follows values to the calls that use them, with the same scope resolution the reader uses for names. A value carries what it came from: the whole environment object (or a copy or serialization of it; one variable is not), a path that names a credential file, what reading such a path gives, what a network response gave, a request or socket that can be written to, a secret variable of a family stealers go for, the program's own source text, or a relative module's export. It is followed through bindings and reassignments (`body += chunk`), destructuring and aliases, object and array literals, spreads, `await`, `.then` and event callbacks (`res.on('data', d => …)`), `emit` on an emitter to the listener `on` or `once` registered on it (also under another name for the emitter), a generator's `yield` to `for … of` and `for await`, the callback of a read (`fs.readFile(path, cb)`), `new Promise` executors, string building and serializers (`JSON.stringify`, `Buffer.from(…).toString('base64')`, `path.join`), and members (`res.data`). What a program puts into a container is part of it: `push`, `unshift`, `splice`, `set`, `add`, `a[i] = v`, `o.k = v`, `Object.assign`, `Object.defineProperty` and `Reflect.set`, also through another name for the container (`const b = a; b.push(env)`).

Each call of a function is worked out with its own arguments: while a body is read its parameters stay symbolic (`param:<function>:<index>`, with the members taken from them), and a call puts what its own arguments carry in their place, so `id(process.env)` kept in one place and `id('public')` sent in another are two calls. A sink inside the body (a helper that sends what it is given) takes what every call passes. A named member of an object or array the program builds is what that member holds (`tokens.npm` is the npm token, not every token in `tokens`), plus what the program later puts under that name or under a name apm cannot read. A named property of a value holding a credential path is not that path (`config.root` beside `deny: ['.npmrc']`), and a named entry of a credential file's parsed contents (`rc['//registry.npmjs.org/:_authToken']`) is one token, not the file. A named field of a response that is not its body (`json.version`) still runs as downloaded code in an evaluator, but put into a longer command it is a value, not a command.

A value another file exports is worked out once every file is read, as a fixed point over the package's export graph: each export is one node whose labels only grow, so a shared re-export DAG costs one visit per edge rather than one per path through it, and a cycle ends when nothing new arrives. The whole package has one allowance for this, carved out of the work meter below (`MAX_CROSS_FILE_STEPS`, 2,000,000 steps, each label looked at a step); it is checked at every step, the final resolution of each flow included, and a package that runs it out is `incomplete`.

The calls it reports are the reader's own roles: an evaluator (eval under any name, `Function`, `vm`, a `Worker` with `eval: true`, string timers), a process (`exec`, `spawn`, `Bun.$`), a request (`fetch`, `http(s)`, sockets, `sendBeacon`, DNS, the calls of HTTP client libraries such as axios and got, writes to a request or socket, and the arguments of `curl`, `wget` and `nc`, as a program or at the start of a command line), and a file read. A file the program writes (`writeFileSync`, `fs.promises.writeFile`, a write stream fed by `pipe`, `write` or `pipeline`, `Bun.write`) and then loads (`require`, `import()`, `fork`, a `Worker`, `node <file>`) or runs as a program (`execFile`, `spawn`, `exec('./agent …')`) is matched by its binding or its path, so downloaded bytes written and then run are run. A regex's `exec` is not a command, and what an address lookup gives (`dns.lookup`, `resolve4`, `resolve6`, `reverse`) is not downloaded text. From those come the confirmed facts behind `exfiltration` (-61), `remote-shell` (-61) and `credential-read`. A downloaded body put into a longer command a shell runs (`exec('echo ' + body)`, a template, `spawn(cmd, { shell: true })`) may run as a command and may not, so it is a possible `remote-shell` at its table weight (-50), which puts it under the floor at install; a helper's command parameter is judged by the shape each caller passes it.

Code a file holds as text is read as a program of its own, cited at the line that holds it, so what runs at install is still install time: a string it hands an evaluator (decoded or not), text it recovers from its own source and runs (a function made a string with `String(fn)` or `fn.toString()`, a regex body through `.source`, the file read through `__filename` or `import.meta`, with the comment and regex delimiters taken out so what they held reads as the code it becomes), and a string that reads as a program used some other way (a builtin another file redefines as an evaluator can run it; only the risks such a string holds count, not its capabilities). A string a module only keeps as data (what it exports, directly or in object and array literals it exports with no method beside the string, as a code generator's examples are) adds its risks but not its flows: no confirmed flow comes from text that does not run. The same string written to a file and loaded is run code. Recovered text whose comments name nothing dangerous is prose and is left alone; recovered text that names a network, process, credential or code call is `runs-decoded-code` on top of whatever it does. Runs of whitespace in recovered text and in code run from strings are squeezed to one before the limits apply, so padding cannot push a payload out of view. Code held as text is followed three levels deep and up to 256 KB per file, and one string or one recovered range up to 256 KB; code that runs past any of these is `incomplete`, never dropped.

Small decoder functions the program defines are run on the strings they are called with (`decode.ts`): a function of a few hundred characters whose body is expressions over strings, numbers and arrays (string and array methods, `String.fromCharCode`, `parseInt`, `atob`, `Buffer` decoding, arithmetic, and callbacks of those), so `require(g('6178696f73'))` reads as `require('axios')`. A run ends one of three ways. **Decoded**: the string it returns. **Unsupported**: the function does something the decoder does not run (a loop, a write, a call it does not know, a `$` pattern in a replacement), and the value stays unknown as any other computed value does. **Exhausted**: it hit a limit, and the call is code apm did not finish reading, so the analysis is `incomplete`. The limits are 200,000 steps a call, 2,000,000 for every call in one file together, 64 KB of text (counted before `join` or `replace` builds a string), calls nested four deep, and the file's 256 KB of decoded text. Every string or list a step builds or copies costs a step per 16 characters, and every step is charged to the work meter as it is taken. The built-in decoders the reader works out itself (`atob`, `Buffer.from(…, 'base64' | 'hex')`, `decodeURIComponent`, `unescape`) check the file's decoded-text budget before they decode: what they give is never longer than their input, so a decode that does not fit is not run, and the code it would have given is code apm did not read (`incomplete`). Before this, seven `sink(atob(…))` calls of 60,000 characters each scored 80 with a note, and one large decode could go past what was left. A regex runs only if apm can prove it linear (`safeRegexCost`). That means characters, escapes, `.` and classes, each once or an exact `{n}` times (n at most 99, 64 characters wide in all), with at most one optional atom in the whole pattern and no groups, alternation, back-references, lookarounds, open or ranged repeats, or lazy quantifiers. Such a pattern tries at most two fixed paths from each start, and that work is charged to the step budget before the engine runs. Any other pattern is unsupported. Before this, `^(a?){40}a{20}$` passed the old check and backtracked 2^40 paths inside native `replace`, outside every budget.

What stops it: a value followed more than 32 steps, a module apm cannot resolve, and obfuscator output, whose strings come from tables no flow analysis follows (there a hidden credential name still counts as a read). Past each, the text rules and the close-together rules above are the floor. Each of these makes the analysis `incomplete`, or `unanalyzed-files` for files nothing runs, and none of them reads as clean:

- a chain of values deep enough to exhaust the stack;
- one file's flow allowance (`MAX_FLOW_WORK`: 64 million meter units, a label rebuilt with a member name costing more than one followed);
- the cross-file allowance;
- a decoder that hit a limit (above);
- one file's constant strings past a million characters and 16 for each character of the file (`const s1=s0+s0` doubled 23 times builds 16 million from 435 bytes, and scored 100 before);
- the analysis's work meter (below).

The flow budget exists because imported helpers that pass each other's results multiply labels with every level: a generated 1.3 KB file ran for more than a minute without it.

**Bounded, and how.** One work meter (`packages/core/src/meter.ts`) covers a whole analysis: inflating the tarball, reading the tar and PAX headers, parsing, scopes, constant folding, reading the tree, flow, cross-file resolution, decoders, code read from text and recovered source, the text rules and scoring. Every operation whose cost grows with the input charges it before it does the work: AST walks (every walk goes through one child-listing helper, which charges each node and field), scope lookups per scope climbed, label sets by their size and labels by their length, folded strings by the length they will have, regex passes by the length of the text they read, decoder steps and what they build, and copies. The meter holds `MAX_ANALYSIS_WORK`, 320 million units. When it runs out it throws, which unwinds the whole analysis: no phase carries on past it, it stays spent so a later charge throws again, and `analyze` checks it before it returns. The analysis is then `incomplete`, and its evidence names the phase ("analysis work limit: apm stopped reading this version while following values across files, …"); what the reading found before it stopped is not reported, since half a reading cannot be weighed, and `incomplete` alone puts it below the floor. The per-phase allowances (a file's flow work, the cross-file steps, a file's decoder steps and folded strings) are carved out of the meter: charging one charges the meter too, and each only decides when that phase stops while the rest of the analysis goes on. There is no time limit any more: in a deployed Worker the clock does not move while code runs, so a deadline bounded nothing there.

A unit is sized to cost about the same in every phase (a text pass reads 32 characters a unit, an acorn token is 4 units, a Babel try 2 units a character). The tarball's gzip trailer says how large it inflates, which is charged before anything is inflated, and a stream that inflates past what its trailer says is refused as invalid. Every regex over package text is tested for linear time: `test/regex-linear.test.ts` runs every regex literal in `src/` and every rule pattern on inputs built for backtracking, and fails on any whose time grows faster than its input. It found four besides the PAX one: `importsOf`'s `\b[\w$]+\.join(` restarted at every `a$` of `a$a$…`, the net-tool command match's `\S*\/` scanned from every `$(`, and the secret scan's `//[^\s:]+:_auth` from every `//` and `^\s*_auth` across blank lines. A pattern built from strings is not a literal, and the review of d49bf6e found one that was quadratic: the environment-dump match's `\bfor\s*\(\s*(?:const|let|var)?\s*[\w$]+` split a run of blanks between two adjacent `\s*` from one `for (`, so `for (` and 64K blanks took 2.4 s while the meter charged one linear pass. It now reads `(?:(?:const|let|var)\s+)?`. `test/runtime-regex.test.ts` greps `src/` for every `RegExp(` call, runs `src/` in a process that records every regex built at runtime and the line that built it (the parser's own included), fails if a grepped call was never recorded, and times each one on the same inputs plus one start followed by one long run (`for (` + n blanks + `!`, for every word a pattern names). The decoder's one call, which builds a package's own regex, is checked instead: it runs only patterns `safeRegexCost` proves fixed-width.

A `package.json` is read without recursion before anything recursive reads it (`src/manifest.ts`): an explicit stack, one unit charged per value and its text, stopping at 64 levels, 100,000 values or 4 MB of text. Past a limit the analysis is `incomplete` and nothing else reads the manifest. Before this a manifest nested a few thousand levels deep overflowed the stack in zod or `JSON.stringify` and the analysis threw; the fallback for a spent meter read the manifest recursively too, and now reads only its top-level fields when it is past a limit. Folder exports are matched once per distinct target, each comparison and each file added charged, into a set no larger than the file list: 1,600 conditions all naming `./lib/` over 1,600 files had made 2.57 million comparisons and as many list entries for 60,129 units. Glob patterns a package writes (capability declarations, npm-run-all patterns, `exports` subpaths) are matched in one pass, no longer as regexes that backtrack over every way to split the text between stars.

The meter is not a proof that an analysis is bounded. Every review so far has found some work it did not charge (in the fourth round: the regex, the folder exports and the deep manifest above), and the next may find another. So the bound is layered:

1. **The meter** stops every phase it counts, and its failures are reported as `incomplete`.
2. **The platform's CPU limit** (today Cloudflare's default 30 s per invocation, set on the registry Worker in packages/infra: `WORKER_CPU_MS` in packages/registry/scripts/compat.ts; raising it to the 300 s maximum would let a full meter fit) stops a run the meter undercounted. A Worker spends about 4.7 times this machine's CPU per unit (vite 8.3.8 on staging: 5.2 s against 1.1 s), so a full meter is about 70 s there; at the default 30 s, three 0.187.0 was stopped on every run.
3. **Recovery** turns any run that ends without a stored result into a stored outcome after bounded retries: a platform stop, an out-of-memory kill, a stack overflow, any thrown error (see "In the registry"). Until a version has a real score it is pending: a warning in default mode, refused in strict mode and hidden by `~safe`.

An input the meter undercounts can therefore cost CPU, up to the platform's limit per try and a bounded number of tries, but it cannot yield a clean score, and no version is left looking queued forever. The measurements below say what the meter costs on the inputs we have; they are not a bound on inputs we have not seen. Measured in V8 (Node 24, the engine workerd runs) on this machine, by main-thread CPU time:

| | units | CPU | per unit |
|---|---:|---:|---:|
| three 0.187.0, the slowest package of the corpus under the registry's caps | 168.4 M | 6.4 s | 38 ns |
| the 70 popular packages, most per unit (angular-core) | 18.2 M | 0.9 s | 50 ns |
| the adversarial suite, most per unit (a re-export DAG of 3,201 files) | 6.3 M | 0.35 s | 55.5 ns |
| the adversarial suite, a full meter (3,200 files nested 200 to 800 deep) | 320 M | 11.1 s | 35 ns |

On these inputs a full meter costs about 320 M × 55.5 ns = 17.8 s of CPU, and three uses 53% of the meter. The suite (`test/fixtures/adversarial.ts`, 24 generators, one or more per phase and the review's cases at 90b3072) was swept at one to sixteen times each generator's base size, and the most expensive unit of any case spending more than 5 million units is the one above. An input that is not in the suite may cost more per unit; that is what the platform limit and recovery are for. Of the 70 popular packages, two are over the registry's unpack cap and need more: prisma-client 7.10.1 (234 M, which fits) and next 16.4.6 (852 M, which does not: `incomplete`, 39; the registry records it too large and never analyses it).

`test/termination.test.ts` runs every generator in a child process with a kill timer, under a meter capped at 10 million units, and checks each finishes in under 2 s, and that each one that ran the meter out is `incomplete`, below the floor, never clean; a seeded property test does the same for random compositions of two to four generators at a quarter to eight times their base size.

Every risk signal cites its evidence the way v9's signals did, and an apm reviewer can dismiss evidence of the code risks (`credential-read`, `credential-mention`, `encoded-data`, `obfuscated`, `exfiltration`, `capture-endpoint`, `remote-shell`, `runs-decoded-code`, `install-network`, `install-shell`, `install-eval`) for one tarball digest, as before.

### Declared capabilities

A package can say what it does in its `package.json`:

```json
{
  "name": "@opencoredev/email-sdk",
  "apm": {
    "capabilities": {
      "network": ["api.resend.com", "*.amazonaws.com"],
      "env": ["AWS_*", "RESEND_API_KEY", "*_BASE_URL", "SMTP_*"],
      "filesystem": "reads attachment files",
      "shell": "sendmail transport"
    }
  }
}
```

The keys are `network`, `env`, `filesystem`, `shell`, `eval`, `native` and `install`. A value is a reason (a string), `true`, or a list; `false`, `""` and `[]` declare nothing. A capability the code uses and the declaration lists is shown as declared. One the code uses (with `code` evidence; a text mention does not count) and the declaration leaves out is `undeclared-capability`. One declared and never seen is shown as "declared, not seen used", a note. For `env`, the list is variable names where `*` stands for any run of characters; variables read outside it are listed under the capability, not scored. Network hosts are shown as declared, not checked against the URLs in the code: too many URLs in code are documentation links for a host check to mean anything. A declaration never cancels a risk signal. A package without a declaration, which is most of npm, is scored on risk signals alone; an `apm` field without `capabilities`, or one apm cannot read, counts as no declaration (the second with a note), so a typo cannot cost points.

### A score informs; it does not block

Since the project owner's policy of 2026-11, no install is refused because of a score. The score tells users and agents what apm found, and the install goes ahead. What it warns about, and what each surface does by default and in strict mode:

| State | `apm add` / `apm x` | Bun scanner | Agent verdict (`apm explain`, `explain_install`, `/api/explain`) |
| --- | --- | --- | --- |
| Score under 40 | warns, installs; `--strict` refuses | warns, installs; `APM_SCANNER_STRICT=1` cancels | `review-first` ("Installs, but scores 30/100 (F): …") |
| Analysis `incomplete` (sass, three and next in the corpus) | warns, installs; strict refuses | warns; strict cancels | `review-first` ("Installs, but apm could not fully analyse it: …") |
| Never scorable (too-large, unavailable, unreadable, analysis-limit) | warns, installs; strict refuses | warns; strict cancels | `review-first` |
| Still pending after the wait (about 20 s at the registry, 60 s at the scanner) | warns, installs; strict waits up to 90 s, then refuses | warns; strict cancels | `review-first` |
| A dependency whose metadata could not be fetched (registry or npm down) | warns "could not be checked: registry or upstream unavailable", installs; strict refuses (resolve `503`, `Retry-After`) | warns; strict cancels | `review-first` |
| The dependency walk stopped at a limit (300 packages, 400 lookups, 32 levels) | warns, installs; strict refuses | not applicable (the scanner sees bun's full list) | `review-first` (dependencies not all scored) |
| Revoked or revoke-pending | refused (`--force` does not lift it) | cancelled | `do-not-install` |
| Yanked (new resolves) | refused | not flagged (lockfiles keep working) | `do-not-install` |
| Confirmed malicious by an apm reviewer, the version or anything in its tree | refused (`--force` does not lift it) | cancelled | `do-not-install` |
| Inside the 24-hour cooldown | skipped; refused when nothing else is in range; `--force` or `--no-cooldown` lifts it | not flagged | `review-first`, no command |

A warning names the package and version, the score and grade or the state, up to three reasons, each with the file and line its evidence cites, and a link to the version's page. Resolve carries them in `warnings` on a `200` and keeps the structured `tree.pending`, `tree.unscorable` and `tree.unavailable` lists; scan carries them in `warnings`, with `warn` advisories and `pending`, `unscorable` and `unavailable` lists. The Bun scanner returns a `warn` advisory only where bun can ask about it (a terminal): elsewhere bun cancels the install on a `warn` advisory, so the scanner prints the same text instead and the install continues. The `~safe/` view stays a filter, since using it is the choice to filter: it is the strict option for npm and pnpm, and still hides versions under 40 and incomplete ones.

### In the registry

An upstream version is analysed in the registry Worker, on the analysis queue, and never by a request, signed in or not: a version with no stored analysis is queued, and the answer says so (the score endpoint's 503 `pending`, scan's `pending`, the website's queued notice, which refreshes the page until the score is there). Before this (review of 5b5b492, finding 3), a token caller's or website session's request analysed up to two small tarballs itself and downloaded before it recorded the attempt, so three runs stopped inside the download left no outcome row, no reservation and no queued job; inline analysis and its budget are gone. The queue's consumer takes one message per invocation and gives the analysis the whole meter, unpack included, under the registry Worker's CPU limit (`WORKER_CPU_MS`, which packages/infra sets; at today's default 30 s, three 0.187.0 is stopped every time and stored incomplete). A registry with no queue records each job all the same, and its cron sweep runs it.

A version with no score is pending, never clean, on every install path:

- `GET /-/apm/v1/resolve` treats a queued root or dependency as pending. It waits up to 20 s for the queue, reading the database once a second (I/O, not CPU), then answers from what landed. What is still pending is a `pending` warning on a `200`; with `strict=1`, a `202` with `pending` and `Retry-After`.
- `apm add --strict` and `apm x --strict` ask again with progress for up to 90 s, then refuse with "still being analysed, try again in a minute".
- The scan API lists queued versions in `pending`. The Bun scanner asks again for up to 60 s, then warns about anything still pending; `APM_SCANNER_STRICT=1` cancels the install.

Measured end to end in the acceptance suite (`tests/acceptance/cold-install.test.ts`, the Worker in Miniflare with its queue), anonymous, after inline analysis was removed: `apm add` of a cold clean package installed in 2.1 s; `apm add` of a cold root with a cold `curl … | sh` dependency waited for the score, warned naming it and installed in 2.2 s, and `apm add --strict` of it was then refused in 0.1 s; `bun add` through the scanner took 3.1 s for a cold clean package (installed) and 3.1 s for a cold malicious one (warned, installed), and with `APM_SCANNER_STRICT=1` the malicious one was cancelled at once. On d49bf6e the first two were refused or passed at once (0.1 s), and the malicious one installed.

A per-address limit on the requests that queue is not added: the website reaches the registry through a service binding without the visitor's address, so it would throttle every website visitor as one client, and what an anonymous request can cost is bounded without it (no analysis, one claim per version per 10 minutes, and a metered run on the queue).

Should the platform stop a run anyway, its record exists before it does anything: a queued run counts its start (`startAnalysis`, a row in `analysis_outcomes`, migration 0010) before it asks the upstream for the packument or the tarball, and decides whether to stop trying before it downloads anything. The cron's sweep every 10 minutes (`Analysis.recover`) requeues every run that began longer ago than the CPU limit plus two minutes (`RUN_WINDOW_MS`) and never stored an analysis or an outcome (migration 0011 indexes them), and every job the queue accepted at least 10 minutes ago that never began a run (`analysis_jobs`, indexed by migration 0014). A sweep sends at most 200 (`RECOVER_PER_SWEEP`), and each kind has half of them (`RECOVER_ACCEPTED_SHARE`); either takes what the other leaves unused. Before this (review of 89441a9, finding 6), unfinished runs came first, so 200 of them left the accepted jobs waiting through every sweep. So a stopped run always ends in a stored outcome:

- If another run began within that window, it may still be going, and the job comes back after it.
- A run cannot learn why the platform ended the one before it (its CPU limit, its memory limit, a deploy), so recovery does not ask. The run after one that never stored anything is run again in full. The run after two such runs reads at most 4 MB under a quarter of the meter, and its analysis is `incomplete`, with the reason as its first evidence line. The run after three records `analysis-limit` without asking the upstream anything (`planFor`, `STOPS_BEFORE_RERUN`).
- Before this, the run after a single stop was the smaller re-run. On production on 13 Nov seven queue runs shared one isolate, its memory went past 128 MB, and the platform ended all seven; the next delivery of express 5.3.0, axios 1.21.1, eslint 10.14.0, prettier 3.10.1 and tailwindcss 4.3.5 read less and stored 39, though express needs 0.3 s of CPU. The queue consumer now runs one invocation at a time (`maxConcurrency: 1` with `batchSize: 1`, `packages/infra/alchemy.run.ts`), so analyses never share an isolate's memory.
- A run that fails with an error it reports, or cannot fetch the version, ended: it is not a stop, and the run just after it is in full. The counts alone cannot say which run came last, so the store records the start number of the latest run that reported how it ended (`reported_start`, migration 0017). Before this (review of 89441a9, finding 5), two stops and then a reported failure (`starts` 4, `failures` 1) still picked the smaller re-run. The stop bound holds across such histories: three stops in all record `analysis-limit`, whatever came between them.
- A run that cannot fetch the version (the upstream could not be asked, or answered with an error that may pass) keeps its start, counts a fetch failure (`fetch_failures` and `fetch_failed_since`, migration 0013) and ends, so the queue's retry 30 s later runs it again, and once the queue's retries run out the sweep does. Fetch failures are starts but not analyses, so they do not count toward `analysis-limit`. Once there are 10 of them and an hour has passed since the first, it is settled as `unavailable`; a shorter outage never settles a version. A run that loses the database after it began counts the same way: its result's write is tried twice more first, then the run is handed back so the queue's retry runs it in full, not as the smaller re-run (on staging a closed Hyperdrive connection under vite 8.3.8 had stored that re-run's incomplete 34).

Before this (review of 9913a74, finding 3), the run probed the upstream and fetched, verified and cached the tarball before it recorded its start: six failures there left no record and the sweep found nothing, and a row already at two starts stayed at two through six more.

A run that fails with an error it can report (a stack overflow, a bug) keeps its start counted too: `failAnalysis` counts the failure, keeps the error's class (never its message, which may quote the package) and marks the run ended, so the queue's next delivery or the sweep starts it again. After 2 failed runs the version is stored as `incomplete`, naming the error class. No run takes its start back. Before this, every reported failure reset the record, so the sweep never saw the version again.

A queued version the upstream no longer has (the package, the version or its tarball) is settled as `unavailable`, so the sweep never picks it again. The sweep takes the rows it picked longest ago (or never) first, and marks each one it picks (`swept_at`, migration 0012, indexed by 0014), so rows it cannot settle go to the back.

The analysis indexes (0011 and 0014) are built `CONCURRENTLY` outside a transaction, as 0009's is, with a bounded `lock_timeout`, and a failed build's invalid index is dropped before the next try; 0012 and 0013 only add columns, with a 2 s `lock_timeout`. Before this (review of 5b5b492, finding 4), 0013 built `analysis_jobs_queued` with a plain `CREATE INDEX` in its transaction, so one open write to `analysis_jobs` held the build and every later queue write behind it. `packages/registry/test/migrate.test.ts` holds a write open while the migrations run and checks that a later write still goes through. Before this, 200 removed versions ahead of one stopped live version were picked by every sweep, and the live one never was.

`packages/registry/test/analysis-stops.test.ts`, against the real Postgres store: one stop is followed by a full run that stores a complete analysis (on 3549541, the smaller re-run's incomplete one); two stops by the smaller re-run, whose first evidence line is its reason; three by `analysis-limit`; and a run that failed with an error it reported by a full run.

`packages/registry/test/analysis-recovery.test.ts`, against the real Postgres store with recording stubs: a run stopped between its start and its store is requeued and the rerun runs in full; after three stops the fourth run records `analysis-limit`; a run that throws is retried and the second failure stores `incomplete` naming `RangeError`, queued or swept; a run stopped inside the tarball fetch keeps its record and is requeued; no request, signed in or not, downloads anything; 200 removed versions ahead of a live one are settled by the first sweep, after which the live one is scored; runs stopped while fetching are counted and the fourth gives up without downloading; a row at three starts is settled before any upstream call; ten packument or tarball fetch failures over an hour settle the version `unavailable`, and thirty in a quarter of an hour do not; and an accepted job that never ran is requeued once it may be claimed again.

A version is therefore never left looking queued forever, and never scored clean on a reading that stopped short.

Some versions can never be scored, and the registry records why, per scorer:

- `too-large`: the tarball is over the 32 MiB download cap or the 48 MiB unpack cap. next 16.x is 43 MB and 192 MB.
- `unavailable`: the upstream lists no checksum, serves the tarball from a host apm will not fetch, or no longer has the package, the version or its tarball.
- `unreadable`: not a gzip tar apm can read, or a path appears twice or escapes the package folder.
- `analysis-limit`: the platform stopped its analysis twice before it finished.

For such a version:

- The score endpoint answers 422 with the reason, not 503 "queued, try again in a minute".
- The website says it cannot be scored and why.
- `apm add` and `apm x` install it with a warning that gives the reason; `--strict` and the `~safe` view skip it with the reason. As a dependency it is a warning on the tree (listed in `tree.unscorable`); strict resolve answers 422 naming it and the reason, and `--force` does not lift it.
- The scan API answers it with an advisory naming the reason: `warn` by default, `fatal` in strict mode.

None of these is installed as if it passed: each says it has no score. Before this (review of 9913a74, finding 2), a dependency that went from pending to `analysis-limit` made resolve answer 200 with it only unchecked, and the scan listed it as unchecked, with no word of why. A version stored `incomplete` after failed runs has a score (39 at most) and warns as any low score does. `packages/registry/test/resolve-pending.test.ts` covers each of the four reasons in resolve and scan, and `tests/acceptance/unscorable.test.ts` runs `apm add` and `apm x` against one.

### Every limit, and what it does

An analysis that did not read every file it should have is `incomplete`, 39 or below. No limit is absorbed into a normal-looking result: each one below either makes the analysis `incomplete` or does not drop code that would otherwise be read.

Make the analysis `incomplete`:

- The work meter, anywhere (`analyze` catches `MeterExhausted`, and checks the meter before it returns in case a step swallowed it).
- A `package.json` past `MANIFEST_LIMITS` (64 levels, 100,000 values, 4 MB).
- A file over 32 MB, a file past the 200 MB budget whether or not an entry point reaches it, and a re-run's 4 MB budget.
- A parser limit: more than 480,000 tokens, more than 1 MB of TypeScript, or a stack too deep for acorn, Babel or the reader (finding 1 of the review of 9913a74).
- Flow analysis that runs out of its work budget or of stack, and cross-file resolution past its steps.
- Code run from a string past three levels, 256 KB in one file, 256 KB in one string or 50 strings; recovered source past 256 KB.
- A decoder function stopped at its steps, characters, call depth or a builtin's `RangeError`; a built-in decode, or char codes, past the file's 256 KB of decoded text.
- A lifecycle hook whose expansion stops at 8 levels or 200 commands, and a file handing more than 200 commands, or one of more than 4,000 characters, to a shell or a process.

Do not drop code (each was checked against this rule in this round):

- `String.fromCharCode` used to keep only the first 65,536 codes; it now builds the whole string, and import lists are no longer cut at 500 paths.
- A JavaScript file over 1 MB that acorn rejects is not offered to Babel. acorn reads all the JavaScript node runs; Babel only adds the decorator dialect node does not run, so acorn's syntax verdict stands.
- A decoder apm does not support leaves its value unknown, as any value computed at runtime is; nothing was cut.
- A base64 literal past the decoded-text budget that no code is seen decoding is data: it is decoded only to look inside it, and code that decodes it goes through the checked path above.
- The tokenizer's 64 resumes in a file no parser accepts: what follows is still read by the rules as written.
- `package.json` fields that are not paths or strings (`main: 3`, a non-string script) are ignored by node and npm too.
- A tarball over 100,000 entries, 32 MiB to download or 48 MiB to unpack is recorded `too-large`, not scored.

Bounds on precision, not on reading: the reader still visits every node and the text rules still read the whole file. These are an expression with more than 6 possible values, a function with more than 32 return statements (for the reader's names; the flow reads every return), a constructor that sets one field more than 8 times, values nested more than 24 levels, a value passed through more than 32 steps, and a command variable with more than 8 values. They are listed in what a report did not check, and they fire in most large bundles of the 70 popular packages, so hitting one is not by itself `incomplete`.

A bound never empties a value (review of 5b5b492, finding 1: the environment copied through 32 nested `Object.assign({}, v)` calls, or returned before 32 other returns, scored 100; 28 copies scored 39). A value cut at a bound keeps every label apm saw up to there and a `limit:<bound>` label that says it was cut. Past the 32 steps, the code under the cut is read without recursion (up to 4,096 nodes) for every label it names: the environment, a relative module's export, a credential path, a download. A name the reader stopped resolving at a bound (6 candidates, 8 constructor writes, 24 levels, 32 returns) carries the bound too, and a call whose callee was cut is a call apm could not name, which may send, run or load what it is given. A command variable with more than 8 values is checked against every file the program wrote.

Where such a cut value reaches a call that sends (the environment, a credential file's contents), runs, executes or loads (a download, the program's own source), or a call apm could not name past a bound, the analysis is `incomplete`, and the reason names the file and line, the bound, and what the value may carry. A cut value with none of those, or one that reaches no such call, stays a note. `packages/core/test/v10-r6.test.ts` has the review's two cases and one for each other bound; each scored 100 at 5b5b492 (the 8-values case with no note at all) and scores below 40 now. The corpus is unchanged: the same 3 packages (sass, three and next) are `incomplete`, no score or signal moved, and the full evaluation took 6% more CPU (78.9 s to 83.6 s). The first 40 facts of each kind per file are still the facts kept, but past them one that sits beside a network call is still placed, and exfiltration reads a harvest fact beside the network when the file has one, not only the first.

## What it reads, in order

1. **Lifecycle scripts.** `preinstall`, `install` and `postinstall` run on every install. `prepare`, `prepack` and `postpack` run when the package is installed from a git URL; both kinds run on the installing machine, so the files they run are install-time code. Each one is followed the way the package managers follow it: `npm run x` (with `prex` and `postx`), `yarn x`, `pnpm x`, `bun run x`, `npm-run-all` and `run-s`/`run-p` patterns, `sh -c '...'`, and base64 payloads passed to `node -e`. Every command they reach is checked, and every word in them that names a file in the tarball is read first.
2. **binding.gyp.** Its `action` lists and `<!(...)` command expansions are commands like any install script. A `Makefile` or `CMakeLists.txt` is checked too when an install script runs `make` or `cmake-js`.
3. **Entry points**: `bin`, `main`, `module`, `browser`, `exports` and `imports` (every subpath and condition), then every file those load through a path apm can read: a literal `require`/`import`, `require.resolve('./x')`, `path.join(__dirname, 'lib', 'x')` and `__dirname + '/x'`, with node's extension and index probing (`.js`, `.cjs`, `.mjs`, `.json`, `.node`, `.ts`, `/index.*`). A subpath pattern (`"./*": { "node": { "require": "./docs/*.txt" } }`) or folder mapping (`"./lib/": "./lib/"`) is matched against the tarball, each `*` standing for the same text as node substitutes it, and every file it exposes is an entry point read as JavaScript whatever its extension: node runs `require('pkg/payload')` from `docs/payload.txt`. JSON, type declarations and `.node` files a pattern exposes are data. A README or LICENSE that `"./*": "./*"` exposes and no parser accepts is left out: node would throw a SyntaxError loading it, so nothing in it runs.
4. **Every other file that could be code**, whatever its extension (`lib/payload.dat` is read). Left out unless code reaches them: docs (`README`, `*.md`, `*.txt`), type declarations, source maps, JSON, YAML, styles and markup. Images, fonts, archives and WebAssembly are recognised by their first bytes and skipped; executables and `.node` files are listed as `binary`.

A file's bytes are read whatever they look like: a NUL byte does not make a file "binary". One file over 32 MB is not read and makes the analysis `incomplete`. All files together are read up to 200 MB, the most a tarball may unpack to; a caller analysing its own file list can pass a smaller `maxScannedBytes`. Because install targets and entry points come first, padding a package with filler can only push other filler out of the budget. A file that runs but did not fit makes the analysis `incomplete`; one that nothing was seen loading adds `unanalyzed-files`.

## How each file is read

The rules run three times: on the text as written; on the text with split strings joined (`'chi' + 'ld_' + 'process'` becomes `'child_process'`, `x['ex' + 'ec']` becomes `x.exec`, and `\x63hild` escapes are decoded); and on strings decoded from base64, hex (`Buffer.from('…', 'hex')`), char codes (`String.fromCharCode(102, 101, …)`) and URI escapes. A dangerous name or rule match that only appears after joining or decoding also counts as `obfuscated`. These passes run on the whole text of every file (the floor, below); for JavaScript and TypeScript the parsed program then adds what its tree sees.

### The floor: v3's rules over all text, by construction

Since **apm-score-v9** the score's findings include every finding apm-score-v3 makes, on any package, and its score is at most v3's. That holds by construction, not by a list of proofs:

- **v3's rules read all text.** Every file is read whole by v3's text rules (`scanTextRules` in `textrules.ts`: the rules as written, with split strings joined, on decoded strings, and the environment-dump rule; each rule carries v3's own patterns verbatim, `V3_PATTERNS` in `rules.ts`, and v3's `obfuscated` rule runs on the joined text and each decoded string as v3 ran it). Comments, regex bodies, TypeScript types, JSON, type declarations and every other kind of file are read as they are. Every match is confirmed and keeps v3's points.
- **Every file v3 reads, and every file v8 reads.** `analyze` walks the tarball as v8 did (install targets, entry points and every `exports` pattern, what those load, then every other file that could be code) and reads each file whole. Then `readLikeV3` walks it again as `test/v3/score.ts` did, with v3's order, entry points and byte budget, and reads whole any file the first walk did not. So no budget, no entry-point rule and no path apm resolves differently from v3 can leave out a file v3 read. (One file v8 reads stays out: a README or LICENSE that an `exports` pattern such as `"./*": "./*"` exposes and no parser accepts. Node throws a SyntaxError loading it, and v3 never read it, since v3 did not expand patterns.)
- **Nothing removes or downgrades a finding.** There are no exclusions and no gate: v8 left comments, regex bodies and erased types out while no `eval`, shell or computed-load signal stood in the package, and its review ran that text through `new Worker(code, { eval: true })` and used it as data (an environment variable's name, a path, a URL) with no evaluator at all. v9 deletes that logic, and the semantic proofs v7 used and v8 kept behind `PRECISION_PROOFS` are deleted too.

The parsed program's tree may only add to that floor:

- findings v3 lacks: escaped names (`f\u0065tch`, `"\u{63}hild_process"`), a `fetch` reached through a getter, code run through a constructor chain, calls inside evaluated strings, `new Worker(code, { eval: true })` (confirmed when `eval: true` is written, possible when the options are a value apm cannot read), an inspector session asked to `Runtime.evaluate` or `callFunctionOn` (confirmed), and computed loads in every file read, whether or not an entry point reaches it;
- `possible` findings, for what only the tree sees, such as loading `inspector`, whose sessions can run code;
- better citations: a call or load the tree confirmed is cited before a text match in code, and that before a text match in a comment, a regex, a type or a JSON file;
- the label wording (below).

What this buys, as a property: on any package, every signal v3 raises is raised, confirmed, with v3's points, and every file v3 cites for it is cited; so the score is at or below v3's. `test/superset.ts` checks exactly that, and every review fixture and every generated package is held to it. Two rules keep it unconditional. `analyze` refuses a file list in which a path appears twice (after dropping `.` and empty segments) or escapes the package folder, by throwing `AmbiguousPathsError`, the same rule (`ambiguousPaths`) the registry and `apm publish` apply before scoring; such a tarball extracts differently in different tools, so no score can speak for it. And a signal shows five evidence items and keeps 100 for dismissals, but when it has more it also keeps `sources`, every file (or, for evidence with no file and line, the part before the first ": ") its evidence cites, so the cap never drops a file v3 cites. The helper compares those sources too, on every signal.

**Where a text match sits.** The parse still says which matches sit in text the program does not run as written, and the evidence line names it, so a reader can weigh it: "(text match in a comment)", "(text match in a regex)", "(text match in a TypeScript type)", "(text match in a JSON file)". A text match elsewhere ends "(text match)". Comment ranges come from the parser, so every ECMAScript line terminator ends a line comment (LF, CR, U+2028 and U+2029, in hashbangs too), HTML-like comments are comments only in a script, and a regex right after `await` is a division in a script. A TypeScript file that is also valid JavaScript runs as JavaScript where nothing strips its types, so a match is said to sit in a type only when every program the file parses to puts it there.

**No silent limits.** Every bound on the tree's analysis keeps an unknown value for what it did not follow, and the bounds only limit what the tree adds; they cannot remove a text match. They are more than 6 values one expression can be, more than 32 `return` statements in one function, more than 8 `this.x = …` writes to one field in a constructor, more than 24 levels of nested values, more than 3 levels of code run from strings, 256 KB of decoded or evaluated text per file, and more than 32 steps following one value. Each one hit is named in the score's not-checked list with the files it was hit in.

The floor is tested as a property (`packages/core/test/floor-fuzz.test.ts`): generated packages wrap an inert payload in two or three shapes taken from all six reviews' fixtures, and each one's apm-score-v9 findings must include every apm-score-v3 finding (`supersetGaps` in `test/superset.ts`), with no exceptions. The v3 reference is `packages/core/test/v3/`, copied from commit `5437674`. The shapes are template tags, `Function` subclasses and constructor chains, generators, Symbol keys, bind/apply/call/Reflect, Proxies, getters, TypeScript namespaces, logical, ternary and comma callees, shadowing decoys, `with`, exports wildcards, comments ended by every line terminator, HTML comments, JSX text, padding past the parse limit and token-window boundaries, a replaced `fetch`, a patched `Error.prototype` or `Object.prototype`, keys read back with `Object.keys`, completion values and strings round-tripped through `String`, `JSON` and URI encoding; the v7 review's seven families (conversion hooks, `with` writes, default-parameter closures, reflected names and keys, a binding named `eval`, a custom `fetch` handed a `data:` URL, a builtin replaced from a file with no tree); and the v8 review's: text in a comment or a regex body run by `eval` or by `new Worker(…, { eval: true })` (written in place, destructured, or with its options in a constant), text in a comment, a regex body or a TypeScript type used as data, and the program in a file no entry reaches beside a computed load. Each shape is also run once in a `node:vm` context against recording stubs, so a shape that stops running its payload fails the test. CI runs 300 composed cases on a fixed seed, every shape alone in each language it is valid in, and all 296 stored fixtures of the six reviews. `APM_FUZZ_CASES=10000 APM_FUZZ_SEED=random` runs the long mode.

### JavaScript and TypeScript are parsed

Since **apm-score-v5**, JavaScript and TypeScript files are parsed, not lexed by hand (`packages/core/src/parse.ts` and `js.ts`):

- **JavaScript and JSX**: [acorn](https://github.com/acornjs/acorn) 8.19 with [acorn-jsx](https://github.com/acornjs/acorn-jsx). Each file is parsed as a script first (CommonJS, with `return` allowed at the top, and the HTML-like `<!--` and `-->` comments old browser scripts have), then as a module, then, for a `.js` file, with JSX. `.jsx` files are parsed with JSX.
- **TypeScript and TSX**: [Babel's parser](https://babeljs.io/docs/babel-parser) 8.0 with its `typescript` and `estree` plugins, as a module, then as a script, with TypeScript's legacy decorators (`experimentalDecorators`, parameter decorators) and then the standard ones (`export @dec class`). Both parsers give the same ESTree nodes with source offsets, so one reader reads both.
- **JavaScript acorn rejects** (decorators, which acorn does not parse) is offered to Babel with JSX and the same two decorator dialects, up to 1 MB. Flow is not enabled: its type annotations would read as code.

Two things parse under both goals but mean different code. An HTML-like comment hides the rest of its line in a script but is code in a module (`x <!-- y` is `x < !(--y)`), and `await` is a name in a script (`await (f)(x)` calls `await`) but an operator in a module (it calls `f`). A script that holds either is parsed as a module too, and both programs are read: node runs `.mjs` and `"type": "module"` files as modules.

Comments, strings, regex literals, template text and JSX text are whatever the parser says they are, so every ECMAScript line terminator ends a comment (CR, U+2028 and U+2029 as well as LF, in hashbangs too), `1. / x / 1` is a division, `of` and `await` are names where they are names, and `// {require(x)}` inside a JSX element is text holding an expression. TypeScript types (annotations, interfaces, `import type`, `type X = import('net').Socket`, `declare` blocks) are erased before anything runs and are not read (the floor section above lists exactly which); `import('node:http')` in a `.js` file is code whatever follows it.

**No tree is not a pass.** A file no goal accepts (invalid syntax, or Flow), or one a parser stopped on at one of its own limits, is read two ways (`scanUnparsed` in `source.ts`). The limits are a tree that would not fit in a Worker (more than 480,000 tokens of JavaScript, about 45 MB of tree, as acorn takes 90 to 95 bytes a token in V8; or more than 1 MB of TypeScript) and nesting deep enough to exhaust the stack, in acorn, Babel or the reader. V8 throws a `RangeError` for a stack that runs out, which used to read as a syntax error or as a file read raw:

- **Raw, as apm-score-v3 read every file**: v3's rules over the whole text as written, however large, every match counted, comments and strings included, and nothing taken for a definition or a type. The alias patterns (`x.fetch(…)`, `= globalThis.Function`, `XMLHttpRequest`, `= require`) confirm too, as they did in v3, so a file can never score higher for losing its tree than v3 scored it. Every detection fixture of the reviews is tested that way behind a 1 MB comment.
- **Token by token**: acorn's tokenizer streams tokens without building a tree, so its memory stays flat at any size. Each token is written back in plain form (`requ\u0069re` as `require`, `'ch\u{69}ld_process'` as `'child_process'`), what lies between two tokens as blanks, and a gap longer than 64 characters (a long comment, a run of blank lines) as one character, a line break if it held one; a map takes every position back to the file, so citations point at the file as written. The same rules read the result in windows of about 4 MB (`tokenWindows`). A window ends just after a `;` that ends a statement, outside every `(`, `[` and `${`, so never inside a `for` header or a function passed as an argument; in a file with no such `;` within a further 256 KB (a semicolonless file, one long array) it ends after the next token, so no window grows much past its size. No token is ever split, gaps are short, and each window reaches 64 KB back, so a call and its arguments are always read together. That undoes what only a tokenizer sees through: escaped names, braced escapes and comments between joined pieces. A character the tokenizer cannot read (a decorator's `@`) is kept and reading resumes after it. This pass only adds: it adds signals the raw pass did not confirm.

Both readings' findings count, but only for a file node would reject too do they stand for the whole reading. A file a parser stopped on at a limit is valid code apm did not read as a tree: no flow was followed in it, so the raw findings are extra evidence, never a full analysis, and the file makes the analysis `incomplete` ("index.js:1: … the file is too large for apm to read as a tree …, so where its values go was not followed"). The review of 9913a74 put 240,001 inert `0;` statements in front of an environment upload that scores 36: the raw reading found nothing, and it scored 100 (65 with a postinstall). It is now `incomplete`, 39 (4 with the postinstall). apm-score-v9, live then, scores the same payload 65 unpadded and 90 padded (75 with the postinstall). `packages/core/test/v10-r5.test.ts` holds these cases, the TypeScript size cap, nesting 5,000 and 100,000 levels deep, and code run from a string that is too deep; the v7 review's six padded `unparsed-builtin` fixtures went from 62 to 1. A file node runs because code `require`s or `import`s it, or because it is an entry point, is parsed as JavaScript whatever its extension (node runs `require('./x.c')` as JavaScript), so C-style comment rules cannot hide code in it. In the 70 tarballs below, 3 JavaScript files have no tree, all for size, and each makes its package `incomplete`: `sass.dart.js` (5.7 MB, 1,067,000 tokens), next's bundled webpack (2.5 MB) and a three.js Draco decoder (0.7 MB of asm.js, 494,619 tokens) that three's `./examples/jsm/*` export exposes.

C-family, C# and Python files, install commands and shell scripts are read raw, as v3 read them: a hand-written lexer is not a parse, and an install script can run any of them, so their comments and strings count (`a || sh` in C++ counts as a pipe, as it did in v3). JSON files and type declarations (`.d.ts`) nothing loads are data: what they name is possible at most, and they load nothing.

### What the code does, read from the tree

This is what the tree adds to the text rules and how it picks citations. None of it removes or weakens a text match (since apm-score-v8, and by construction since v9): where the tree reads something as harmless (a definition, a string that only reaches a comparison, a Promise called as a function, a comment), the text rules still count what v3 counted there.

- **Calls are calls.** A function or method *definition* named `fetch` or `exec` is not a call to the tree (the text rules still count its name), and nothing in a comment or string can make a call look like one. Optional calls (`require?.('x')`, `globalThis.fetch?.(u)`), escaped identifiers (`requ\u0069re`, `f\u0065tch`), `f.call(that, …)`, `f.apply(that, […])`, `Reflect.apply` and `Reflect.construct` are calls to `f`.
- **Names are followed, by scope.** Since **apm-score-v6** every name is resolved to the binding that covers it: `var` and parameters belong to their function, `let`, `const`, classes and functions declared in a block to the block, a TypeScript namespace to its body. A `const fetch` inside an unused function does not hide the global `fetch` the file calls, an ambient `declare` or a type's parameter declares nothing, and a name read inside a `with` body is taken for the global (it may be a property of the `with` object). A name with one declaration in its scope and never reassigned resolves to what it holds: `const cp = require('child_process'); cp.exec(…)`, `const { execSync } = require('node:child_process')`, `import { spawn } from 'child_process'`, `const Fn = globalThis.Function; Fn('…')()`, `const read = require('fs').readFileSync; read('.npmrc')`, `const fetch = globalThis.fetch`, `const r = createRequire(import.meta.url)`, `const { ['fe' + 'tch']: send } = globalThis`, `const { run = eval } = {}`, `const [send] = [fetch]`, a parameter's default (`function f(go = eval)`). A name declared twice in one scope, or assigned after it is declared, is read by its name only. Constants work as module targets: `const cfWorkers = "cloudflare:workers"; import(cfWorkers)` loads `cloudflare:workers` and is not a dynamic load.
- **Every operand that can be the callee.** `(a || b)(x)`, `(a && b)(x)`, `(a ?? b)(x)` and `(c ? a : b)(x)` are read as a call to each operand that can be the value: the one apm can tell is chosen when the test is a literal (`(null || eval)` is `eval`, `(true ? fetch : f)` is `fetch`), both when it cannot. Each argument takes the strongest role any of them gives it. `(0, eval)` and other comma expressions are their last operand.
- **Members of values the file makes.** An object literal's property, getter (`{ get run() { return eval } }`), spread (`{ ...globalThis }`) and `__proto__`; an array's element; a class's static members and, on `new C()`, its methods, getters, fields and `this.x = …` in its constructor; every member of a Proxy whose `get` trap returns something apm can read; a member of `Object.create(proto)`; and later writes to the object (`obj.fetch = globalThis.fetch`, `Object.assign(obj, globalThis)`, `Reflect.set`, `Object.defineProperty(obj, 'run', { get: () => eval })`, `Object.setPrototypeOf`). A getter that returns the value directly is that value, so `obj.run(code)` is `eval(code)`; one apm cannot read, or a write under a key it cannot work out, is read by the property's name (possible at most). Calling a function the file defines gives what its own `return` statements give (`const get = () => eval; get()(code)`), and `Function('return this')()` and `Reflect.get(globalThis, 'fetch')` are the global object and its `fetch`.
- **Promises and generators.** Calling what an async function or a generator returns calls a Promise or a generator object, which throws: the tree confirms neither what the function returns nor what it is handed (the text rules still count both). Awaiting the call gives what the function returns.
- **Evaluators.** `eval`, `(0, eval)`, `globalThis.eval`, `Function` and `new Function` (called directly, parenthesized, through an alias or a constructor chain such as `[].constructor.constructor` or `(async () => {}).constructor`), string `setTimeout`/`setInterval`/`setImmediate`, `vm.runInThisContext`/`runInNewContext`/`runInContext`/`compileFunction`/`Script` and `module._compile`. What they are given is read as code: a literal, a template, pieces joined with `+`, a constant, or a payload decoded with `atob` or `Buffer.from` is parsed and read like the file, so `(Function)(\`fetch(u)\`)()` confirms both `eval` and `network`. Up to three levels of code running code are followed. `Function('return this')` finds the global object and is not eval. `eval` handed on as a value (`run(eval, code)`, `{ go: eval }`) is a possible eval, and the call it is handed to has its other string arguments read as code.
- **Arguments keep their positions** through `f.call(that, a)`, `f.apply(that, list)`, `Reflect.apply(f, that, list)`, `Reflect.construct(F, list)`, `f.bind(that, a)(b)` (bound arguments first, also through a constant holding the bound function) and spreads (`eval(...args)`), where `list` and `args` are array literals or constants holding one. Holes keep their place, so the tree reads `eval.apply(null, [, code])` as passing `undefined` (the text rules still count what `code` names). Past a spread apm cannot read, positions are unknown and the remaining arguments are read as plain values.
- **Module loaders.** `require`, `import()`, `import`/`export … from`, `import x = require()`, `module.require`, `require.main.require`, `process.getBuiltinModule`, `Module._load`, `createRequire(…)`, and a `require` passed in as a parameter (bundles and module wrappers pass it that way).

### What a string is for

A string's **role** comes from where the code uses it, and decides what the tree confirms from it. The text rules also count every string as v3 did, whatever its role, so a role only adds: it confirms what v3's rules could not see (an escaped or decoded name, code run from a string) and picks the citation.

| Role | Where | Confirms |
| --- | --- | --- |
| Module specifier | `require('x')`, `import`, `from 'x'` | the module load: `child_process` is `shell-exec`, `http`/`net`/`ws`/`axios` and `import('https://…')` are `network`, `vm` is `eval` |
| Code | passed to eval, Function, vm or a string timer | whatever the code does, read as code |
| Command | passed to `exec`, `spawn`, `execFile`, `fork`, `execa`, `Bun.spawn`, `` Bun.$`…` ``, `` $`…` `` | shell text (`curl …`, `\| sh`, `wget`, `powershell`), download commands and credential paths in it |
| Path read | passed to `readFile`, `readFileSync`, `createReadStream`, `open`, `copyFile`, `Bun.file`, `Deno.readTextFile`, also through `path.join(os.homedir(), '.npmrc')` | a credential path in it |
| Request | a URL or body passed to `fetch`, `http.request`, `WebSocket`, `sendBeacon`, `dns.lookup` | the request itself (the text rules still count shell text or a token name in it) |
| Plain | anywhere else | nothing beyond what the text rules count |

Decoded content takes the role of the place it is used: `eval(atob('…'))` runs what the base64 holds, so what it does is confirmed. Shell text in a URL (`fetch('https://x/curl … | sh')`), `.npmrc` in a path that is only built (`path.join('.npmrc')`), `readFileSync('child_process')` (a file name, not a module) and a token name in a request body were possible from apm-score-v5 to v7; each rested on the callee being the builtin, so since v8 they are confirmed, as v3 had them.

### Evidence cites the occurrence that matched

Every finding carries the source position of the node it came from, through every transformation: a joined string is cited where its first piece is, a decoded payload where the decoder is called, and code read from a string where the string is. A comment or an earlier string with the same text cannot take the citation. (Text read raw keeps an edit map through the joining pass for the same reason.) In each file a call is cited before a reference, a reference before a module load, and a load before a string, so `vm.runInNewContext(…)` is cited rather than the `import vm from 'node:vm'` above it. A citation from a test file the package ships (under `test/`, `tests/`, `__tests__/` or `spec/`, or named `*.test.*` or `*.spec.*`) says `(in a test file)`, and a signal lists the package's own files before its tests.

### Confirmed and possible

Every code signal carries `confidence`. **Confirmed**: apm saw the code do it or load the module that does, or v3's text rules matched it anywhere in a file apm read; such a line ends "(text match)", or names where it sits ("(text match in a comment)", "… in a regex", "… in a TypeScript type", "… in a JSON file"). **Possible**: only the tree saw it (a braced escape such as `"\u{63}hild_process"`, `eval` returned from an async function, a loaded `inspector`, a Worker whose options apm cannot read) and v3's rules found nothing of that signal. A possible signal is labelled as one ("Possible shell use: …"), costs about a third of the points, and lists only possible evidence, each line saying why it is not confirmed. One confirmed finding makes the whole signal confirmed, and then only confirmed evidence is shown.

**Labels say what was found.** A confirmed code signal whose every piece of evidence is a text match (no call or load the parsed program showed) is labelled by what the text is, not by what code would do: "Mentions a credential file (.npmrc, .ssh) or secret variable; apm did not see one read" in place of "Reads credential files or secret environment variables", "Mentions a shell command or child_process; apm did not see one started" in place of "Starts shell commands". The points are v3's. The version page, the approval page and `apm score` show the label as it is, with each evidence line saying where its match sits; the phone's one-line summary takes the label up to its first explanation ("Mentions a credential file"). One call or load the tree confirmed gives the signal its usual label, and that call is cited first.

### Dismissed evidence

Some confirmed evidence is false, and no sound rule tells it apart: vite 8.3.8 is refused at 30 for `.npmrc` in `server.fs.deny`'s defaults and for WebAssembly in base64 counted as obfuscation. That is fixed by a person's decision about that exact content, not a looser rule. One of apm's reviewers (`APM_ADMINS`), signed in on the website and confirming with a fresh authenticator code or passkey (CLI and CI tokens are refused), can dismiss one evidence item. An item is named by the scorer version, the package, the version, the tarball digest, the signal, the file and the line (`packages/registry/src/evidence.ts`, table `evidence_dismissals`). Only code signals (`shell-exec`, `network`, `credential-access`, `eval`, `obfuscated`) can be dismissed; facts such as an install script cannot.

- Each dismissal records its reason and who made it, and goes into the package's public log (`evidence-dismissed`) in the same transaction. An undo needs its own reason; it is recorded the same way (`evidence-restored`, with the undo's reason and the dismissal's) and brings the item and its points back. A code or passkey check confirms one item with one reason.
- The score is recomputed without the item wherever a score is read: the version page, the package page, the packument's `_apmScore`, `~safe` and `apm add`. A signal keeps whatever evidence is left (each signal keeps up to 100 items for this, not only the five shown), falls back to its possible evidence when every confirmed item is dismissed, and goes when nothing is left (`applyDismissals` in `score.ts`). An item of that possible evidence can be dismissed too; it is listed with the rest and can be undone.
- A dismissal applies only to the bytes and scorer it names: another version, a different digest or a new scorer version reads the item afresh.
- The version page keeps the item, struck through, with "Dismissed by an apm reviewer: <reason>" and the date. Anyone can ask for a dismissal with the "Appeal a score" issue form.

## What the score does not catch

Known and left on purpose, each with what it would take:

- **One named token sent by policy.** `fetch(url, { headers: { authorization: process.env.NPM_TOKEN } })` is what every registry client does, and a stealer that sends one token looks the same. So does a CLI that reads `~/.npmrc` and sends the `_authToken` entry for one registry: `credential-read` costs 30, the send nothing. Caught: the whole environment, a credential file's whole contents (or a line of it taken by index), three families of tokens in one request.
- **WebAssembly internals.** A module's bytes are never read; a value a WebAssembly import receives is followed only on the JavaScript side (`wasm-env` in the review probes is caught because the upload is in JavaScript).
- **Payloads in dependencies.** A package that hands `process.env` and the home directory to a dependency (naniod), or only declares one, has no payload of its own; `risky-dependency` catches it once the dependency is scored. `tools/score-eval` reports these samples apart ("no payload in this tarball").
- **Typosquats with no visible payload.** `typosquat` costs 20; a squat that ships a copy of the real package passes at 80.
- **Destructive code that does not steal or download.** Deleting files, wiping a disk or corrupting a build with nothing sent or fetched uses only capabilities, so it costs nothing outside install time (install time still costs `install-shell` and the rest).
- **A downloaded field in a command.** `exec('npm view pkg@' + json.version)` is a value in a command: nothing. The whole downloaded body in a command is a possible `remote-shell` (-50), not a confirmed one, so it refuses at install and costs 50 otherwise.
- **Example text near a network call.** A package that exports example code is not a confirmed flow, but the text rule still sees an environment dump (or three token families) beside `fetch(` in the file, which costs `exfiltration` at its table weight (-35): 62. The same holds for an SDK config that reads three token families and sends one.
- **Containers and events apm does not see filled.** An object filled in by a function it is passed to (`fill(o)`), events a class emits on itself (`this.emit`), and a write to a file whose path apm cannot work out are not followed.
- **The install-time catch-all.** A rule that refuses any install-time file with a network read and any dynamic exec, require or eval would refuse esbuild (an install script that downloads its binary from the npm registry and runs it with `--version`), so there is none: each class the third review named has a precise flow instead.

The list below is also in the `notChecked` list every score carries, in short.

- **Malicious code that only uses capabilities** (apm-score-v10). Code that runs on `require` and does only what an SDK does (reads a key, sends a request) costs nothing, wherever it sends it: the score cannot tell an API host from an attacker's. It is listed under capabilities, with its evidence, and the AI release review reads it. Install-time code, collected secrets, request bins, remote shells and obfuscation still cost points.
- **Network hosts against a declaration.** A declared network list is shown, not compared with the URLs in the code.
- **A call inside a string that runs, in a file with no tree.** `runs-decoded-code` needs the parse to see that a string is run; a file too large to parse keeps every v3 finding, but not that one.

- **Runtime behaviour.** Code that downloads, decrypts or assembles a second stage while running looks like whatever its loader looks like. A loader still needs `fetch`, `eval`, `vm` or `child_process`, so it usually scores low, but the score cannot say what the second stage does.
- **Other encodings.** XOR, compression, a custom alphabet, or base64 that decodes to more base64. Only base64, hex, `\x` escapes, char codes and joined string literals are undone.
- **Names built any other way**: values read from a file at runtime, a decoder longer or less pure than `decode.ts` runs, or a value passed through a function apm does not follow. Constants are followed (literals, joins, templates, `[…].join('')`, `'…'.split('').reverse().join('')`, an element of a constant array by a known index, a one-element array key, base64, hex, char codes, URI escapes and small decoder functions), but only within one file and only for names declared once and never reassigned.
- **Files only a computed path loads.** Docs, type, JSON, style and markup files are read only when code reaches them by a path apm can resolve. Node runs any required file as JavaScript, so `require(name)` pointing at `docs/notes.md` would run code apm did not read; that call shows up as `dynamic-require` with no points.
- **Files with no tree.** A file no parser accepts is read raw and token by token. Every file's text counts anyway; what such a file loses is what a tree would add (scopes, getters, argument positions, flows, Worker and inspector calls) and the "in a comment" notes. Flow-typed JavaScript is one such case. A file too large or too deep to hold as a tree is read the same way and makes the analysis `incomplete`: apm cannot vouch for a file it could not follow, so large single-file bundles (sass, a three.js decoder) score below the floor until apm can read them another way.
- **Values that cross a function boundary, read by the tree.** A parameter is read by its name: `function run(f, c) { f(c) }` cannot tell that `f` is `eval`. Writes to an object through another name (`const h = g; h.fetch = …`), through a function it is passed to, or into `this` outside a constructor are not seen, and a getter or Proxy trap that computes what it returns is read by the property's name. None of this lowers a score below the floor: what the tree cannot follow it cannot prove harmless, so the text in the file counts as apm-score-v3 counted it. It means the tree adds nothing there, and that a call v3's rules do not match (`run(f, c)` with `f` an alias of eval and `c` built at runtime) is not seen. A method on an object apm cannot identify (`config.fetch(…)`, `this.fetch(…)`) counts as v3 counted it, confirmed.
- **Text that becomes code at runtime, as text.** Every comment, regex body, type and JSON file counts, so `String(fn)`, `re.source` or a file reading its own source cannot bring back text apm left out: nothing is left out. What the score cannot do is tell a comment that is only a comment from one that is read back and run; both count, and the evidence says "(text match in a comment)" so a reader, or a reviewer dismissing it, can tell. Text that is not in the tarball (written to a file at runtime, fetched) is the runtime-behaviour case above.
- **Native code and WebAssembly.** Listed as `binary` (native) or skipped (WebAssembly), never read.
- **A popular name under another scope.** `@someone/react` is not a typosquat: scopes exist so names can be reused, and `@sentry/react` and `@types/node` are real.
- **Dependencies' code.** Each dependency has its own score; `risky-dependency` and the resolve tree walk use them. Git, URL and file dependencies cannot be scored and are listed by name.
- **The publisher's machine or CI.** A compromised build that publishes clean-looking code with a subtle backdoor scores well.
