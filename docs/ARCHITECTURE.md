# Architecture

apm runs on Cloudflare: two Workers, one Postgres on Neon, one R2 bucket and one queue, declared together in an Alchemy stack. This page says what each part does, how a request moves through the registry, and why it is built this way.

## The parts

```
 npm, bun, pnpm, apm CLI ──────────────▶ registry Worker  (registry.apmjs.dev)
                                            │  Effect program over request-scoped services
 browser ──▶ website Worker (apmjs.dev)     ├─ Store ────▶ Hyperdrive ──▶ Neon Postgres 18
             Next.js via OpenNext ──────────┤                         (packages, versions, accounts,
             REGISTRY service binding       │                          Better Auth, second-factor ledger)
                                            ├─ Blobs ────▶ R2 bucket (tarballs by sha512)
                                            ├─ Upstream ─▶ registry.npmjs.org
                                            ├─ Analysis ─▶ analysis queue ──▶ same Worker's queue()
                                            ├─ Review ◀── apps/reviewer (pulls AI review jobs over HTTPS)
                                            └─ cron every 10 min: write down matured revokes, expire staged versions
```

| Package | What it is |
| --- | --- |
| `packages/core` | The score engine, tarball reader, name and dependency parsers. Plain TypeScript, no I/O. |
| `packages/registry` | The registry Worker. `src/worker.ts` is the entry; `scripts/build.ts` bundles it. |
| `packages/infra` | The Alchemy stack (`alchemy.run.ts`), the deploy script and the smoke check. |
| `apps/web` | The website: Next.js 16 with shadcn, built with OpenNext and deployed as a Worker. |
| `packages/cli`, `packages/bun-scanner` | The `apm` CLI and the Bun security scanner. They talk HTTP to the registry. |

## A registry request

1. `worker.ts` parses the Worker's environment with a zod schema (bindings, vars, secrets). A misconfigured Worker answers 500 and logs why; legacy password auth on a public https URL without `APM_ALLOW_LEGACY_IN_PROD` answers 503 to every request.
2. It builds the request's services as Effect layers (`servicesFor`) and runs `router.ts`.
3. The router picks a route module: `review.ts` (the AI review queue and views, when it is on), `account.ts` (sign-in, device login, confirmations, staged approvals), `files.ts` (one file of a version as text, for the website's file view), `apm.ts` (scores, resolve, scan, audit, yank and revoke, the upstream proxy), and `server.ts` (the npm protocol: packuments, tarballs, publish, dist-tags, search).
4. A route returns a `Response` or fails with a typed error. `HttpFailure` becomes its JSON error body; `StoreError`, `BlobError`, `AuthError` and `QueueError` become a 500 and one structured log line with the operation that failed.

The layers live for one request. `Store` opens one Postgres connection through Hyperdrive and closes it when the request ends; Hyperdrive pools the connections to Neon. Better Auth is built on first use, so routes that never touch sign-in never pay for it; its code (with the passkey, WebAuthn and pg libraries and Better Auth's password hashing) is `auth-engine.ts`, a chunk of its own that a request loads the first time it needs it. It is about half the Worker's code: an isolate Cloudflare starts for a burst of npm's requests waits for its whole entry module before the first answer (up to 450 ms in production, outside both the invocation's wall time and Server-Timing), and with the chunk apart the entry is 1.3 MB instead of 2.7 MB and evaluates in about 61 ms instead of 110 in Node.

### Services

| Service | File | Job |
| --- | --- | --- |
| `Store` | `db.ts` | Every table, through `@effect/sql-pg`. Rows are parsed with zod schemas at this boundary. Includes the second-factor ledger. |
| `Blobs` | `blobs.ts` | Tarball bytes in R2, keyed `sha512/<hex>`. A staged tarball that gets approved keeps its object; identical bytes share one. |
| `Upstream` | `upstream.ts` | Reads npm: packuments, search, scope checks, advisories, and tarballs fetched only from the upstream's origin and verified against the published checksum: for a download, passed to the client as they arrive (below, "Serving an upstream tarball"); for an analysis or the file view, held, verified and cached in R2. A tarball over the 32 MiB download cap is not downloaded for analysis, but is still served: streamed to the client as it arrives (`verified-stream.ts`), never held, cached or charged to the memory pool. Answers are kept for `APM_UPSTREAM_TTL_MS` in the isolate, and packuments also in the Workers Cache API so other isolates in the data center reuse them. |
| `Analysis` | `analysis.ts` | Scores upstream versions on the queue, every cache miss alike (no request analyses inline); requeues runs the platform stopped. A tarball too large to hold is read as a stream (`streamed-analysis.ts`). |
| `Auth` | `auth.ts` | Better Auth (GitHub, Vercel, TOTP, passkeys, device flow) on the same Postgres, with apm's own route allow-list and second-factor checks. |
| `Clock` | `clock.ts` | The registry's time (`now`) and the wall clock codes are checked against (`wallNow`). |
| `RegistryConfig` | `config.ts` | Public URLs, the upstream, the name policy and legacy auth. |
| `ReviewConfig` | `review.ts` | Present only when `APM_REVIEW_TOKEN_HASH` is set: the AI review's service token hash, admins and limits. Its routes and hooks do nothing without it. |
| `Blocklist` | `blocklist.ts` | What the install routes refuse while Postgres is down, in R2 (see [When Postgres is down](#when-postgres-is-down)). |
| `ReleaseHooks` | `hooks.ts` | Listeners for "a version went live" and "an upstream packument was fetched". `worker.ts` wires the AI review queue to them. |

### Data

The schema is SQL in `packages/registry/migrations`, applied in order by `scripts/migrate.ts` and recorded in `apm_migrations`. Times are milliseconds in `bigint` columns; manifests, scores and dist-tags are `jsonb`. Better Auth's tables come from its own generator (`0002_better_auth.sql`).

Publishing is one transaction that creates or locks the package row, rechecks ownership, writes the tarball to R2, inserts the version (the primary key decides a race: the loser gets 409 and its blob is dropped when nothing else uses it), moves dist-tags and logs the event. Approving a staged version decides the staged row and commits the version in the same transaction. A staged upload is inserted in one transaction that takes an advisory lock, rechecks that nothing waits for the same name@version and that the per-account and per-package quotas still allow it; the byte quota counts the tarball plus the manifest, readme and score the row keeps. A rejected or expired upload keeps only its audit fields. Uploads and cleanup share each blob key's advisory lock: an upload holds it shared from writing the object to inserting the row that points at it, and deleting an unused blob holds it exclusively while it checks for references, so an expiry sweep never deletes the object a re-upload of the same bytes just wrote. Every change to an existing package (yank, revoke, restore, dist-tags, deprecation, owners, incident response) takes the package row lock first and checks ownership under it, so an owner removed while a change waits cannot finish it. Wrong passwords are counted with one upsert before the hash check, so concurrent guesses all count. Per-user answers get `Cache-Control: private, no-store` and `Vary: Authorization, Cookie` in `worker.ts`, whichever route made them. The package page's reads (package, score, review, readme and file answers) carry `Server-Timing` (`timing.ts`): every answer is bound by round trips to Postgres, so each says how long its queries took. The header goes only to a request whose `x-apm-debug` header is the stage's debug token (`APM_DEBUG_TOKEN_HASH`, docs/DEPLOY.md); anyone else gets none, because even the database's time against the total shows whether npm's answer was cached, which tells what others asked for. A lookup reads only what its answer needs: the existence check (`HEAD`) and the review answer read npm's listing without apm's scores, an upstream package's analyses and dismissals come back in one query, and the review answer reads the stored review and its job in one. The package, score, versions and review answers start from one statement (`Store.pageRead`): the package row, then a local package's versions, dismissals and owners, or an upstream package's kept summary and (except for the review answer) its analyses, dismissals and unscorable versions. Production's Workers reach Neon in about 75 ms a round trip, and the package answer used to wait on four in a row; it now waits on one, plus npm's version document when the isolate does not hold it (the summary's own check, below). One statement is one snapshot, and it runs after the request began, so a revoke, a score or a dismissal committed before the request is in it, as before.

### Version states

`lifecycle.ts` holds the transitions between `active`, `yanked`, `revoke-pending` and `revoked` as one pure function, so every route agrees on what a yank, unyank, revoke, second-owner confirmation and restore may do. A pending revoke becomes final 24 hours after it started. Reads apply that rule themselves (`effectiveStatus`), so a matured revoke is a 410 the moment its window closes; the cron writes it down and logs the event later. Staged versions expire the same way. This keeps the test clock authoritative and costs no extra write on install traffic. XState would add a runtime for six states and no timer it could own, so it isn't used.

### When Postgres is down

Agents install through the registry by default, so an outage of Neon or Hyperdrive must not stop installs of npm's packages, and must not make the registry answer anything it cannot check. Four parts do that.

**Bounded waits** (`db-health.ts`). Connecting waits at most 3 s and each statement 8 s, for the Store, the AI review's own statements and Better Auth's pool. Transactions are bounded by the connection itself (a socket that gets no byte back within 9 s of a write destroys itself, which is what bounds BEGIN, COMMIT and ROLLBACK) and by a 60 s backstop: a transaction still running then (a publish's long R2 upload, say) is ended by closing its connection and fails as an ordinary store error. A statement or transaction the guard gives up on is stopped in the background, so nothing waits on its cancel. Every failure that says the database is not there is the request's own: a connection error the driver reports (refused, reset, DNS, TLS, closed by the server), an authentication failure, a server shutting down or out of connections, a network error code such as `ETIMEDOUT` anywhere in its causes, a stall kill, a statement past its 8 s, or one of the request's connections closing under it (`meansUnreachable`, `RequestConnections`). That request takes the database as unavailable: its connections are closed, its later statements fail at once without trying, its install routes answer from the degraded route and its other routes 503. An SQL error on a database that answers stays an ordinary store error (a 500). Nothing is remembered between requests: the next request tries the database again, and the health check reports the database from a check of its own each time. Until 2026-11-16 a failure opened an isolate-wide breaker for 15 s. It took a Postgres that was answering as down whenever a resolve kept an isolate's CPU busy for 7 to 16 s, because Workers' clocks do not move while code runs and a busy isolate leaves an answer unread exactly as a silent database does, and every request that isolate served then answered 503 or degraded. What dropping it costs: in an outage every request pays its own attempt, up to its bound, and none answers in milliseconds. A database that refuses connections costs each request its connect attempt (at most 3 s; a refusal is usually immediate). One that accepts connections and never answers costs each request its connect timeout (3 s) or, once connected, its statement timeout (8 s), before the degraded answer, and each opens one connection to Hyperdrive; no request opens more than its own. Every connection, TLS included, goes through the guard's own socket, so the guard can close any of them: with TLS the driver wraps that socket as it would wrap its own, and the stall timer sees only the bytes before TLS takes it over, so a TLS connection is ended by the statement and transaction deadlines. The rollback tools' read of the migration ledger is one query on a connection of its own with one deadline for all of it; at the deadline the connection is destroyed and nothing waits for it (`queryOnce`).

**The block list** (`blocklist.ts`). What the install routes must refuse is kept in R2 as one object, `state/install-blocklist.json`: every package published on apm, and every version an apm reviewer confirmed malicious, by tarball digest. It is never less strict than the database: a first publish (`commitVersion`) and a confirmed review add their entry before their transaction commits, and the write fails, changing nothing, when the add fails. Adding an entry that is already there asserts it again and renews its time, so a review confirmed again after a dismissal is not aged out by a sync that read the dismissed state. Nothing in a request removes an entry. The cron rewrites the list from the database every 10 minutes, keeping what the database holds plus entries asserted in the last 15 minutes (a block whose transaction may still be committing), so a dismissed review or a publish that rolled back stays blocked until then. Every write is a read-modify-write conditional on what it read: the object's ETag, or, when there was no object, R2's create-only `If-None-Match: *`, so two writers that both found it missing cannot overwrite each other (`blocklist-race.test.ts` runs these races on workerd's R2). R2 was chosen over Workers KV because R2 reads see the last write everywhere; KV can serve a stale copy for up to a minute. Until the cron has synced the list once, it says so (`syncedAt` is null) and outage answers refuse every install.

**Degraded install routes** (`degraded.ts`). When a packument, tarball or ping request fails because the database cannot be reached (never for a statement that failed on a database that answers: that is a 500, as before), `worker.ts` answers it again without the database: npm's packument and tarballs come through `Upstream` as usual, a version on the block list is left out of the packument and its tarball answers 410, a version the OSSF malicious-packages feed lists (`osv.ts`, which needs no database) is left out and its tarball answers 403, and the answer carries `x-apm-degraded: database-unavailable`. Scores live in the database, so packuments carry none: they say `x-apm-scores: unknown` and `_apmDegraded: { reason, scores: "unknown", blocklistSyncedAt }`. Nothing is queued for analysis. What is refused, with a 503, `Retry-After: 30` and a sentence that says why:

- packages published on apm: their versions, owners and states live only in Postgres, so the registry refuses them rather than answer from npm under the same name;
- the `~safe` view, which filters by score;
- every other route that needs the database (resolve, scan, the package page, sign-in, publish, yank and revoke), as `{ error, degraded: true, reason: "database-unavailable" }` rather than "Internal error";
- everything, when the block list cannot be read or has never been synced.

Revoked, revoke-pending and yanked versions exist only on packages published here, which are refused whole, so none of them is served in an outage. `tests/acceptance/outage.test.ts` runs the Worker in workerd with real npm upstream and its database behind a link the test cuts, both as a database that refuses connections and one that accepts them and never answers: npm and bun install `ms@2.1.3`, a version on the block list is refused, the apm package answers 503, and the health check reports it.

**Health** (`health.ts`). `GET /-/apm/v1/health` reports whether Postgres, R2, the block list, the analysis queue and npm answer. It reads and parses the block list the way the degraded routes do, so it calls the list ready only when they would use it, and it never reports installs working while R2 does not answer (tarballs are read through R2). See docs/DEPLOY.md, "Health checks".

### Scoring npm packages

The score endpoint, `~safe`, resolve and scan need a score now. No request analyses anything, signed in or not: a version with no stored analysis is queued and reads as "not scored yet" (`~safe` hides it, and the website's queued notice refreshes the page until the score is there). A look at an upstream package also wants each version a dist-tag names and each published in the last week that has no result yet, newest first and at most eight (`versionsToSeed`): a prerelease line such as typescript's nightly `next` is never `latest`, and before 18 Nov 2026 nothing queued it until someone asked for that exact version. The page answer hands those to `seeding.ts` and returns: they are claimed and sent after the response, in its waitUntil, on services of their own, aborted at 5 s, at most two at a time in an isolate and each package once per ten minutes there, and the claim takes nothing once the queue took 60 jobs from any caller in the last ten minutes (`SEED_INTAKE_MAX`): admissions queue on an advisory lock, count under a fresh snapshot and claim only the room left, so concurrent seeds never pass the quota between them, and a crawler's page views add no work past it. A user's own ask never takes that lock. The cron is the path that does not depend on those bounds: each sweep picks up to 12 packages someone looked at in the last day (`kept_packages`), seeded longest ago first (`seeded_at`, migration 0024), and queues their versions with no result yet, 24 in all; the cron's popular-scores refresh queues the same versions of the packages the home page asks about. A sweep's background work is bounded: at most 48 jobs a sweep (`enqueueBackground`, `BACKGROUND_PER_SWEEP`), about a minute of a queue that runs one analysis at a time (production, 18 Nov: a run takes 1.0 s on average, p99 4.9 s, and the queue stored 622 to 1,217 an hour with a backlog), each sent at once; a user's ask is always sent at once. An inline run used to download before it recorded the attempt, so a run stopped inside the download left nothing for the sweep (review of 5b5b492, finding 3); the queue's run records itself first. A queued version is pending, never clean: resolve waits up to 20 s for the queue, polling the database, then answers from what landed, and what is still pending is a warning on a `200` (strict mode, `strict=1`: a `202` with the pending versions); scan lists them in `pending`, and the Bun scanner asks again for up to 60 s and then warns (strict: refuses). A score informs; it does not block: a score under 40, an incomplete analysis, a version apm cannot score, a dependency whose metadata could not be fetched and a walk cut short at its limits are each a `warnings` entry on resolve and a `warn` scan advisory, and refuse only in strict mode (`apm add --strict`, `APM_STRICT=1`, `APM_SCANNER_STRICT=1`, and the `~safe` view, which always filters). Revoked, revoke-pending and yanked versions, and versions an apm reviewer confirmed malicious, refuse in every mode. A registry with no queue records each job all the same, and its cron sweep runs it. The queue consumer is the same Worker's `queue()` handler, which fetches, verifies, analyzes and stores. `analysis_jobs` keeps one version from being queued twice within ten minutes; when the queue refuses the job, that reservation is dropped so the next request queues it. A send that has not answered in 4 s may still land, so its reservation stays and the sweep sends the job again if no run began in ten minutes; a job delivered twice finds its run taken and stores once. A job whose upstream failed in a way that may pass (a network error, a 5xx or 429, bytes that failed their checksum, a packument it could not fetch) is handed back with `message.retry()`. A version the upstream no longer lists is recorded `unavailable` and acked. One apm can never score is recorded in `analysis_outcomes` with its reason, and every surface shows that reason instead of "not scored yet": its tarball is over what apm reads as a stream (256 MiB compressed, 512 MiB inflated), it has no checksum, it is not a package apm can read, or three of its analyses were stopped before they stored anything. A tarball over the 32 MiB download or 48 MiB unpack cap of a tarball read whole is read as a stream in the same run (`streamed-analysis.ts`, docs/SCORE.md "Tarballs too large to hold"): two passes over the same bytes, each hashed against the version's sha512 before anything it read is used, the first to index the files and the paths each imports, the second (held entry by entry to the first, verified one) to keep at most 6 MiB of the files the analysis reads first; what it keeps is charged to a child of the job's memory lease first, and what it does not hold makes the analysis's coverage partial (apm-score-v11: graded P, no points, and refused by strict mode and `~safe` apart from the score). Analyses and outcomes are kept per scorer. The current scorer reads an earlier one's result where it would store the same (apm-score-v10's clean analyses and its `unavailable`, `unreadable` and `analysis-limit` decisions: `apm_v10_reusable` and `apm_v10_outcome_reusable`, migration 0023), so reads, waits, runs and the sweep treat those as its own; the rest (a v10 `too-large`, an analysis with a file left unread or `incomplete`) are analysed again when asked for, and the cron seeds the popular ones a few a sweep. `analysis_jobs` records the scorer a reservation was made for, and the sweep re-sends an older Worker's reservation only for a version that never got a result or a run (docs/SCORE.md, "apm-score-v11: coverage"). The consumer takes one message per invocation, runs one invocation at a time (`maxConcurrency: 1`, so no two analyses share an isolate's 128 MB), and gives the analysis the whole work meter (`@apm/core`'s `meter.ts`), which counts work, since the clock does not move while code runs. The meter is one of three layers, not a proof: work it does not charge is stopped by the registry Worker's CPU limit (packages/infra sets it from `WORKER_CPU_MS`: 60 s, approved by the operator, which covers every package measured on staging; prettier needs 28-35 s), and recovery turns every run that ends without a result into a stored outcome. A queued run's record exists before it asks the upstream anything (`startAnalysis` in `analysis_outcomes`), and it decides whether to stop trying before it downloads. The cron's sweep (`Analysis.recover`) requeues every run that began longer ago than the CPU limit plus two minutes and never ended, the ones it picked longest ago first, and every job the queue accepted over 10 minutes ago that never began a run; each kind has half of a sweep's 200, and either takes what the other leaves. A run that began and stored nothing is run again in full, since a run cannot learn why the platform ended the one before it: after one such stop the next run is full, after two it reads at most 4 MB and is `incomplete`, and after three the version records `analysis-limit` (full, full, reduced, `analysis-limit`). A run just after one that reported a failure or a fetch failure runs in full (`reported_start`, migration 0017), and three stops in all still end in `analysis-limit`. A run that throws keeps its start counted, and after two failures the version is stored `incomplete` with the error's class. A run that cannot fetch the version, or loses the database after it began (its result's write is tried again first), counts a fetch failure and ends, so the queue retries it in full; after ten, and an hour since the first, the version is `unavailable`. A version recorded unscorable is a warning on resolve trees and a scan advisory (fatal in strict mode), never only unchecked (docs/SCORE.md, "In the registry").

A Worker has 128 MB of memory, so the registry caps what it reads: upstream downloads held whole at 32 MB, inflated tarballs held whole at 48 MB (a larger upstream tarball is analysed as a stream that holds at most 6 MiB of its files, and serving one never holds it), publish bodies at 32 MB and JSON API bodies at 5 MB. An npm packument is streamed, never held whole (`packument-read.ts`): the reader checks the whole JSON grammar, the parts it discards included, accepts exactly what `JSON.parse` accepts (duplicate keys: the last wins), keeps only the top-level fields the registry reads and, of each version's document, the fields npm's abbreviated packument carries plus the few the registry and full-packument readers use (`KEPT_VERSION_FIELDS`: scripts, publisher, description, links, license, entry points), and of its `dist` only `tarball`, `shasum` and `integrity`. The rest (`licenseText`, `readme`, `exports` maps, npm's signatures, per-version maintainers, `devDependencies`) is read past: when every version field but four was kept, @mastra/core (1.64 million values, 1.2 million of them its `exports` maps), @clerk/backend and @clerk/shared passed the node limit, and prisma, @prisma/client and firebase the 24 MB limit, so npm install of each answered 503. It refuses one past 160 MB read, 24 MB or 1.5 million values kept, a weight of 48 MiB, or 100,000 levels of nesting (nine bytes of stack each). Weight is an upper bound on the heap a kept part is held in once parsed, measured in workerd (`WEIGHTS`, `packument-heap.workerd.test.ts`): the text while it is held, then each string's content (twice when V8 holds it two bytes a character) and a cost per value, container, key and new object shape, so a packument cheap as text and dear as objects (a million empty arrays) is refused, and each parse's moment is charged while it lasts. Kept text is copied into 64 KiB slabs, so a packument sent a byte at a time costs no more than one sent whole. The full packument apm serves adds each version's `devDependencies` back from a second read that keeps only them (next's are 17.5 MB, so both together would pass 24 MB; @prisma/client's, 1.64 million values, are refused and left out), and is written to the client one version at a time, each version's document made only as it is written. One request holds at most 72 MiB of weight in all, the reads it has in flight and each package's records included, out of the isolate's pool (below); a dependency past that is unchecked, with a warning, and devDependencies past it are left out. vite's full packument is 39 MB, 35 MB of it the `licenseText` each version repeats; read with `res.text()` and `JSON.parse` it peaked at 156 MB of V8 heap and the platform ended its page request, and streamed it keeps 2.8 MB. The isolate's packument cache holds at most 32 MiB of weight (`PROBE_CACHE_WEIGHT`), oldest first out. Request bodies are read through a counting reader that cancels the stream at the cap, so a body with no or a false `Content-Length` is not buffered first. A tarball's `package.json`, which is the manifest apm stores and serves, is capped at 1 MB. A local tarball is checked against its published sha512 before it is served. A package over those caps is refused (publish) or left unscored (upstream), never passed as clean.

Serving an upstream tarball needs no analysis and no packument (`fast-tarball.ts`). A published npm tarball never changes for a name and version, and every client checks it against the integrity in the packument it was given, so a GET or HEAD of `/<name>/-/<name>-<version>.tgz` reads only what can refuse it, on every request, at once: one statement (`Store.tarballRead`: whether the name is published here, the digests of that version's tarball apm reviewers confirmed malicious, and whether the version is scored, decided or queued already), the install block list in R2 (never less strict than the database, so this only adds refusals), and npm's document for that one version (`Upstream.versionOf`, a few KiB, kept in the isolate for the upstream TTL as the packument was), which says the version exists now, where its tarball is and its checksum; a document whose `version` is not the one asked for (npm resolves tags and ranges there) counts as absent. A version confirmed malicious, in the database or on the list, is `410` before anything is downloaded. Beside those reads, the OSSF malicious-packages feed is asked about the name (`osv.ts` `advisoriesFor`: one small OSV query per name, kept 5 minutes in the isolate and the data center's cache); any other version it lists is `403`, citing its `MAL-` id. Then npm's tarball is opened (only from the upstream's origin, every redirect checked) and passed on as it arrives through `verified-stream.ts`, which hashes it on the way and holds back the last chunk until every byte matched, while a version with no analysis, outcome or recent reservation is queued (the same `Analysis.enqueue` as before). Nothing is held, kept in R2 or shared between requests, so a request with credentials takes the same path and no copy can outlive a block. `~safe`, a package published here, a file name other than the one apm's packuments link, a version npm's document does not confirm or could not be read for, one with no checksum, a block list that cannot be read or names the package as published here, and an upstream tarball that could not be opened go to the packument route, which answers as it always has: the whole packument read, `~safe`'s whole policy (cooldown, score, unscorable) applied before anything is fetched, a tarball up to the 32 MiB cap downloaded whole, checked and kept in R2, a larger one streamed. Before this, every download read the whole packument (next's is 31 MB) and made about five database round trips, and a tarball up to 32 MiB was downloaded whole before its first byte was sent: `scripts/perf/npm-install-bench.ts` (npm install of react, react-dom, zod, express, lodash and axios, 81 packages, in workerd against real npm with a 75 ms database round trip) took 7.3 s with the colo's copies warm and 1.4 s a tarball, and takes 3.3 to 3.6 s and 0.12 s. npm's tarball is not opened while the checks run: that saved about 30 ms a tarball in the bench, but asked npm for the bytes of versions apm refuses. On both paths the streamed answer's `Content-Length` is npm's (a `FixedLengthStream`), so a client sees the registry as the only host and the lockfile's `resolved` URL stays on it. A tarball that fails its checksum, or whose length is not the declared one, ends with an error before its last bytes, and the client's own check of `dist.integrity` (npm, bun, pnpm and apm all do one) refuses what it got. Big tarballs are not kept in R2: an R2 copy would have to be written from a tee of the stream, which buffers whatever the slower side has not read, and the copy would only be read whole later. Measured in workerd (`tarball-stream.workerd.test.ts`), the isolate holds about 0.5 MiB above its base while 40 MB stream.

Everything an isolate holds of npm's package metadata is leased from one pool of 80 MiB of weight (`memory.ts`, `POOL_WEIGHT`), which leaves 48 of the isolate's 128 MB to the runtime and other work. `worker.ts` opens one lease for each request, queue job and sweep (`RequestMemory`, 72 MiB at most), and every read the run makes is under it or a child of it: a resolve's root, its reloads and its walk, a scan's packages, the packument route's two reads, the score and package answers, and each name of popular-scores. The upstream reader takes a lease as an argument, so code that has none does not compile. These are leased:

- the text the reader holds and the values it parses, a string at two bytes an input byte when it has any byte past ASCII (bytes that are not UTF-8 decode to U+FFFD);
- every key it parses, until the next key at its depth replaces it; a key at the root, or in a version document whose fields a profile lists, that is longer than any listed name is never built;
- each read's fixed working set while it runs (`READ_OVERHEAD_WEIGHT`, 192 KiB; 144 KiB measured);
- converting a read into a package (`packageMoment`), before anything is built from it;
- what a resolve walk, its root and a scan keep of each package: only the versions they pick from it (`walk-catalog.ts`; the root's newest 20 candidates, a scan's one version), with each manifest cut down to its dependency, platform and install-script fields. Its packument is held only while it is read and picked from, and one the isolate cache already has stays the cache's, never charged to the request. next and its 50 packages hold 0.1 MiB once picked, against 26.6 MiB for next's packument alone;
- the served packument's per-version lists and what streaming it holds (`streamWeight`, from the longest member the reader saw), until its last byte is sent;
- the package page's answer (`GET /-/apm/v1/packages/<name>`): its version rows, and what streaming it holds, counted from its serialized size before a byte is written (`longestPiece`). A readme or description is written 64 KiB at a time, never as one string, and the request's lease stays open until the last byte is sent or the client cancels;
- the isolate cache's entries (32 MiB at most, `CACHE_WEIGHT`);
- work after the response. A shared-cache copy starts only once converting its read has fit, and holds its own lease, on the package and its stream's buffers, until the write settles or is stopped (at 20 s, or at its lease's deadline). The AI review's look at a fetched package holds one too. At 30 s (`BACKGROUND_DEADLINE_MS`) the lease's signal aborts and the work stops; the lease is released only once it has, so work that does not stop keeps its charge and the pool refuses that room to others.

Memory several holders refer to (a package a request read, the cache keeps and a copy is being written from) is a block: the pool counts it once while anyone holds it, every holder counts it against its own limit, and a cache eviction or a request that ends frees only its share. A read that does not fit is refused, never waited for: its package is reported unchecked, with a warning, as when its request is full. Before refusing, the pool takes back cache entries only the cache holds. The claim: **the sum of all leases never exceeds 80 MiB.** Reads, their parsed values, the per-read buffers, the answers and the cache are charged before they are made, and a charge is given back only once nothing refers to what it stood for. An interrupted read (a sibling lookup failed, the request ended) cancels its stream and waits for that cancel before its fiber ends and its lease is released (`joinedPromise` in `upstream.ts`); a read refused as malformed or too large drops the scanner and keeps its charge until its stream's cancel has settled. `memory-pool.workerd.test.ts` checks it in workerd with random concurrent mixes of reads, walks, scans, streamed packuments, shared-cache writes (some cancelled), pressure that evicts the cache, interrupted reads, malformed reads whose cancel takes a moment, and looks at fetched packages that stop at their deadline or ignore it, five seeds of 150 operations, up to ten at once. At every sample, taken with all of them parked, the isolate held less above its base than the pool was charged, by 3.1 MiB at the closest over two runs; the test allows 4 MiB of overhead. `lease-ownership.workerd.test.ts` measures each of those moments on its own. Not leased, because none of it is npm metadata: the database rows of packages published here, tarballs (capped on their own, above, or streamed past the cap), and search and advisory answers.

Analyses of npm versions are keyed by tarball digest and scorer version, so a re-published tarball or a new scorer never reuses an old answer.

A resolve walk, its root and a scan keep what they chose of each npm package in `upstream_choices` (migration 0021, `kept-choices.ts`), one row per document (the exact URL the packument was asked for at, so another upstream's `304` never answers from it; a document npm redirects keeps nothing, and a conditional request follows no redirect): npm's strong ETag for the packument (a weak or missing one keeps nothing), and for each choice (a dependency's range or tag, a root's page of candidates, a version a scan asks about) the versions it took and their records, manifests summarized as above. A choice reads only the packument's version numbers, states and dist-tags, so while npm answers `304 Not Modified` for that ETag the same choices hold, and the next read sends `If-None-Match` and answers from the row without reading the packument. That request is the one validation the registry makes of a packument (`Upstream.listingIfChanged`), shared with package pages' kept summaries (`kept-package.ts`): one GET whose `304` keeps what was kept and whose `200` is the changed packument itself, so no packument is checked with a HEAD and then read. Like package pages' other small reads it waits at most 2 s for npm to start answering and is skipped for 30 s after npm failed one for the package; on a failure the packument is read whole, as before anything was kept. Any other answer is read as before: a `200` replaces the row, and an outage or a 404 leaves it alone and is reported as it always was. Scores never live in the row; they are read from `upstream_analysis` on every read. Each choice keeps when npm sent the packument it was made of (a choice made from the isolate cache is as old as the read that filled it) and answers for an hour from then; a write under the same ETag keeps an older choice's time, so nothing makes a choice young again. Past its hour the packument is read whole again. A write is merged into the row kept for the same document and ETag by the database, never by reading older choices back into the Worker: the older choices that still hold stay beside the new ones, newest first, up to 16, and if the merged row would pass 64 KiB only the new choices are kept. That merge relies on strong validators meaning the same bytes, which npm honours. Keeping never costs an answer: the rows read and the rows planned are held on a side lease of the pool, never the request's, taken only from room the pool has free and given up first when anything needs room (a row given up while npm was asked means a whole read). A planned row is one string, the row's JSON text with only this request's choices, built under a reservation from an upper bound and then charged once, at least its UTF-8 bytes; nothing it was built from is kept. The pool taking it back drops the string and its charge together, and a writer claims it before reserving anything else, so it cannot be taken back while it is written. The planned rows are written after the response (`ctx.waitUntil`, on a connection and a memory lease of their own), one at a time, each under a short reservation for what the database driver allocates to send it (an upper bound from the installed driver's code: its encoding buffer, grown from 8 KiB in doubling steps, and the frame it copies for the socket), given back before the next; a write whose reservation does not fit is skipped; one writer at a time takes the lock with `pg_try_advisory_xact_lock`, and a busy lock skips the write instead of waiting, so no answer ever waits on keeping. Rows are bounded at 64 KiB as Postgres stores them (UTF-8 bytes, checked again in the statement) and 16 choices each, on every write, and 5,000 in all, and the cron drops the rows nobody asked about for a week. A resolve of next's 53 packages went from reading 118 MB of packuments to none (`scripts/resolve-bench.ts`, which checks every answer against hashes recorded from the resolver before this change). Reading the rows is charged to the request's lease before they are sent: the statement sends rows only while their measured weight fits the reservation.

### The install packument

`npm install`, pnpm and bun ask for the abbreviated packument (`Accept: application/vnd.npm.install-v1+json`), and every install of a package only npm has goes through it. Outside `~safe` it carries no score, and an npm package has no apm revoke or yank, so the document apm serves is a function of npm's packument, of the versions apm reviewers confirmed malicious, and of the OSSF malicious-packages feed's advisories for the name (`osv.ts`), and of nothing else. Its route (`installPackument` in `apm.ts`) reads both facts the database holds in one statement (`Store.installRead`: whether the name is published here, and the confirmed reviews), on every request, and reads no analyses. The text it serves is kept in the data center's Cache API (`Upstream.installCopy`, written after the response by a second serialization charged like the first) with npm's ETag, when npm sent it, and the SHA-256 of the confirmed set and the feed's advisories beside it (the same as the confirmed set's alone when the feed lists nothing). The next request answers from that copy when its stamp is the one it just read and npm's packument is the same: within the upstream TTL from when npm sent it, or once npm answers a conditional read of that ETag (`If-None-Match`) with a 304, which this isolate then trusts for a TTL. A confirmed or dismissed flag changes the stamp, so the very next request is made anew; a new npm version changes the ETag. A copy answers for at most an hour (`KEPT_CHOICES_MAX_AGE_MS`) from the whole read of npm's packument it was made of, however many 304s came since (review of 7479593, finding 1), and whatever the upstream TTL: then the packument is read whole from npm, past the isolate's cache and the shared copies, and what a whole read runs runs with it, the AI review's look at new versions included, so an enqueue that failed is tried again within the hour, as it was at the next read past the TTL before copies. That read's time on the registry's clock travels with the packument (`readAt`, and a header on shared copies), and a copy is dated from it, never from when the copy was made, so only a whole read from npm makes one younger (re-check of fa220f7). A read time counts only between an hour ago and now (60 s of clock skew allowed): one from the future, or none, is passed over like an old one (re-check of 977b103, finding 1). That whole read is coalesced per isolate: a second request for the same package while one is reading waits, polling this isolate's cache on its own timer (no promise is shared between requests), for up to 10 s, and uses what the first published there. Isolates and data centers do not coordinate, so each may read once at the hour (finding 2). A package too heavy for the isolate cache is not published there, and its waiters read for themselves once the first is done. A request with an `Authorization` or `Cookie` header never reads or writes the copy (finding 2) and is answered as before. The copy is looked up, and checked with npm when it is past the TTL, while that request's own statement reads the confirmed set through the guarded query runner (`db-health.ts`); neither needs the other, and the copy answers only once the statement has read a set whose stamp is the copy's (a whole read of npm's packument with no copy to check still waits for the statement, so a name published here is never read from npm here). It is served or written only while that guard still takes the database as up, checked again after the copy or npm was read and once more just before a copy is put (finding 3): when Postgres cannot be reached that statement, or that check, fails first, and the request is answered by the degraded route (`degraded.ts`) from npm and the R2 block list, which never reads or writes the copy (`outage.test.ts`). The two sets are never mixed: the copy's stamp is of the database's set, the degraded answer filters by the block list, which is never less strict than the database. npm's edge weakens its ETag (`W/"<hash>"`) when it compresses, and answers If-None-Match with either form; the copy uses it as sent. Which form a Worker receives in production has not been observed (kept-choices.ts keeps rows only for a strong one), so each isolate logs the first packument answer of each form (`npm-etag-form`). Measured in workerd against real npm with production's 75 ms database round trip (`scripts/perf/install-bench.ts`), a repeat install past the TTL went from 0.38 to 2.0 s (@prisma/client) to 0.12 to 0.16 s, one database round trip and one npm 304; the bench checks that a block and its undo show on the next request. A request that finds no usable copy reads the package as before, and HEAD, `~safe` and the full packument are answered as before.

### Install checks answered in the data center

With `APM_INSTALL_CHECKS=edge` (off by default: a deploy turns it on with `--install-checks edge`, in the order `docs/DEPLOY.md` gives under "Install checks"), the install document and the tarball redirect of a package only npm has make no Postgres round trip (`edge-checks.ts`). Both depend on two facts the database holds: whether the name is published here, and which of its versions an apm reviewer confirmed malicious. (The OSSF feed is asked beside the view either way, as on the database path.) The block list in R2 holds both and is never less strict than the database, so each isolate keeps its read of it (an edge view) and answers from that. Before, the statement was the floor of every warm install request: 65 to 105 ms of an install document's 65 to 105 ms in production, about 70 ms of a tarball's.

- A view is dated from when the R2 read that made it began (a copy from the Cache API keeps the date of the R2 read it was made from). A view that clears a name hands the route a clearance with that date, and the route asks again, immediately before it makes its answer and after every wait (npm's document, the data center's copy), whether the view is still under 4 s old; if not, the request is answered by the database path from the start. A read that lands late is dated from its start too, so one begun before a write and landing after it is already old.
- So an entry put on the list at P is behind every answer given after P + 4 s + L + S. L is the CPU time the answering request spent since its last I/O: Workers' clocks stand still while code runs, so the clock it checks lags real time by that much. S is how far the clock of the isolate that read R2 runs ahead of the answering one; a copy dated more than 250 ms ahead is not used.
- A request that finds its view 2 s old starts the next read in the background (`ctx.waitUntil`) and answers without waiting for it, so steady traffic never waits for one. A request that finds none young enough reads first, the data center's copy (under 2 s old) else R2, and waits at most 300 ms: past that it takes the database path while the read goes on for the next request. An isolate runs one read at a time, until it settles: a request that finds one running waits for it on its own timer until that read's deadline (no promise is shared between requests), and one that comes after the deadline does not wait and takes the database path; however slow R2 is, no second read starts beside the first (the next item says how a read that never settles is handled). Each isolate logs what its views decided once a minute (`edge-checks`), one count per request for how it was answered: cleared, each fallback reason (a clearance that aged out before the answer counts as `expired` only; one whose tarball npm's document does not let the edge redirect to as `unservable`), R2 reads, copies used, failed reads, and skipped, late and failed analysis asks.
- A view clears a name only when the list was synced in the last 15 minutes (the cron syncs every 10, so a missed sync turns the views off), does not list the name as published here, and lists no confirmed version of it. Anything else (a listed name, any confirmed version of it, a list missing, unreadable, never synced or stale, an R2 read that failed) takes the database path, unchanged; a failed read is kept like a view, so an R2 outage costs one read per window. An isolate runs one read at a time. A request waits for a read's result until its deadline, but the read is out until the underlying R2 call and its body settle, and no timer ends it, so two reads are never out at once. The request that started it keeps it in its `ctx.waitUntil` for 10 s at most; a read still out then is counted (`readTimeouts`) and runs on, and every request the isolate sends to the database path meanwhile is counted too (`readStuck`). A read that never settles keeps that isolate on the database path, which is safe and shows in the per-minute log. So do requests with credentials, `~safe`, clients that do not check tarballs themselves (yarn 2 and later, unnamed clients) and tarballs npm links from another URL.
- A confirmation goes on the list before it commits (review.ts), so every view refuses the version from 4 s + L + S after the put.
- A first publish of a name with no package (publish and staged approval alike) puts the name on the list, then waits 8 s before it opens its transaction (`fenceNewName`, the publish fence); the transaction creates the package only under that fence, checks ownership again under the package's lock, and a staged approval checks its row is still pending and unexpired. The wait holds no lock and no transaction, so a second publish of the same name waits its own fence alongside instead of on the first one's row. 8 s covers the 4 s and leaves 4 s for L + S, so npm's tarball or document is never served under a name that exists here unless a request spent nearly 4 s of CPU between its last I/O and its answer. Every Worker holds the fence whatever its read mode, which is what lets edge views go on only once no build without it is publishing. apm already refuses a first publish of a name npm has; the fence covers npm gaining it while the publish runs.
- Revoke, yank, restore, deprecation, dist-tags and owners change only packages published here, which a view never clears. `edge-writers.test.ts` reads the shipped code (operational scripts included; benches under `scripts/perf` are not) for every statement that inserts a package or can set a review confirmed and fails on one it does not know; a write made by hand in SQL shows at the cron's next sync (10 minutes), the backstop.
- A download answered from a view is queued for analysis after its answer, on a connection of its own, as the database path did inline. An isolate asks about one name@version at most once a minute, again after 5 s when the ask failed, and runs at most 8 asks at once (a turn takes its ask in the same step that sees it free, so turns that look on one tick never take more). Each ask runs in the `ctx.waitUntil` of the request that accepted it and no other: up to 120 more wait their turn, first come first, each on its own request's timer for at most 5 s, then are dropped, counted (`queueLate`) and forgotten, so the next download asks again. 8 asks at a time get through 120 in 5 s while an ask (a statement, and an insert for a version not yet queued, at production's 65 to 105 ms round trip) averages under 0.33 s; one cold `npm install` of the bench's 83 new packages fits. An ask is aborted at 15 s whatever it waits on (a statement gives up at 8 s, a queue send is waited for 4 s and then left to the sweep): its slot is freed, the timeout counted (`queueTimeouts`) and the download asked about again after 5 s, so the wait plus one ask ends by 20 s, well inside the 30 s a request's background may run. A send the queue refused counts as a failure (`queueFailures`) and is asked again after 5 s too. A download past the 120 is not asked about (`queueSkipped`), and the next one is.

`scripts/perf/npm-install-bench.ts` measures both (`BENCH_INSTALL_CHECKS=edge`), `tests/acceptance/edge-checks.test.ts` runs a first publish while npm gains the name and polls both answers, and two first publishes of one name at once while it checks that no transaction is open during the fence, and `edge-checks.test.ts` checks the windows on a simulated clock, an R2 read that lands after a publish's commit, the deadline and the one read per isolate (a stalled read, and one out while the clock moves minutes, included), and the asks: never more than 8 at once when twenty arrive on one tick, a stalled ask aborted at its deadline, a refused send asked again. On the database path the tarball route's own read of the block list waits at most the same 300 ms; past it the database's statement decides alone, as it does for the install document (`fast-tarball.ts`, `blockListWithin`).

### The file view

Every score citation and AI review finding on the website links to the file it names, opened at the cited line. `files.ts` answers `GET /-/apm/v1/file/<name>/<version>?path=...` from the same verified tarball the install routes serve (a local blob checked against its sha512 integrity, an upstream one through `Upstream.tarball`). The path is matched against the parsed entry list, never joined onto a directory, so `../` names nothing. Files that are not valid UTF-8 are reported with their size and not sent; a revoked version answers 410. An upstream tarball too large to hold (next's) is read as one verified stream that holds only the file asked for, up to 8 MiB (`readOneFile` in `streamed-analysis.ts`): nothing is shown until every byte matched its sha512, and a larger file is listed with its size and its lines refused (413). Answers are cached in R2 under the tarball's digest: one index of paths and sizes, and one object per path read. The website renders the text as text only, in blocks of 200 lines that skip layout while off screen, and shows bidi controls and other hidden characters as visible markers.

The whole-file answer stops at 1 MB, but a citation can point into a 20 MB bundle, so `?path=...&line=N&context=K` returns lines N−K to N+K (K at most 100) of a file of any size the tarball caps allow, with their real line numbers. A line longer than 4 KB (a minified bundle) is cut on a character boundary and reports its full length. Excerpts are built from blocks of 100 lines cached in R2 per digest, path and block, plus one line count per path, so however many ranges are asked for, the cache holds at most one copy of the file. A line past the end answers 416 with the line count. Evidence links carry the line in the query as well as the fragment (`?line=12#L12`), because the server only sees the query: a file over 1 MB opens as an excerpt of about 40 lines around the cited one, highlighted, with "Show more" controls that fetch 100 lines at a time.

`GET /-/apm/v1/readme/<name>/<version>` answers the README in a version's tarball, picked the way npm picks one (a root `README` or `README.*` file, any case; the first with a markdown-like extension in path order, else one named exactly `README`), through the same checks and caps as the file view. The package page uses it when npm's packument carries no readme, and says "No readme published" when neither has one. The page also links the latest version's `homepage`, `repository` and `bugs`, but only http(s) URLs without credentials, with the same `rel` as readme links.

### AI release review

`review.ts` keeps the review-job queue and results in Postgres (`0004_reviews_and_password_lockout.sql`). The model never runs on Cloudflare: the reviewer process (`apps/reviewer`) runs next to the model on the owner's tailnet, leases jobs with a service token (`SELECT ... FOR UPDATE SKIP LOCKED`, so two reviewers never get the same job), downloads tarballs from the registry, and posts results back. The Worker stores only the token's sha256.

Two hooks fill the queue. After a publish or an approval commits, the version is queued on the request's own connection. When an upstream packument is fetched whole (not on a cache hit, nor when npm's `304` lets a resolve answer from its kept choices, which happens for at most an hour after the choice was made), the enqueue policy runs after the response through `ctx.waitUntil`, on its own Postgres connection, because the request's connection closes with the request. The `review_seen` high-water mark is claimed in the same transaction that inserts the jobs, so two isolates that fetched the same packument queue its new versions once, and a failed insert leaves them unseen for the next fetch. The download count the policy needs is fetched before that transaction. See `docs/AI-REVIEW.md`.

### Sign-in and second factors

Better Auth handles OAuth, sessions, TOTP enrolment, passkeys and the device flow. The registry exposes only the Better Auth routes the website uses, and gates the ones that change how someone signs in behind the existing factor (the `x-apm-second-factor` header). apm checks codes itself, against a ledger in Postgres: one attempt budget per account across TOTP and recovery codes, each TOTP time step accepted once, and a website confirmation of one named CLI command used once within ten minutes. Because the ledger is in Postgres, every Worker isolate sees the same budget.

Every second factor on the website is bound to one action (`0007_action_confirmations.sql`). `actions.ts` gives each website action one canonical key that holds every parameter deciding what it does: the staged upload's id, the CLI command, the review decision and its note, the evidence item and the reason, the sign-in setting. A code, or a passkey check, issues a confirmation for that key and the session that made it (`POST /-/apm/v1/factor/confirm`), and the change spends a confirmation only when its own key and session match, once, within five minutes. A passkey check answers a WebAuthn challenge the registry made for one named action (`POST /-/apm/v1/factor/passkey-challenge`) and is verified against the account's own passkeys; Better Auth's passkey sign-in makes a session and no confirmation. A code sent with the change itself is issued and spent on that change in the same request. The website-only routes (approvals, confirmations, review decisions, evidence dismissals, token revocation and the gated sign-in settings) refuse a request without the website's `Origin` (`origin.ts`); routes that take a token do not look at it.

### The website

The website is Next.js 16 with shadcn, built by OpenNext through Alchemy's `Website.Nextjs`. `proxy.ts` forwards `/api/auth/*` and `/-/apm/v1/*` to the registry so the session cookie lives on the website's origin, and server components read the registry for package pages and search. Both go through `lib/registry-transport.ts`: inside the Worker that is the `REGISTRY` service binding, because Workers on one account can't fetch each other's public URLs and a binding skips the network hop; under `next dev` it is plain HTTP to `APM_REGISTRY`.

What a revoke hides is one policy, for revoked and revoke-pending versions alike. People revoke to pull malware, and also to pull a secret they published by accident; both need the same guarantee.

**Hard guarantee.** For a revoked or revoke-pending version, no route serves its file contents or quoted code, its readme text, AI review text that could quote the package, its install script bodies, or the files of the staged upload it came from. The one exception is a revoke-pending version's tarball, which stays downloadable for existing lockfiles until the revoke is final.

**Best effort.** The publisher's metadata (description, keywords, deprecation message, file names, dependency names) is hidden where that is practical, but it is not part of the guarantee. Today the answers below leave out the description, keywords and deprecation message, replace file names with numbered references, and name a dependency only when its key is a valid npm name. A publisher who put a secret in any of these should treat it as public and rotate it.

The registry is the only gate for a version's source. It reads the version's status from the database on every request that can carry source, keeps immutable bytes in R2 under the tarball's digest, and marks those answers `Cache-Control: private, no-store`, so a revoke (a database write) refuses the very next request. Files, excerpts and the tarball readme answer 410, as do a staged upload's files once the version it became is withheld; the staged detail then sends the upload's facts and hashes with no description, file list or score. A withheld version's review, score, resolve and package answers, and the admin review queue, are rebuilt from an allowlist in `withheld.ts` and `review.ts`. Kept: line numbers, rule ids, severities, verdicts, counts and the revoke's reason. Score evidence is dropped entirely, because the package's own text can sit anywhere in an evidence line. A review finding's sentence is replaced by fixed words ("Finding withheld with this version"; a finding has no category apm could word it from), and every path the review names becomes a numbered reference ("file 3"), as does every path in the score's dismissed items and skipped files (one numbering for both, with each skipped file's size and reason kept). The not-checked list is rebuilt from fixed wording, so no dependency spec goes out, and a dependency key that is not a valid npm name is called "a dependency with an invalid name"; the license is dropped. A revoke-pending version's manifest answers 404 like a revoked one's. The package's description and keywords, which every publish overwrites, come from the newest shown version while any version is withheld, ordered by publish time and then insert order (`seq`), as the database orders them, in the packument, search and the package answer; search reads that text for every affected package in one query. The package's public log keeps who, when and which version for a withheld version's events, and drops publisher text by event kind (a deprecation message, a dist-tag name, a file path). The revoke's reason is the owner's words, not the package's, and travels in its own field: `revokeReason` on a 410 and on resolve's skipped list, `statusReason` in the package answer, `reason` in the log; refusal messages say only "revoked by its owner" or "revocation pending", except the tarball's 410, whose `error` is the one line npm prints and so ends with the reason. The package row records which version's publish wrote its readme (`readme_version`), and the readme is hidden while that version is withheld; a row whose owner is unknown hides it while any version is.

Every GET route is listed in one table, `routes.ts`, and `router.ts` answers 404 to a GET or HEAD whose path matches no entry before any route module sees it, so a GET handler added to a module answers nothing until it is listed. The table matches a path the way the modules read it (empty segments dropped, each segment percent-decoded, as `splitPath` does), so a trailing slash, `%40` and `%2f` reach the same route they did before the table; `tests/acceptance/route-compat.test.ts` checks 2,828 URL forms against the statuses 19a99eb returned. `tests/acceptance/revoke-sweep.test.ts` probes every entry of that table and fails on one it does not probe. It publishes a package with a marker in every free-text field, brings one version in through a staged upload a signed-in owner approves, revokes one version and puts another into revoke-pending, and asks every route as anonymous, the maintainer's token, the signed-in owner and an admin, plain and under `~safe`. Each answer must have the status its probe expects and a body, and a marker may come back, in a body or a header, only at the exact route, status and field the test names.

The website keeps no answer that carries source and no record of whether a version may be shown: the package answer, a file, an excerpt, the tarball readme, the AI review, an older version's score and `/api/readme` are read from the registry (through the `REGISTRY` service binding) on every view, and `/api/readme` answers `private, no-store`. Source-free answers go through a short cache in `lib/edge-cache.ts`, the isolate's memory and the Workers Cache API on custom domains: search results made only of npm's packages, a package's public log, and that a package or a file of a version exists. A search answer with a package published here is never cached, by the edge cache or by `/api/search`, which sends it `no-store`: that package's description changes the moment one of its versions is revoked. `lib/registry-fetch.ts` refuses to cache any other path. `proxy.ts` decides a package page's status before the shell streams with a HEAD of the package or file answer, which the registry answers without building it; a package or file known to exist needs no registry call there, and the page's own read is what a revoked version is refused on, with a page that says why. When the registry can't be read the page says so and shows nothing from before. The page shows the package's name as soon as the request is routed (it is in the URL; nothing read from the registry is shown before the package answer), then starts its reads together: the package answer, the public log, the AI review of the asked version or of `latest` (the review route resolves a dist-tag), and an asked older version's score. They run after `connection()`, in the request's dynamic stage: the edge cache and the version list read the clock, which Cache Components refuses earlier, and that refusal made every view render twice and stream nothing until its slowest read was in. The package answer is read once per request (`getPackage`, kept on OpenNext's per-request context, never across requests), because Next.js renders `generateMetadata` apart from the page and React's cache alone read it twice. An early review or score is used only when it names the version the page shows and is as restrictive as the package answer reports that version (redacted when it is revoked or revoke-pending, since a revoke can commit between the two reads), otherwise that version is read (`lib/early-answer.ts`, `lib/package-reads.ts`), so a warm view waits for one registry answer rather than two in a row. The page streams the AI review, the tarball readme and the public log behind their own Suspense boundaries; the header, install box and score do not wait for them. While a review is queued, its card asks again every 5 seconds for up to 3 minutes.

A package's readme is publisher-written, so `lib/readme.ts` renders it on the server through unified (remark-gfm, rehype-raw, rehype-sanitize with GitHub's allow-list) into React elements, never inner HTML. Relative links and images resolve into the package's GitHub repository (the `repository` field of the package answer) or are dropped, images load over https only, external links get `rel="nofollow noopener noreferrer ugc"`, and every id is prefixed with `user-content-`.

## How `apm add` makes the package manager install what apm checked

`apm add` asks the registry to resolve and score a package, then runs your package manager (bun, npm, pnpm or yarn) to install the exact version. The check only means something if the package manager then installs the same bytes from the same registry, for the package and for everything under it. Two things can break that:

- A config file sends a scope to another registry. A project `.npmrc` line like `@someone:registry=https://elsewhere/` applies to every package in that scope, including dependencies several levels down.
- A lockfile pins a package to another registry's tarball. bun, npm and pnpm reuse a locked `resolved` URL and integrity even when told a different registry, so a committed lockfile can bring in bytes apm never saw.

`apm add` closes both, lockfile first: it checks the exact graph the package manager resolves before anything is installed, so a refusal never has anything to undo (review of a2227d1: an install-then-roll-back design restored the wrong directory in workspaces, deleted dependencies and patches, followed symlinks out of the project and stopped halfway). In this order:

1. **Bind every scope.** apm pins each scope in the resolve answer's tree (`tree.packages`), plus the added packages' own, to the checked registry: `--registry` and `--@scope:registry` flags for npm and pnpm, and the matching `npm_config_*`/`BUN_CONFIG_REGISTRY` variables in the child environment. If an `.npmrc`, `bunfig.toml` or `.yarnrc.yml` sends one of those scopes elsewhere, apm refuses. After step 3 it does the same for every scope in the computed lockfile.
2. **Copy the project.** `project.ts` finds where the package manager installs: the workspace root whose patterns take the project in (`workspaces` in package.json for npm, bun and yarn, `pnpm-workspace.yaml` for pnpm), else the project itself. `lockfirst.ts` copies into a fresh `mktemp` directory under `TMPDIR` only `package.json`, the lockfile (npm's `npm-shrinkwrap.json` before `package-lock.json`, as npm reads them), `.npmrc`, `pnpm-workspace.yaml`, `.pnpmfile.cjs`, `bunfig.toml`, `.yarnrc.yml`, every workspace member's `package.json`, the patch files `patchedDependencies` names inside the project, and yarn berry's own release when `.yarnrc.yml` points at one. A `bun.lockb` alone is refused here: apm cannot read it.
3. **Compute the lockfile there.** In the copy (in the member's directory, for a workspace) apm runs `npm install --package-lock-only --ignore-scripts`, `pnpm add --lockfile-only --ignore-scripts` or `bun add --lockfile-only --ignore-scripts` with the exact versions. Nothing is installed and nothing in the project changes. If the package manager changed any copied file besides `package.json` and the lockfile, apm refuses: it copies only those two back.
4. **Check every package of it.** `lockfile.ts` reads every node of the computed lockfile, nested copies, overrides and peers included, each with its origin taken from the lockfile's `resolved` or resolution, not guessed from its version. `installed.ts` sends each registry package to the scan (`POST /-/apm/v1/scan`, 200 a request, with its integrity and the add's `--cooldown` and `--floor`) and asks again about pending ones for up to 90 s. A revoked, revoke-pending or yanked version, one an apm reviewer confirmed malicious, one whose integrity names other bytes, and a name@version the lockfile locks to two different artifacts are refused in every mode. Integrity is compared by algorithm (`@apm/core`'s `sri.ts`, shared by the scan and the CLI): it matches only when the algorithm the package manager will check (the strongest one the lockfile lists) is one the registry knows and every shared digest is the registry's; any other digest under a shared algorithm is a mismatch; and a lockfile hash the registry cannot compare (no algorithm in common, or a stronger one only the lockfile lists) is unverified, never a match. Each occurrence keeps its own integrity: two copies of one version with the same hashes in another order are one artifact, a copy with no integrity is unchecked even when another has one, and two copies with integrities that cannot be compared are each sent. A version inside the cooldown, with a low or incomplete score, one apm cannot score or has not scored yet, one the registry could not look up, an unverified integrity, a registry entry with no integrity, and a git, file, link, remote-tarball or undeclared workspace entry are warnings; strict mode refuses them. A workspace member counts as the project's own source, and is not asked about, only when the lockfile's node is bound to a declared member: the member's folder, its `package.json` name, and its version where the lockfile records one; every external dependency a member brings is checked like any other, and apm refuses to write if any copied file (a member's `package.json` included) changed while it checked. `--force` lifts the cooldown and score floor of the exact versions it names and nothing else: the scan gets the asked-for cooldown and floor, so a fresh transitive version still warns and a stricter `--floor` still holds for the rest. A bundled dependency (npm's `inBundle`) ships inside its parent's tarball, so the parent's score covers its code: it is sent with `bundled: true`, which asks only whether that version is revoked, yanked or confirmed malicious (refused in every mode), never for a score, a cooldown or an integrity. If anything is refused, apm exits 1 and names it; the temporary directory is removed (`sandbox.ts`: only apm's own directory directly under `TMPDIR`'s real path, never through a symlink, and `rm` removes a link inside it as a link).
5. **Apply.** apm writes the checked `package.json` (the member's, in a workspace) and lockfile over the project's, each written beside it and renamed into place, after keeping the old bytes in a backup under `TMPDIR`. If either changed since apm copied it, or is a symlink, apm refuses and writes nothing.
6. **Install exactly that.** `pnpm install --frozen-lockfile --ignore-scripts` or `bun install --frozen-lockfile --ignore-scripts` at the install root. npm has no frozen install but `ci`, which deletes `node_modules` first: apm runs `npm ci --ignore-scripts` when there is no `node_modules`, and otherwise `npm install --ignore-scripts`, which keeps what it need not change (a hand patch in an untouched package), and step 7 confirms the lockfile stayed byte-identical. A production install is read once, the way each package manager reads it (`groups.ts`, with `ini.ts` decoding `.npmrc` files as npm's `ini` does: quotes, inline comments, `key[]` lists, sections, `${VAR}`). For npm, apm folds `omit`, `include`, `only`, `also`, `production`, `dev` and `optional` layer by layer, from the defaults (`omit=dev` when `NODE_ENV=production`) through the builtin, global, user and project `.npmrc` to the environment, as npm's `buildOmitList` does, so an `include=dev`, `production=false` or `dev=true` keeps devDependencies whichever layer set it. pnpm 10 takes the first layer that sets `only` or `production`, reads `production` untyped (any value but `false` or `null` counts) and reads neither `omit` nor `NODE_ENV`. `apm add --production`/`--prod` asks any of the three; bun reads none of these settings. `packages/cli/test/fixtures/omission-cases.ts` lists the settings and what real npm 9 and pnpm 10 do with each, and the tests hold both apm and the real package managers to it (review of efef668, finding 3). The install is then told so explicitly (`--omit=dev`, `--prod`, `--production`), and so is the command that runs held scripts in step 8 (`npm rebuild --omit=dev`, `pnpm rebuild` with `npm_config_production=true`, `bun install --production`; review of efef668, finding 1); the lockfile is still computed and checked whole, devDependencies included (review of 2b7767f, finding 3).
7. **Verify.** `verify.ts` checks what was installed the way Node will load it, not as a set of names: the lockfile is still the checked bytes; from the root and each workspace member, every dependency edge the lockfile locks is looked up as Node looks it up and must reach a package of the locked name and version (a workspace member: its own folder), then each of that package's edges, and so on, which covers pnpm's and bun's store links and peer contexts, wherever the package lives: a pnpm virtual store outside the project is walked like one inside it, and only what apm may remove depends on where a package is (review of 2b7767f, finding 1). A package's `package.json` must hold the version the lockfile records for it, which for a file tarball or git entry is the manifest version npm and pnpm record beside its locator, and a pnpm `file:` dependency resolves to its own lockfile entry, edges included (finding 4). A required package that is missing is a mismatch; an optional one, a devDependency of a production install, and one built for another platform than this machine's are not. A platform is no optionality: a package built for this machine that a required edge reaches must be there (finding 2); and each npm lockfile key, a member's own `node_modules` included, must hold its locked version, with the integrity npm recorded installing there (`node_modules/.package-lock.json`). A package found at its lockfile place but reached by no edge (a devDependency's dependency, installed though the devDependency was left out) has its own edges walked too, before any script runs (review of efef668, finding 2). Every other package directory is accounted for: inside a checked package whose `bundleDependencies` name it (pnpm leaves these out of its lockfile), it is asked about with `bundled: true` and refused if revoked, yanked or confirmed malicious; there before this install (left over, outside the lockfile), it is a warning, refused in strict mode, since install scripts could load it; anything else the install put there is a mismatch. A package directory apm cannot read, one with no `package.json`, a directory that cannot be listed, and anything in a package store (`.pnpm`, `.bun`) that is not a package directory are warnings, refused in strict mode, never an empty inventory. A store holding nothing but pnpm's `lock.yaml` is metadata: pnpm leaves that with `node-linker=hoisted` or a virtual store outside the project, and that external store (named in `node_modules/.modules.yaml`) is inventoried too, so a copy there from before is not taken for a new one (review of efef668, finding 5). If the install is not the checked lockfile, apm runs no script, leaves the files as installed (it never undoes an install: an undo that half works is worse than none) and prints the commands that put `package.json` and the lockfile back from the backup, then reinstall. An error after the write (removing apm's copy of the project, a package manager that cannot start, a filesystem error) prints them too, and says whether any install script may have run (review of 2b7767f, finding 7).
8. **Run the scripts.** Only for the packages this install put in place, at those locations (compared with what `node_modules` held before): `npm rebuild <directory>` for each (npm matches a directory to its exact location, so a same-version copy elsewhere is left alone), `pnpm rebuild <name@version>` (never `--pending`, which also ran builds left from before and the project's own `postinstall`) when every installed copy of that version is one this install put in place: pnpm rebuilds every copy of a version, peer contexts included, and cannot be pointed at one, so a version with an older copy keeps its script held and apm prints `pnpm cannot run <pkg>'s install script for only the new copy; run \`pnpm rebuild <pkg>\` yourself if you want it` (review of 2b7767f, finding 5). bun only runs scripts while installing a package: apm removes those directories and runs `bun install --frozen-lockfile`, then checks the result again as in step 7, with what `node_modules` held just before that install as the baseline, so a package it brings is not taken for one left from before (finding 6); the backup is kept until that check passes. Removal never goes through a symlink and never leaves the project: the directory must be a real directory whose real path is its path, inside the `node_modules` of the root or a member, and that `node_modules` must itself be a real directory of the project, not a link to a shared or external store. A local (file or git) package is found where the lockfile resolves it, not by its source spec. Each package manager's own script policy still applies (bun's `trustedDependencies`, pnpm's `onlyBuiltDependencies`). apm runs none of the project's own `preinstall`, `install`, `postinstall` or `prepare` scripts under npm and pnpm, and says so; bun's reinstall runs them, and apm says that too.

`apm x` runs steps 1, 3, 4, 6, 7 and 8 in a temporary project of its own (npm when the project uses yarn), then runs the package's binary (the one named like the package, as npx picks it) in your directory with the package's own `node_modules/.bin` (where pnpm links its dependencies' binaries) and the temporary project's first on `PATH`, so a helper binary it calls is the checked one. The directory is removed afterwards. `apm audit` checks every package in `node_modules` with the same code: a blocked version is a critical finding, a warning a warning, and what could not be checked keeps the audit from passing. The Bun scanner needs none of this: bun hands it the exact install set, a version the lockfile pins and a new package reuses included (`tests/acceptance/bun-scanner.test.ts`).

Limits:

- yarn runs install scripts while it installs. `apm add --strict` refuses a yarn add before anything runs ("apm cannot check yarn installs before yarn runs their scripts."). In the default mode apm warns first, then for yarn 2 and later computes the lockfile in the copy (`yarn add --mode update-lockfile`), checks it (by version: yarn's checksums are not the registry's integrity) and refuses with the project untouched, or writes it back and runs `yarn install --immutable`, saying that yarn runs scripts before apm can check what it installed. It then checks that `yarn.lock` is still the checked bytes and that `node_modules` holds nothing the checked lockfile does not, and keeps the backup until it has; a difference is refused with the commands that put the project back. Yarn 1 has no lockfile-only mode: yarn installs and runs scripts first, and apm checks `node_modules` afterwards and says it did.
- The resolve walk is the early answer, printed before the lockfile is computed: it stops after 300 packages, 400 dependency lookups (failed ones included), 32 levels or 6 s of reading (`WALK_BUDGET_MS`), and lists anything past that as not checked. At 6 s the npm reads still running are stopped and no further level is started; the reads that finished keep their choices (`upstream_choices`), so the next resolve of the tree answers those from npm's 304 and gets further. A walk cut short by time answers at once, without waiting for queued analyses and walking again. Before the limit, firebase's walk read for 30 to 44 s in production, past the website's 25 s; the check of the computed lockfile covers the whole graph. Each name and range is picked once per walk, and a level's packages are read in one batch of four statements (this registry's dist-tags and version heads, the picked rows' sizes, the picked rows, dismissals), reserved from their sizes before they are read.
- The walk predicts the tree. The CLI sends no `os` or `cpu`, so every platform's optional packages are checked (review of 1924692, findings 2 and 3), a peer counts as met only by its own package under its own name, and a peer the project provides is checked at the version its lockfile pins (sent in `installed`), or at the newest in range with no lockfile entry. That context is advisory: a project with more than 500 direct dependencies, or ones whose names take more than 8,000 bytes, sends none and is told so, never a part of it, and the check of the computed lockfile reads every package.
- Without a lockfile, the package manager computes one from `package.json` alone (the copy has no `node_modules`), so it may pick newer versions in range than an earlier install left in `node_modules`. They are checked like everything else.
- Integrity on disk: npm records the integrity it installed at each path, which step 7 compares; pnpm and bun keep no such record in `node_modules`, so for them the frozen install's own integrity check against the checked lockfile is what binds the bytes. A user's hand patch inside an installed package is kept by design, so installed bytes are not re-hashed.
- `.pnpmfile.cjs` is project configuration that runs while pnpm computes the lockfile, even with scripts off: apm copies it, and trusts it as part of the project.

## Analytics and error reports

Production sends analytics and server error reports to [Databuddy](https://www.databuddy.cc). Other stages send nothing, because only production gets the client id (`packages/infra/analytics.ts`): `deploy.ts` passes it to the website and docs builds, and `alchemy.run.ts` binds it to both Workers. A build without the id renders no tracker at all.

- **The tracker**: both sites load Databuddy's standard script, `https://cdn.databuddy.cc/databuddy.js`, but neither renders a tag for it. Each renders one inline, synchronous loader in `<head>` that adds the tag only when the page may report: `databuddyLoaderScript` in `apps/web/lib/analytics.ts`, rendered by `components/databuddy.tsx` in the root layout, and `docsLoaderScript` in `apps/docs/analytics.ts`, a Blume `script()` adapter used by `blume.config.ts` (the unit test checks the two are the same script). A static `<script async src>` would not work on the website: React hoists async external scripts to the top of `<head>`, so databuddy.js would start before any check could run. The tag the loader adds carries `data-track-web-vitals`, `data-track-errors` and `data-track-outgoing-links`, so Databuddy records page views (on hard loads and client-router navigations, with the URL, title, referrer, and UTM parameters and click ids), Web Vitals, browser errors and outgoing-link clicks. Page views appear in Databuddy's own Pageviews reports. The script sets no cookies; it keeps a random visitor id in `localStorage` (`did`) and a session id in `sessionStorage`.

  The loader adds nothing, and sets `window.databuddyDisabled = true`, when the page is not at its site's canonical origin (`https://apmjs.dev`, `https://docs.apmjs.dev`), when Global Privacy Control is on (`navigator.globalPrivacyControl === true`), when Do Not Track is `"1"` or `"yes"` in `navigator.doNotTrack`, `window.doNotTrack` or `navigator.msDoNotTrack`, or when reading any of these throws. The browser then makes no request to `cdn.databuddy.cc` or `basket.databuddy.cc` at all. databuddy.js on its own reads only GPC and `navigator.doNotTrack === "1"` and skips only `localhost`-like hosts, so the loader is what keeps a production build served on a preview host or a `workers.dev` address silent.

  On the website the loader also adds no tag while `location.pathname` is a private route: `/account`, `/approve`, `/admin`, `/device`, `/signin` or `/publish`, bare or with anything under it (`PRIVATE_ROUTES`). databuddy.js therefore never runs on a hard load of a private page and never reads that page's URL; its query can hold ids, and click ids such as `gclid` that databuddy.js would keep as attribution. The loader leaves `window.__apmLoadDatabuddy` behind, and `components/databuddy-route-loader.tsx` calls it after each client-router navigation, once the router has committed the new URL, so a visitor who goes on to a public page gets the tracker there with only that page's URL in view. Once a document has loaded the tracker, the loader turns any client-router navigation into a private route (`history.pushState`, `history.replaceState`, or `popstate`) into a full page load of that route instead, so a tracked document never enters a private URL and databuddy.js never reads its path or query parameters in either normal or late-load timing. As defense in depth, the tag also carries `data-skip-patterns` (each route bare and as `/<route>/*`, because databuddy.js reads `/foo/*` as "starts with `/foo/`") and `data-mask-patterns` (`/<route>/**`). databuddy.js reports a page view's referrer as origin plus path, and a document keeps the Referrer-Policy it loaded with, so every page sends `Referrer-Policy: strict-origin` (`apps/web/lib/security-headers.ts`, and both sites' static `_headers`): any full navigation from `/approve/<id>` to a public page leaves it `https://apmjs.dev/` as its referrer, not the id.

  The CSP allows `https://cdn.databuddy.cc` in `script-src` and `https://basket.databuddy.cc` in `connect-src` (`apps/web/lib/security-headers.ts`, `apps/web/lib/databuddy-origin.ts`). The website's Worker sends it on every page; the files Cloudflare's asset layer serves alone get it from `_headers`: the website's `/_next/static/*`, and every docs page and file through the docs' `/*` rule (the docs site is assets only). Cloudflare joins a header set by two matching rules with a comma, so the docs' `/_astro/*` rule sets only its cache policy (`apps/web/lib/static-headers.test.ts`). Blume's own search and feedback events go to `window.databuddy` too; a search reports its length, never its text (`search: { analytics: { queries: false } }`).

  `apps/web/scripts/analytics-browser.ts` checks all of this in a real browser with the real databuddy.js and a stubbed `basket.databuddy.cc`, serving the local builds at the canonical origins: the served HTML has no databuddy.js tag, public pages send their page views, private routes send nothing and a hard load of one does not even fetch databuddy.js (also with `gclid` and UTM parameters, which never reach Databuddy after the visitor moves on to a public page), any private route in any request is masked to the route alone, no referrer names one (including a full navigation after a client-router visit), local URLs and each GPC and DNT signal make no request to either Databuddy host on either site, and the docs load with no CSP errors. databuddy.js sends nothing from a browser it takes for a bot, so the check hides `navigator.webdriver` and the HeadlessChrome user agent first.

- **Server errors**: the registry reports every request it answers with "Internal error" or "misconfigured", and the website reports what Next.js passes to `onRequestError` (`apps/web/instrumentation.ts`). A report carries a fixed code chosen by the error's class (`misconfigured`, `db_unavailable`, `db_error`, `blob_error`, `auth_error`, `queue_error`, `internal`, `unknown`), a static route label from the worker's method and route table (`unknown` for anything else), the status, the build id and the colo. Never an error's message, name, digest or stack, or a path as sent (`packages/core/src/error-report.ts`). Reports go to `basket.databuddy.cc/errors` from a `waitUntil` task, which also classifies and serializes the error after the answer (with no execution context nothing is reported), without following redirects, at most 10 per isolate per minute whatever hostname a request used. Each carries `User-Agent: apmjs/1.0`: a Worker's `fetch()` sends no User-Agent, and Databuddy's edge refuses a request without one (`missing_user_agent`). Workers Logs keeps the full line.

## Tests

The acceptance suite (`tests/acceptance`, 309 tests) drives real `bun`, `npm` and `pnpm` and the `apm` CLI against the registry exactly as it ships:

- `packages/registry/scripts/build.ts` bundles the Worker with rolldown and the Cloudflare plugin set Alchemy uses. The deploy uploads `dist/worker.js` as built (`bundle: false`), with every chunk under `dist/worker-chunks/` (Alchemy uploads each `.js` file under the entry's directory as a module); the suite runs `dist/worker-test.js`, which imports that entry and adds test-only controls. Miniflare is given the entry and its chunks (`workerModules`), so a test loads `auth-engine.ts` the way production does.
- Miniflare runs the bundle in workerd with R2, the analysis queue and its consumer, and Hyperdrive simulated locally. Hyperdrive points at a real Postgres 18 cluster the suite starts with `initdb` (`tests/acceptance/postgres.ts`), or at `APM_TEST_DATABASE_URL`. Each registry gets a copy of one migrated template database.
- A small proxy in front of Miniflare stamps the test's clocks on every request (`x-apm-test-now`, `x-apm-test-totp-now`), so tests keep moving time with `clock += DAY` while stock clients make the requests. The test entry honours those headers, `/__test/mint`, `/__test/blobs`, `/__test/sweep` (the cron's sweep at the test clock), `/__test/analysis-job` (the queue consumer on one job, reporting ack or retry), `x-apm-test-queue: fail` (an analysis queue that refuses every send) and `x-apm-test-fault: event-insert` (every public-log insert fails inside Postgres) only for callers holding a per-run secret that the deployed Worker never has. Tests that race a request against a lock open their own Postgres connection to the registry's database.

Why not PGlite: Miniflare's Hyperdrive simulation connects over TCP, so PGlite would need its socket server, which serves one connection at a time, while a request here can hold two (the store and Better Auth) and the queue consumer runs in parallel. PGlite is also not Postgres 18. This machine has Postgres 18 installed, CI installs it from PGDG, and Neon runs 18, so the suite tests the same SQL that production runs. Why not `wrangler dev`: Miniflare's API starts in well under a second per registry, takes bindings as plain options and needs no config file per test.

`packages/registry/test` holds the second-factor, body-limit and migration-lock unit tests; the database ones run against a fresh Postgres database through the real `Store`. `packages/infra/test` checks that `deploy.ts plan` changes nothing. `packages/infra/smoke.ts` checks a deployed stage with stock clients.

## Rat Stack

The project follows [Rat Stack](https://ratstack.sh) where it applies: Effect 4.1.2 services with typed errors, `@effect/sql-pg` 4.1.2, Alchemy 2.0.0-beta.85 declaring every cloud resource in one TypeScript program, everything on Cloudflare, exact version pins. Where it differs, and why:

| Rat Stack | apm | Why |

| Effect-native Workers (`Cloudflare.Worker(..., Effect.gen(...))`) | A plain module Worker running an Effect program | The bundle the suite tests is byte for byte the bundle Alchemy uploads, and it runs under Miniflare without Alchemy's dev runtime. |
